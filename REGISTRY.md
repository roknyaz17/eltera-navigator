# Единый реестр заявок

Раздел `/registry` — одно место, где видно все актуальные потребности всех
контрагентов в одинаковом виде, независимо от того, кто и в каком формате
прислал исходник.

## Как устроено

```
источник (TG-пост, строка таблицы, Seatable, ручной ввод)
   ↓  экстрактор — знает формат, отдаёт RawRequest
registry.ingest — дедупликация по (source, source_ref)
   ↓  content_hash совпал → LLM не вызывается вообще
vacancy_parser — только ИЗВЛЕКАЕТ то, что написано
   ↓
registry.normalize — унификация по справочникам
   ↓
SQLite: requests → positions (+ история, ревизии, FTS)
   ↓
/registry (работа менеджера) · /vacancies · /navigator · выгрузка в Sheets
```

**Заявка** (`ELT-2026-000123`) — входящий документ: пост в канале, строка
таблицы, письмо. Хранит исходный текст целиком и все свои прошлые версии.

**Позиция** (`ELT-2026-000123-01`) — конкретная потребность внутри заявки.
ID выдаётся один раз и не меняется никогда, даже если поменяются город,
должность или ставка.

## Развёртывание на новую базу

Порядок важен: интерфейс читает из SQLite, поэтому до миграции реестр пуст.

```bash
python scripts/migrate_from_sheets.py --dry-run
```

```bash
python scripts/migrate_from_sheets.py
```

```bash
python scripts/seed_dictionaries.py
```

После сида откройте `/registry/dictionaries`, просмотрите предложенные
соответствия и подтвердите. Пока вариант не подтверждён, он в реестре
показывается как есть — ничего не склеивается за спиной у человека.
Если список просмотрен целиком и устраивает, можно подтвердить пачкой:

```bash
python scripts/seed_dictionaries.py --confirm
```

И обязательно — пересчёт по подтверждённым справочникам. Миграция
нормализовала данные, когда справочники были ещё пусты, поэтому без этого шага
старые позиции останутся со старыми формулировками:

```bash
python scripts/renormalize.py --dry-run
```

```bash
python scripts/renormalize.py
```

Тот же скрипт запускают после каждой заметной правки справочников. Если после
пересчёта две позиции сходятся в одну, он их не склеивает, а называет обе —
разбираться должен человек.

Последний шаг миграции — убрать следы правил, которые раньше достраивали данные
за контрагента (смена по умолчанию «день», «вахта → питание», «пищевое → медкнижка»,
регион по городу). Стирается только то, чему нет подтверждения в исходном тексте
заявки:

```bash
python scripts/clear_legacy_guesses.py --dry-run
```

```bash
python scripts/clear_legacy_guesses.py
```

После него ещё раз `renormalize.py` — регион вернётся из справочника, но уже как
решение человека, а не догадка модели. Стёртые значения остаются видны в истории
изменений позиции.

## База знаний по проектам (Яндекс.Диск Градуса)

Пост в канале Градуса — телеграмма: «BMJ, Шарапово, РФ до 55, грузчик 3520, вахта от
20». Того, что не меняется день ото дня, в нём нет физически: адреса объекта,
часов смены, что за склад, сколько человек в комнате, есть ли форма и
медкнижка. Всё это лежит у контрагента на публичном Яндекс.Диске — по папке на
проект, с описанием и фотографиями проживания.

```
папка проекта на диске           пост в канале
   ↓ scripts/index_vahtapro_disk      ↓
disk_projects (индекс в реестре)  →  project_kb: сопоставление по названию
                                      ↓
                            vacancy_parser: пост + СПРАВКА
```

Границы намеренные:

* **Справка не создаёт позиций.** Потребность, ставка, возраст, сроки — только
  из поста; в справке они устаревают. В промпте это сказано прямо, а
  проверяется скриптом (см. ниже).
* **Не уверены — не подставляем.** «Все инструменты» без города похоже на
  четыре папки одинаково; в таком случае заявка разбирается как раньше, без
  справки. Что подставилось и с какой уверенностью, видно в `raw_payload.kb`
  заявки — там же ссылка на папку, чтобы менеджер мог проверить.
* **Во время прогона в сеть за диском не ходим.** Индекс обновляется отдельно и
  недоступность диска прогон не роняет.

```bash
python -m scripts.index_vahtapro_disk           # инкрементально
python -m scripts.index_vahtapro_disk --stats   # что уже в индексе
python -m scripts.index_vahtapro_disk --match "🚀BMJ, Шарапово (Мос. Обл)"
```

Пайплайн сам обновляет индекс, если он старше `VAHTAPRO_KB_REFRESH_HOURS`.

**Кнопка «Фото объекта».** Та же папка нужна рекрутёру живьём: в карточке
`/navigator` у позиций Градуса появляется кнопка, ведущая в папку с
фотографиями на Яндекс.Диске. Один альбом в папке — ведёт прямо в него,
несколько — в папку проекта: выбирать за человека, какое из двух общежитий он
имел в виду, нельзя. Ссылку можно приложить к тексту кандидату — но только
галочкой, вручную.

Связь «позиция → папка» лежит в таблице `position_kb` и считается по полям
самой позиции (контрагент + объект + город), а не по заявке: пост-сводка
описывает десяток проектов сразу, и после нормализации уже не восстановить,
какая позиция из какого куска. Пересчитывается после каждого обхода диска и
каждого прогона, так что переименованная папка чинится сама. Не опознали —
кнопки нет: чужие фотографии хуже, чем никаких. Сейчас папка есть у 52 из 56
активных позиций Градуса; не опознаны те, где по названию нельзя выбрать между
двумя папками («Миксит» — склад или производство, «Атяшево» — Рузаевка или
Торбеево).

Совпадение требует бренда, а не только города: «BMJ, Шарапово» не подберёт себе
папку «Сбер Шарапово», даже если папки BMJ на диске нет. Что считать
географией, реестр знает из справочника городов (`registry/geo.py`).

**Сколько это дало.** `python -m scripts.vahtapro_ab_test --all` прогоняет
реальные заявки Градуса из реестра дважды — со справкой и без — и считает
заполненность полей. На 118 заявках (52 проекта): заполнено полей 2009 → 2882
(+43%), заполненность 40 → 60% от максимума. Больше всего прибавили
`uniform_available` (+68), `object_address` (+64, до этого не заполнялся
никогда), `housing_available` (+62), `object_name` (+60), `uniform_free` (+57),
`housing_conditions` (+50).

Две вещи, выясненные тем же замером и зашитые в код:

* **Место справки в промпте решает.** Та же справка, поданная в системном
  промпте до текста заявки, даёт втрое меньше: 474 заполненных поля против 566
  на одной и той же выборке. Поэтому она идёт последней, после текста поста.
* **Справка иногда «съедает» заявку целиком.** На одном посте из ста длинное
  описание уводило разбор в пустой ответ, и позиция терялась. Поэтому пустой
  результат со справкой перепроверяется по голому посту
  (`vacancy_parser.aparse_raw_ex`).

## Ставки рекрутёра

Раз в неделю контрагент присылает сетку — картинкой или таблицей. Руководитель
переносит её в `/navigator` → «Нормализация» → «Ставки». Из заявок этот слой не
приходит и прийти не может: это внутренняя договорённость.

Три способа выставления — это одна и та же строка правила с разной областью
действия (`registry/rates.py`):

| Стратегия | Область | Откуда взялась |
|---|---|---|
| На всего контрагента | объект пуст, должность пуста | «20 000 за кандидата, и точка» |
| Лестница по сменам | ступени «от N смен» | сетка Градуса: 15/20/30 смен → 15/20/23 тыс. |
| Выбранные объекты | объект (и, если нужно, должность) | лист ЯППИ: ТЭЦ Чульман по разрядам; таблица КНК «объект → ставка» |

Подбор идёт от частного к общему: правило по объекту и должности бьёт правило
по объекту, оно — правило по контрагенту. У лестницы в карточке показывается
ступень, соответствующая «вахте от N смен» этой позиции, а вся лестница —
в «Подробнее»: платят-то по факту отработанного.

Что осталось за скобками сознательно:

* **Надбавки — текстом.** «Повторная вахта — 50%», «физлицам ниже на 5 000»,
  «КЗ/КГ без документов — 10 000» показываются рекрутёру строкой. Посчитать их
  нельзя: реестр не знает, повторная ли это вахта и кто рекрутёр.
* **Срок действия виден, но ничего не прячет.** Истёкшая сетка помечается
  жёлтым и в карточке, и во вкладке — «не задана» вместо суммы было бы враньём.
* **Область переписывается целиком.** Новая сетка контрагента заменяет
  прежнюю: иначе ступень «30 смен» из июля осталась бы висеть рядом с августом.
* **Каждое изменение пишется в историю** — с датой и логином того, кто менял.

Кнопка «Проверить, кого коснётся» считает число позиций до сохранения: ставка
выставляется на весь контрагент разом, и «затронет 56 позиций» лучше увидеть
заранее.

То же самое без интерфейса — `python -m scripts.recruiter_rates`
(`list`, `set`, `import` из CSV, `delete`).

## Переменные окружения

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `REGISTRY_DB_PATH` | `data/registry.db` | файл базы; в контейнере — volume `registry-data` |
| `REGISTRY_ENABLED` | `1` | `0` — аварийный откат на прежний путь через Google Sheets |

| `VAHTAPRO_KB_REFRESH_HOURS` | `6` | как часто прогон переобходит диск |

## Что важно знать при работе

**Контрагент — это источник, а не бренд заказчика.** Контрагентов пять: ЯППИ,
Градус, КНК, Аметист, ААА+ — с ними есть договорённости, чаты и ставки. То, что
парсер Градуса и ЯППИ кладёт в поле `counterparty` («BMJ», «Молком»,
«Все инструменты»), — это заказчик, объект внутри контрагента. Раньше панель
«Контрагенты» строилась по этому полю и показывала три десятка «контрагентов»,
которых нет; теперь карточек пять, а заказчики перечислены внутри карточки.
Запросы недостающих данных группируются так же — их получает контрагент, а не
бренд.

**В запросе контрагенту нет наших номеров.** `ELT-2026-000024` — идентификатор
реестра, в переписке контрагента такого номера нет, и одна заявка часто держит
несколько позиций, так что номер их даже не различает. Позиция опознаётся тем,
что контрагент прислал сам: город и регион, заказчик или объект, его
формулировка должности, ставка и график. Позиции сгруппированы по месту и
пронумерованы по порядку в сообщении — на них и отвечают. Каждое недостающее
поле объяснено в конце письма одной строкой («проживание: есть или нет; если
есть — что за жильё и сколько удерживаете»), иначе на «отсутствует проживание»
приходит «есть» и вопрос про удержание уходит вторым кругом.

**ВахтаПро теперь Градус.** Переименован только контрагент: во всех интерфейсах,
логах и выгрузках он называется «Градус». Ключ источника остался прежним —
`vahtapro` в колонке `source`, `TELEGRAM_VAHTAPRO_CHAT_ID` в переменных
окружения, `source="vahtapro"` в метках метрик. Переименовать его — значит
переписать историю заявок и разорвать ряды в Grafana ради названия, поэтому
ключ не тронут, а `--sources gradus` принимается как синоним `vahtapro`.

**Google Таблица стала витриной.** Она перезаписывается из реестра после
каждого прогона. Правки, сделанные прямо в ней, будут потеряны — статусы,
приоритеты и комментарии редактируются в `/registry`.

**Пустое поле означает, что этого не было в заявке.** Модели запрещено
достраивать данные: нет упоминания смены — колонка «Смена» пустая, нет
региона — пустой регион. Раньше часть таких полей заполнялась догадкой, и
отличить её от факта было невозможно. Фильтр «есть незаполненные поля»
показывает, к каким контрагентам стоит идти за уточнениями.

**Регион по городу** подставляется только из справочника `city_region`, и
только из подтверждённой его части.

**Неизменившиеся заявки не разбираются повторно.** При четырёх прогонах в день
это основная экономия на LLM: в логах смотрите `LLM-вызовов сэкономлено`.
На боевом прогоне 32 заявок Аметиста и Маркетстаффа: первый раз — 32 вызова,
127 тыс. токенов, 2,60 ₽, 40 секунд; повторный без изменений в источниках —
0 вызовов, 0 ₽, 17 секунд.

**Первый прогон после миграции — платный целиком.** У перенесённых заявок ключ
документа свой (`legacy:<хэш>`), у собранных заново — свой, совпадений нет.
Экономия начинается со второго прогона.

**Позиция может завестись заново, если в старой таблице она лежала в нескольких
экземплярах.** Прежний ID был хэшем и менялся от любой правки, поэтому одна и та
же позиция там встречается по 2–4 раза с разным написанием города. Выбирать из
них автоматически нельзя — приём заводит одну чистую запись, а старые копии
остаются в архиве. Если на какой-то из копий был статус или комментарий
менеджера, его придётся перенести руками.

## Тесты

```bash
python -m pytest
```

Тесты не требуют ни ключей, ни сети: разбор подменяется заглушкой, база
поднимается во временном каталоге.
