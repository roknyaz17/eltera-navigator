## Безопасность

Как сейчас (проверено по коду и на рабочем сервере).

Приложение — FastAPI + uvicorn + Jinja2 + APScheduler поверх SQLite (WAL, FTS5), запуск
`uvicorn app:app --host 0.0.0.0 --port 8000` (`Dockerfile:33`). Всё, что связано с доступом,
живёт в двух местах: `security = HTTPBasic()` (`app.py:188`) и зависимость
`verify_creds(creds) -> str` (`app.py:191-207`).

- Учётные данные — **одна общая пара** `WEB_USER` / `WEB_PASSWORD` (`app.py:192-193`),
  пароль в окружении в открытом виде. Ролей, пользователей, сессий и выхода нет.
  Сравнение — `secrets.compare_digest` по логину и паролю отдельно (`app.py:199-200`).
- При пустой любой из двух переменных отдаётся **`HTTPException(500, "WEB_USER / WEB_PASSWORD
  не настроены в .env")`** (`app.py:194-198`), а не 401.
- Возвращённое имя пользователя используется как авторство ровно в двух местах:
  `author` правил ставки (`app.py:434`, `:435`, `:447` → `recruiter_rate_history`) и
  `raw_payload.entered_by` ручной заявки (`app.py:823`). В `position_history` автора нет вообще —
  колонки под него в схеме не существует (`registry/db.py:131-139`).
- **Без авторизации открыты**: `GET /health` (`app.py:211-217`), `GET /metrics` (`app.py:279-292`),
  `GET /jobs` (`app.py:314-325`), `/static/*` (`app.py:184`), а также `/docs`, `/redoc`
  и `/openapi.json` — они включены по умолчанию, потому что приложение создаётся как
  `FastAPI(title="Eltrea Bot", lifespan=lifespan)` без `docs_url=None` (`app.py:181`).
  Наружу уходят состав задач планировщика, потребность и средние ставки по источникам,
  доля пустых полей, расход LLM и полная карта роутов со схемами.
- Middleware в приложении нет вообще (кроме монтирования `StaticFiles`): ни CORS, ни CSRF,
  ни ограничения частоты, ни security-заголовков.
- Публичной проекции нет: `GET /api/navigator` (`app.py:378-397`) отдаёт весь внутренний
  payload разом — ставку рекрутера, контрагента, объект, адрес, исходный текст заявки
  (`navigator_api.build_payload`, `navigator_api.py:715-780`). Единственный барьер —
  клиентский `scrub()` в `templates/navigator.html:448-461`, то есть последний рубеж,
  а не первый. Ни `PUBLIC_FIELDS`, ни таблицы `position_public` в проекте нет.
- В `templates/navigator.html:99-100` захардкожен пароль админ-панели `ADMIN_PASS = '1207'`
  и ключ `localStorage` `eltera_navigator_admin_v1`; проверка целиком клиентская
  (`authed()` `:622`, `openAdmin()` `:626`). Роут `/admin` отсутствует — за «админкой» стоят

### SEC-02. 401 вместо 500 при незаданных учётных данных и проверка конфигурации на старте

**Что нужно сделать.** Переписать `verify_creds` (`app.py:191-207`) так, чтобы отсутствие
`WEB_USER`/`WEB_PASSWORD` давало `401` с заголовком `WWW-Authenticate: Basic`, а не `500`.
Отдельно добавить проверку конфигурации в `lifespan` (`app.py:168-178`), чтобы приложение
не поднималось молча с пустыми учётными данными.

**Как должна работать логика.**

1. `verify_creds`: если `WEB_USER` или `WEB_PASSWORD` пусты — записать в лог **один раз**
   (флаг модуля, чтобы не засорять журнал на каждом запросе) сообщение уровня ERROR
   «WEB_USER / WEB_PASSWORD не настроены — доступ закрыт» и вернуть тот же
   `HTTPException(401, "Неверный логин или пароль", headers={"WWW-Authenticate": "Basic"})`,
   что и при неверной паре. Текст ответа обязан совпадать: снаружи не должно быть видно
   разницы между «сервер не настроен» и «пароль неверный».
2. Сравнение выполнять всегда, даже когда переменные пусты: сначала посчитать
   `secrets.compare_digest` по обоим полям против фактических (возможно пустых) значений,
   и только потом принимать решение. Это убирает разницу во времени ответа между случаями.
3. Сообщение об ошибке одинаково для неверного логина и неверного пароля (сейчас уже так —
   не сломать при правке).
4. В `lifespan` до `scheduler.start()` добавить `_check_config()`: если `WEB_USER` или
   `WEB_PASSWORD` пусты и переменная `ALLOW_INSECURE_START` не выставлена в `1` — писать
   CRITICAL в лог и завершать процесс с ненулевым кодом (`raise RuntimeError`). При
   `ALLOW_INSECURE_START=1` — стартовать, но писать WARNING на каждом старте.
   Смысл: конфигурационная ошибка должна проявляться при запуске, а не через часы
   первым же 500 у пользователя.
5. Ту же проверку выполнять для `METRICS_USER`/`METRICS_PASSWORD`, если они заданы частично
   (задан логин без пароля — ошибка конфигурации).

**Экраны и компоненты.** `app.py`: `verify_creds` (`:191-207`), `lifespan` (`:168-178`),
`verify_metrics` из SEC-01. Новый тест `tests/test_auth_http.py` на `fastapi.testclient`.

**Зависимости.** SEC-01 (зависимость `verify_metrics` появляется там). Вопросами из
`docs/OPEN-QUESTIONS.md` не заблокировано.

**Критерии готовности.**
- При пустых `WEB_USER`/`WEB_PASSWORD` и `ALLOW_INSECURE_START=1` запрос `GET /registry`
  без заголовка `Authorization` → `401`, заголовок ответа содержит `WWW-Authenticate: Basic`;
  тело не содержит слов «не настроены» и имён переменных окружения.
- Запрос с любыми учётными данными при пустых переменных → `401`, а не `200` и не `500`.
- При пустых `WEB_USER`/`WEB_PASSWORD` без `ALLOW_INSECURE_START` процесс не поднимается:
  `uvicorn app:app` завершается с ненулевым кодом, в логе строка уровня CRITICAL.
- Тело ответа при неверном логине и при неверном пароле побайтово одинаково.
- В `logs/eltera.log` при 100 запросах без учётных данных сообщение «не настроены»
  встречается не более одного раза.
- Тест `tests/test_auth_http.py` покрывает четыре случая: нет переменных, неверная пара,
  верная пара, отсутствие заголовка.

**Приоритет.** P0.

**Риски.** Падение процесса при пустой конфигурации — намеренное поведение, но на сервере,
где `.env` подставляется оркестратором после старта, это даст цикл перезапусков; поэтому
предусмотрен `ALLOW_INSECURE_START`. Смена 500 → 401 меняет поведение внешнего мониторинга,
если он считает 401 «нормой», а 500 — инцидентом.

### SEC-04. Модель пользователей и ролей

**Что нужно сделать.** Завести в схеме реестра таблицы пользователей и ролей отдельной
**новой** миграцией v7 в `registry/db.py` (`MIGRATIONS` сейчас содержит шесть элементов,
`registry/db.py:39`) и дать инструмент заведения пользователей из командной строки.
Правка существующих миграций запрещена: DDL v1 собирается из списков полей `models.py`
и на боевой базе повторно не исполняется.

**Как должна работать логика.**

1. Миграция v7 создаёт четыре таблицы:
   - `users`: `user_id TEXT PRIMARY KEY` (формат `USR-0001`, счётчик через существующий
     `id_counters`, scope `user`), `login TEXT NOT NULL UNIQUE` (нормализация: trim + lower),
     `full_name TEXT NOT NULL DEFAULT ''`, `email TEXT NOT NULL DEFAULT ''`,
     `password_hash TEXT NOT NULL`, `password_algo TEXT NOT NULL DEFAULT 'argon2id'`,
     `is_active INTEGER NOT NULL DEFAULT 1`, `must_change_password INTEGER NOT NULL DEFAULT 1`,
     `failed_attempts INTEGER NOT NULL DEFAULT 0`, `locked_until TEXT`,
     `created_at TEXT NOT NULL`, `updated_at TEXT NOT NULL`, `last_login_at TEXT`.
   - `roles`: `role TEXT PRIMARY KEY`, `title TEXT NOT NULL`, `description TEXT NOT NULL
     DEFAULT ''`. Наполняется в той же миграции четырьмя ролями из `docs/ROLES-AND-ACCESS.md`:
     `recruiter` («Рекрутер»), `admin` («Администратор»), `service` («Робот, сервисный
     аккаунт»), `readonly` («Только чтение»).
   - `user_roles`: `user_id TEXT NOT NULL REFERENCES users(user_id) ON DELETE CASCADE`,
     `role TEXT NOT NULL REFERENCES roles(role)`, `granted_at TEXT NOT NULL`,
     `granted_by TEXT NOT NULL DEFAULT ''`, `PRIMARY KEY (user_id, role)`.
     Роли не иерархичны: администратору выдаются обе записи, если он должен видеть подбор.
   - `login_audit`: `id INTEGER PRIMARY KEY AUTOINCREMENT`, `at TEXT NOT NULL`,
     `login TEXT NOT NULL`, `user_id TEXT`, `result TEXT NOT NULL`
     (`ok` | `bad_password` | `unknown_user` | `locked` | `disabled` | `logout`),
     `ip TEXT NOT NULL DEFAULT ''`, `user_agent TEXT NOT NULL DEFAULT ''`.
     Индексы `idx_login_audit_at(at)`, `idx_login_audit_login(login, at)`.
   Пароль в `login_audit` не пишется никогда, ни в каком виде.
2. Новый модуль `registry/users.py`: `hash_password(raw) -> str`, `verify_password(raw, hash)
   -> bool`, `needs_rehash(hash) -> bool`, `create_user`, `set_password`, `disable_user`,
   `grant_role`, `revoke_role`, `get_user_by_login`, `roles_of(user_id)`, `log_login(...)`.
   Алгоритм — argon2id (`argon2-cffi`); добавить зависимость в `requirements.txt`
   с фиксированной версией. Параметры вынести константами модуля, `needs_rehash` перехеширует
   при их изменении на успешном входе.
3. CLI `scripts/manage_users.py` с подкомандами `add`, `list`, `disable`, `enable`,
   `set-password`, `grant`, `revoke`. Пароль читается через `getpass`, не аргументом
   командной строки (иначе он останется в истории shell). Веб-интерфейса управления
   пользователями в этой задаче нет.
4. Первичное заведение: если таблица `users` пуста, а `WEB_USER`/`WEB_PASSWORD` заданы,
   миграция **не** создаёт пользователя автоматически (пароль в открытом виде переносить
   в хеш молча нельзя — он мог утечь). Вместо этого при старте пишется WARNING
   «пользователей нет, работает совместимый режим HTTP Basic; заведите администратора
   через scripts/manage_users.py».
5. Требования к паролю при заведении и смене: минимум 12 символов, запрет на совпадение
   с логином, запрет на значения из короткого списка очевидных (`admin`, `123456`, `1207`,
   `eltera2026`). Проверка в `registry/users.py`, а не в CLI, чтобы действовала и из веба.

**Экраны и компоненты.** `registry/db.py` (новый элемент `MIGRATIONS`), новый
`registry/users.py`, новый `scripts/manage_users.py`, `requirements.txt`,
`tests/test_users.py`, `.env.example` (пометить `WEB_USER`/`WEB_PASSWORD` как совместимый режим).

**Зависимости.** Блокируется вопросом **C1** «Роли: как заводятся пользователи» из
`docs/OPEN-QUESTIONS.md`: от ответа зависит, заводит ли учётки администратор Навигатора
или хозяин записей — Кабинет Eltera (тогда вместо локальных паролей нужен внешний провайдер).
По умолчанию принят вариант 1 (личный вход, заводит администратор) — при этом допущении
задачу можно начинать, зафиксировав его в шапке миграции.
Также зависит от вопроса **D1** «Отдельная команда миграции» и от задачи направления
«Эксплуатация» (`OPS-*`), заводящей явную команду миграции и резервную копию: накат v7
на боевую базу без бэкапа выполнять нельзя.

**Критерии готовности.**
- `PRAGMA user_version` на новой базе равен 7; на существующей после запуска — тоже 7,
  прежние данные на месте (проверяется числом строк в `positions` до и после).
- `python scripts/manage_users.py add --login ivanov --role admin` создаёт запись;
  повторный вызов с тем же логином завершается ошибкой «логин занят», а не дублем.
- В `users.password_hash` строка начинается с `$argon2id$`; исходного пароля в базе нет
  (`grep` по дампу `sqlite3 registry.db .dump` не находит введённого пароля).
- `verify_password` возвращает `True` для верного пароля и `False` для неверного;
  тест на 12-символьный минимум и на запрет пароля, равного логину.
- `scripts/manage_users.py list` показывает логин, роли, активность, дату последнего входа;
  пароль или хеш в выводе не печатается.
- В `login_audit` можно записать строку с `result='bad_password'` и в ней нет поля с паролем.
- `tests/test_users.py` проходит: создание, выдача и снятие роли, блокировка, перехеширование
  при смене параметров.

**Приоритет.** P0.

**Риски.** Ошибка в новой миграции блокирует запуск приложения целиком — схема накатывается
при первом обращении к базе, то есть на первом же HTTP-запросе после деплоя. Перед выкатом
обязательна копия `data/registry.db` вместе с `-wal` и `-shm`. Argon2 — новая нативная
зависимость: проверить сборку в образе `python:3.11-slim` до выката.

### SEC-05. Серверные сессии: вход, хеш пароля, ограничение попыток, журнал, выход

**Что нужно сделать.** Заменить HTTP Basic серверной сессией: форма входа, cookie-сессия
в базе, ограничение числа попыток, журнал входов и явный выход. HTTP Basic остаётся
временно как совместимый режим для скриптов и `smoke_navigator.js`, но проверяется уже
против таблицы `users`, а не против `WEB_USER`/`WEB_PASSWORD`.

**Как должна работать логика.**

1. Миграция v8: таблица `sessions` — `session_id TEXT PRIMARY KEY` (это **sha256 от токена**,
   сам токен в базе не хранится), `user_id TEXT NOT NULL REFERENCES users(user_id) ON DELETE
   CASCADE`, `created_at TEXT NOT NULL`, `last_seen_at TEXT NOT NULL`, `expires_at TEXT NOT
   NULL`, `ip TEXT NOT NULL DEFAULT ''`, `user_agent TEXT NOT NULL DEFAULT ''`,
   `revoked_at TEXT`. Индексы `idx_sessions_user(user_id)`, `idx_sessions_expires(expires_at)`.
2. Токен сессии — `secrets.token_urlsafe(32)`. Cookie `eltera_session`: `HttpOnly`,
   `SameSite=Lax`, `Path=/`, `Secure` при `FORCE_SECURE_COOKIE=1` либо когда схема запроса
   `https`. Срок — `WEB_SESSION_TTL_HOURS` (по умолчанию 12). Продление скользящее:
   при активности реже раза в 5 минут обновляется `last_seen_at` и `expires_at`.
3. Роуты: `GET /login` (страница входа, без авторизации), `POST /login` (form: `login`,
   `password`, `next`), `POST /logout`. Шаблон `templates/login.html` — тёмная тема
   Навигатора, минимальный самостоятельный `<head>` (общего базового шаблона в проекте нет).
   Успешный вход → 303 на `next`, если он начинается с `/` и не содержит `//`
   (защита от открытого редиректа); иначе на `/`.
4. Проверка пароля: `verify_password` из SEC-04. Для несуществующего логина всё равно
   выполняется проверка против фиктивного хеша — время ответа не должно выдавать, есть
   такой пользователь или нет. Текст ошибки один на все случаи: «Неверный логин или пароль».
5. Ограничение попыток: после 5 неудач подряд по одному логину — блокировка на 15 минут
   (`users.failed_attempts`, `users.locked_until`); успешный вход обнуляет счётчик.
   Параллельно — не более 20 неудачных попыток с одного IP за 15 минут, дальше `429`.
   Заблокированному отвечать тем же текстом «Неверный логин или пароль» плюс строкой
   «Повторите попытку позже», без указания оставшегося времени.
6. Журнал: каждая попытка пишется в `login_audit` (`ok`, `bad_password`, `unknown_user`,
   `locked`, `disabled`), выход — `logout`. Хранение — не менее 12 месяцев, чистка не нужна.
7. Единая зависимость `current_user(request) -> User`: сначала cookie-сессия, при её
   отсутствии — HTTP Basic против `users` (совместимый режим, включается
   `LEGACY_BASIC_ENABLED`, по умолчанию `1`). Для HTML-роутов при отсутствии авторизации —
   303 на `/login?next=<путь>`; для роутов `/api/*` — `401` JSON. `verify_creds`
   (`app.py:191-207`) заменяется на `current_user` во всех роутах.
8. Авторство: везде, где сейчас используется строка из Basic — `author` правил ставки
   (`app.py:434`, `:435`, `:447`) и `raw_payload.entered_by` (`app.py:823`) — подставляется
   `user.login`. Это же значение готовится для колонки автора в `position_history`,
   но саму колонку и запись правок менеджера заводит направление «Данные» (`DB-*`) —
   здесь только гарантируется, что объект пользователя доступен в обработчике.
9. Выход: кнопка в шапке `templates/navigator.html` и в `templates/registry.html`
   (форма `POST /logout`, с CSRF-токеном из SEC-09). Оформление кнопки — за направлением
   «Интерфейс»; здесь достаточно рабочего элемента.
10. Все сессии пользователя отзываются при смене пароля и при `disable_user`.

**Экраны и компоненты.** `registry/db.py` (миграция v8), `registry/sessions.py` (новый),
`app.py` (роуты `/login`, `/logout`, замена зависимости во всех обработчиках),
новый `templates/login.html`, `templates/navigator.html` и `templates/registry.html`
(кнопка выхода), `scripts/manage_users.py` (подкоманда `revoke-sessions`),
`tests/test_auth_http.py`.

**Зависимости.** SEC-04 (таблицы и хеширование), SEC-02 (поведение при неверных данных),
SEC-09 (CSRF на форму входа и выхода — выкатывать вместе или сразу после).
Блокируется вопросом **C1**: если принят вариант 3 (внешний SSO), локальные пароли не нужны
и задача превращается в интеграцию с провайдером. По умолчанию принят вариант 1.

**Критерии готовности.**
- `POST /login` с верной парой возвращает 303 и `Set-Cookie: eltera_session=...; HttpOnly;
  SameSite=Lax; Path=/`; значение cookie отсутствует в таблице `sessions` (там лежит sha256).
- Запрос `GET /navigator` с этой cookie → `200`; без неё → `303` на `/login?next=/navigator`.
- `GET /api/navigator` без cookie и без Basic → `401` (не редирект).
- Шесть подряд неверных паролей по одному логину: шестая попытка не входит даже
  с верным паролем в течение 15 минут; в `login_audit` пять строк `bad_password`
  и одна `locked`.
- Время ответа `POST /login` для несуществующего логина и для существующего с неверным
  паролем различается не более чем на 20% на 50 замерах.
- `POST /logout` → cookie аннулирована, `sessions.revoked_at` заполнен, повторный запрос
  с той же cookie → редирект на `/login`.
- Сессия старше `WEB_SESSION_TTL_HOURS` не пускает; запись в `sessions` остаётся с истёкшим
  `expires_at`.
- `next=https://evil.example` не приводит к редиректу на внешний адрес.
- После правки правила ставки под пользователем `ivanov` в `recruiter_rate_history.author`
  лежит `ivanov`, а не значение `WEB_USER`.
- `smoke_navigator.js` продолжает работать: `curl -u login:password .../api/navigator`
  отдаёт 200 при `LEGACY_BASIC_ENABLED=1`.

**Приоритет.** P0.

**Риски.** Это единственная задача, которая ломает вход всем одновременно: пока
пользователи не заведены (SEC-04), включать обязательный режим нельзя. Поэтому
совместимый Basic оставлен по умолчанию включённым, а отключение `WEB_USER`/`WEB_PASSWORD` —
последний шаг, вынесенный в SEC-14. Cookie без `Secure` на http-сервере (сейчас доступ идёт
по `http://`, без TLS) передаётся открытым текстом — до включения TLS сессия защищает
не сильнее Basic; это ограничение обязано быть записано в `docs/LIMITATIONS.md`.

### SEC-06. Разграничение по ролям на сервере

**Что нужно сделать.** Ввести проверку прав на каждом роуте `app.py`, а не скрытием
элементов в вёрстке. Сейчас любой прошедший Basic получает и чтение, и запись: справочники,
ручной ввод, запуск прогонов, правила ставок.

**Как должна работать логика.**

1. Фабрика зависимостей `require(*roles)` в `app.py` (или в новом `auth.py`):
   возвращает `current_user`, если у пользователя есть хотя бы одна из перечисленных ролей,
   иначе `403` (не 401 — пользователь опознан, но прав нет). Для HTML-роутов `403`
   отдаётся страницей с текстом «Недостаточно прав», без перечисления доступных ролей.
2. Матрица прав (роли из SEC-04, требования — из `docs/ROLES-AND-ACCESS.md`):

   | Роут | recruiter | admin | service | readonly |
   |---|---|---|---|---|
   | `GET /`, `/navigator`, `/api/navigator` | да | да | нет | да |
   | `GET /registry`, `/api/registry`, `/registry/{request_id}`, `/registry/position/{id}` | да | да | нет | да |
   | `GET /registry/export.csv` | нет | да | нет | нет |
   | `POST /registry/position/{id}` | нет | да | нет | нет |
   | `GET/POST /registry/dictionaries*` | нет | да | нет | нет |
   | `GET/POST /registry/manual` | нет | да | нет | нет |
   | `POST /api/rates`, `DELETE /api/rates/{id}` | нет | да | нет | нет |
   | `POST /trigger/{name}`, `POST /run` | нет | да | нет | нет |
   | `GET /jobs`, `GET /health/details` | нет | да | нет | нет |
   | `GET /metrics` | нет | да | да | нет |
   | `GET /vacancies`, `/api/vacancies` | да | да | нет | да |

   Матрицу продублировать в `docs/ROLES-AND-ACCESS.md` — она там уже описана словами,
   привести к тому же виду.
3. Запрет по умолчанию: тест перебирает `app.routes` и требует, чтобы у каждого роута была
   зависимость авторизации, кроме явного списка исключений (`/health`, `/login`, `/static`,
   `/webhook/...`). Новый роут без зависимости роняет тест — это единственный надёжный способ
   не забыть про очередной обработчик.
4. Клиент получает права, а не вычисляет их: в payload `/api/navigator` добавляется
   `perms: {admin: bool, rates: bool, dictionaries: bool, manual: bool, run: bool}`
   (`navigator_api.build_payload`). Вкладка «Админ» и её подвкладки рендерятся по `perms`,
   но сервер всё равно проверяет права на каждом вызове — скрытие в вёрстке считается
   удобством, а не защитой.
5. В `templates/registry.html` кнопки «+ Заявка вручную», «Справочники», «Выгрузить CSV»
   скрываются для роли `recruiter`; в контекст шаблона добавляется `perms`.
6. Ответ `403` логируется на уровне WARNING с логином, ролью и путём — это первый сигнал
   о неправильно выданных правах.

**Экраны и компоненты.** `app.py` (все роуты), `navigator_api.build_payload`
(`navigator_api.py:715-780`), `templates/navigator.html` (вкладка «Админ», `viewAdmin`
`:1230-1292`), `templates/registry.html`, `docs/ROLES-AND-ACCESS.md`,
`tests/test_permissions.py`.

**Зависимости.** SEC-04, SEC-05, SEC-03 (после неё вкладка «Админ» уже управляется
серверным флагом). Блокируется вопросом **C1** — от него зависит, нужен ли рекрутеру личный
вход или достаточно общей учётки на отдел; при варианте 2 роль `recruiter` выдаётся одной
общей записи, и авторство правок в подборе становится недостижимым.

**Критерии готовности.**
- Пользователь только с ролью `recruiter`: `GET /navigator` → `200`;
  `POST /api/rates` → `403`; `GET /registry/dictionaries` → `403`;
  `POST /run` → `403`; `GET /registry/export.csv` → `403`.
- Пользователь с ролью `admin`: те же запросы → `200`/`303`.
- Пользователь без ролей: любой защищённый роут → `403`.
- Тест «запрет по умолчанию» перечисляет все роуты приложения и падает, если у роута нет
  зависимости авторизации и он не в списке исключений.
- В ответе `/api/navigator` под ролью `recruiter` `perms.admin === false`, и вкладка «Админ»
  в разметке отсутствует (проверяется `smoke_navigator.js` на сохранённом ответе).
- Каждый `403` порождает ровно одну строку WARNING в `logs/eltera.log` с логином и путём.

**Приоритет.** P1.

**Риски.** Ошибка в матрице закрывает работающим рекрутерам нужный экран посреди дня;
выкатывать с заранее заведёнными ролями и с возможностью быстро выдать `admin` через CLI.
Роль `service` пока не используется ничем, кроме `/metrics` — не выдавать её людям.

### SEC-07. Белый список PUBLIC_FIELDS и физическое разделение проекций

**Что нужно сделать.** Ввести белый список публичных полей и построить публичную проекцию
позиции **отдельным кодом**, а не вычитанием полей из внутренней. Сегодня
`GET /api/navigator` отдаёт всё: ставку рекрутера (`rec`), контрагента (`cp`), объект (`obj`),
адрес (`addr`), внутренние идентификаторы (`id`, `ext`), исходный текст заявки (`raw`)
и по-полевую расшифровку (`rawFields`) — см. `navigator_api.position_row`
(`navigator_api.py:348-436`) и `build_payload` (`:715-780`).

**Как должна работать логика.**

1. В `registry/models.py` появляется `PUBLIC_FIELDS: frozenset[str]` — единственный источник
   правды о том, что можно показать наружу. Стартовый состав (по `docs/ROLES-AND-ACCESS.md`):
   должность, город, регион, район, ставка за смену и за час, график, тип смены, часы,
   минимум смен, формат работы, пол, возраст от/до, гражданство (нормализованный список),
   требования, обязанности, плюсы, медкнижка, проверка СБ, проживание, питание, проезд,
   удержания, публичный алиас работодателя, публичные материалы.
   **Обязаны отсутствовать**: ставка рекрутера и всё из блока `rec`, `cp`, `cpTitles`, `obj`,
   `client`, `addr`, `src`/`srcKey`, `ext`, `position_id`, `raw`, `rawFields`, `citsRaw`,
   `sbRaw`, `conflicts`, `dupes`, `risks` (внутренняя оценка), любые `*_raw` поля.
2. Новый модуль `registry/public.py`:
   - `public_row(row) -> dict` — собирает словарь **с нуля**, перечисляя ключи явно.
     Ни `dict(row)`, ни `copy`, ни `pop`/`del` использовать нельзя: удаление лишнего —
     ровно тот способ, который однажды пропустит новое поле.
   - `public_ref(position_id) -> str` — публичный идентификатор, не равный `position_id`:
     `sha256(position_id + PUBLIC_REF_SALT)[:12]`. Соль — из окружения `PUBLIC_REF_SALT`.
     Нужен, чтобы наружу не уходила внутренняя нумерация `ELT-2026-000123-01`, но остался
     способ сопоставить обращение кандидата с позицией.
   - `assert_public(payload)` — служебная проверка: обходит структуру и падает, если
     встретился ключ вне `PUBLIC_FIELDS`. Вызывается в тестах и в режиме `DEBUG`.
3. Внутренняя проекция остаётся в `navigator_api.position_row` и переименовывается
   в `internal_row` — из имени должно быть видно, что она внутренняя. `build_payload`
   получает аргумент `projection: Literal["internal", "public"]`; ветки не делят общий
   словарь.
4. Роуты разводятся: `GET /api/navigator` — внутренний, под ролями (SEC-06);
   `GET /api/public/positions` — публичная проекция, отдельный сериализатор.
   Публичный роут в этой задаче наружу **не открывается**: он закрыт той же авторизацией
   и существует, чтобы проекция была готова раньше, чем понадобится. Открытие — отдельное
   решение вместе с направлением «Интеграции».
5. Публичный работодатель: пока сущности контрагента нет, `cpAlias` всегда пуст
   (`navigator_api.py:383`), и на публичной стороне показывается категория объекта
   (`vacancy_category`), а при её отсутствии — ничего. Никакого отката на `counterparty`
   быть не должно.
6. Материалы: в публичную проекцию попадают только записи с `vis == "public"`.
   Признак `alive` сейчас захардкожен (`navigator_api.py:341`) — на публичной стороне
   он не показывается вовсе, пока проверка живости не реализована направлением
   «Данные»/«Интеграции».

**Экраны и компоненты.** `registry/models.py` (`PUBLIC_FIELDS`), новый `registry/public.py`,
`navigator_api.py` (`position_row` → `internal_row`, `build_payload`), `app.py`
(новый роут `/api/public/positions`), `tests/test_public_projection.py`.

**Зависимости.** SEC-06 (роли на внутреннем роуте). Блокируется вопросом **C5** «Публичный
алиас контрагента» — от него зависит, что именно показывается кандидату вместо названия
контрагента; по умолчанию принят вариант 1 (алиас — поле контрагента), но самого поля нет,
пока направление «Данные» (`DB-*`) не заведёт `counterparties`. До этого работает правило
из пункта 5, и это допущение записывается в задаче и в `docs/`.
Частично связано с вопросом **B1** «Что такое контрагент».

**Критерии готовности.**
- `PUBLIC_FIELDS` объявлен в `registry/models.py`; в нём отсутствуют `position_id`, `cp`,
  `obj`, `addr`, `rec`, `src`, `ext`, любое имя, оканчивающееся на `_raw`.
- `public_row` не содержит вызовов `dict(row)`, `.pop(`, `del ` — проверяется тестом,
  читающим исходник модуля.
- Тест: в фикстуру внутренней строки добавляется несуществующее поле `secret_probe`;
  после `public_row` его в результате нет, тест на «удаление лишнего» не требуется.
- `GET /api/public/positions` не содержит подстрок из значений `counterparty`,
  `object_name`, `object_address`, `source_name` тестовой позиции (сентинельные значения
  вида `SENTINEL-CP`, `SENTINEL-OBJ`).
- `public_ref` для одной позиции стабилен между запросами и отличается от `position_id`;
  по нему нельзя восстановить `position_id` без соли.
- `assert_public` падает, если в публичный словарь вручную дописать ключ `rec`.
- `GET /api/navigator` продолжает отдавать прежний набор ключей — рабочий экран не сломан
  (`smoke_navigator.js` проходит).

**Приоритет.** P1.

**Риски.** Переименование `position_row` затрагивает `tests/test_project_kb.py`, который
проверяет медиа-блок; правку тестов заложить в задачу. Публичный идентификатор с солью:
смена `PUBLIC_REF_SALT` меняет все публичные ссылки разом — соль обязана быть постоянной
и лежать в том же хранилище, что и прочие секреты.

### SEC-08. Серверный стоп-словарь и тесты на утечку

**Что нужно сделать.** Перенести вырезание внутренних названий из браузера на сервер.
Сейчас `scrub()` живёт в `templates/navigator.html:448-461` и вырезает из текста кандидату
`r.cp`, `r.obj`, `r.src`, аккуратно не трогая ссылки; текст собирается там же
(`candidateText`, `:464-535`). Это последний рубеж вместо первого: тот же текст,
собранный любым другим клиентом, не будет очищен.

**Как должна работать логика.**

1. В `registry/public.py` (из SEC-07) добавляются:
   - `stop_terms(row, conn) -> list[str]` — стоп-словарь для конкретной позиции:
     `counterparty`, `counterparty_raw`, `object_name`, `object_address`, `source_name`,
     `vacancy_name_raw`, внешний номер заявки, плюс все алиасы из таблицы `dictionaries`
     с `kind='counterparty'`, у которых `canonical` равен контрагенту позиции
     (`registry/dictionaries.py`), плюс глобальный список из настройки `PUBLIC_STOP_WORDS`
     (значения через запятую).
   - `scrub_text(text, terms) -> tuple[str, list[str]]` — возвращает очищенный текст
     и перечень фактически вырезанных терминов (для показа блока «Вырезано стоп-словарём»).
2. Правила замены, повторяющие и уточняющие поведение клиента:
   - замена на `———`;
   - сравнение регистронезависимое, `ё` приравнивается к `е`;
   - термины короче 3 символов игнорируются (иначе аббревиатура вырежет пол-текста);
   - совпадение по границе слова, чтобы «АМ» не вырезалось внутри «АМЕТИСТ‑подобных» слов;
   - **URL не трогаются**: сначала все `https?://…`, `tg://…`, `mailto:…` выносятся
     плейсхолдерами, потом выполняется замена, потом ссылки возвращаются на место —
     ровно то, что уже делает клиент (`templates/navigator.html:451-459`);
   - термины сортируются по убыванию длины, чтобы длинное совпадение вырезалось раньше
     вложенного короткого.
3. Текст кандидату собирается на сервере: `GET /api/positions/{public_ref}/candidate-text`

   собирать текст сам и показывает пришедшее; блок «Вырезано стоп-словарём» заполняется
   из `removed`. Клиентские `scrub` и `candidateText` удаляются — два независимых
   генератора одного текста разойдутся при первой же правке.
4. Через `scrub_text` проходит **любой** свободный текст в публичной проекции:
   требования, обязанности, плюсы, условия проживания, условия проезда. Не только
   финальное сообщение.
5. Тесты `tests/test_public_leak.py`:
   - фикстура с сентинельными значениями `SENTINEL-CP`, `SENTINEL-OBJ`, `SENTINEL-SRC`,
     `SENTINEL-ADDR` во всех внутренних полях;
   - для каждой позиции: ни один сентинел не встречается ни в публичной проекции,
     ни в тексте кандидату, ни в списке материалов;
   - ссылка `https://disk.yandex.ru/d/SENTINEL-CP` остаётся целой (проверка, что вырезание
     не ломает адреса);
   - текст, где контрагент написан со строчной буквы и через `ё`, всё равно вырезается;
   - позиция без контрагента и объекта не приводит к вырезанию пустой строки (иначе
     весь текст превратится в `———`).
6. `smoke_navigator.js` продолжает проверять утечку `r.cp / r.obj / r.src`
   (`smoke_navigator.js:135-141`) — его не удалять, он ловит регресс на стороне разметки.

**Экраны и компоненты.** `registry/public.py`, `app.py` (новый роут текста кандидату),
`templates/navigator.html` (`scrub` `:448-461`, `candidateText` `:464-535`, модалка

**Зависимости.** SEC-07 (модуль публичной проекции и `public_ref`). Ответ на **C5**

### SEC-09. CSRF для форм, ограничение частоты и security-заголовки

**Что нужно сделать.** После перехода на cookie-сессии (SEC-05) все изменяющие запросы
становятся уязвимы к межсайтовой подделке: сейчас в приложении нет ни одного middleware,
ни CSRF-токена, ни ограничителя частоты. Добавить защиту форм, ограничение частоты
и базовые заголовки безопасности.

**Как должна работать логика.**

1. CSRF, схема «двойная отправка с привязкой к сессии»:
   - токен = `hmac_sha256(session_id, CSRF_SECRET)` в hex; отдаётся в cookie `eltera_csrf`
     (**без** `HttpOnly`, `SameSite=Lax`) при создании сессии;
   - для методов `POST`, `PUT`, `PATCH`, `DELETE` middleware требует совпадения токена
     из поля формы `csrf_token` **или** заголовка `X-CSRF-Token` со значением cookie,
     сверка через `secrets.compare_digest`;
   - дополнительно проверяется заголовок `Origin` (при отсутствии — `Referer`): хост обязан
     совпасть с хостом запроса. Отсутствие обоих у изменяющего запроса — отказ;
   - несовпадение → `403` с текстом «Сессия устарела, обновите страницу»;
   - **исключения**: запросы, аутентифицированные HTTP Basic (у них нет cookie, подделать
     их браузером нельзя), и роут вебхука (SEC-13, у него собственная проверка).
2. Формы, которые нужно дополнить скрытым полем `csrf_token`:
   `templates/registry_dictionaries.html` (три формы: `/registry/dictionaries/confirm`,
   `/delete`, `/confirm-all`), `templates/registry_manual.html` (`POST /registry/manual`),
   `templates/registry_position.html` (`POST /registry/position/{id}`),
   `templates/login.html` и форма выхода. GET-форма фильтров в `templates/registry.html`
   токена не требует.
3. `fetch` в `templates/navigator.html` (`POST /api/rates` `:1933`,
   `DELETE /api/rates/{id}` `:1951`, будущие вызовы) добавляет заголовок `X-CSRF-Token`,
   читая cookie `eltera_csrf`. `credentials: 'same-origin'` уже стоит.
4. Ограничение частоты — middleware со счётчиками в памяти процесса (планировщик и так
   требует одного воркера; при переходе на несколько воркеров ограничитель обязан
   переехать во внешнее хранилище — записать это в `docs/LIMITATIONS.md`).
   Лимиты по ключу «пользователь, иначе IP»:
   - `POST /login` — 10 запросов в минуту на IP;
   - `POST /run`, `POST /trigger/{name}` — 5 в час (запуск прогона стоит денег на LLM);
   - `/api/*` — 120 в минуту;
   - остальное — 300 в минуту.
   Превышение → `429` с заголовком `Retry-After` в секундах. Ответ `429` пишется в лог
   на уровне WARNING с ключом ограничения.
5. Security-заголовки для всех ответов: `X-Content-Type-Options: nosniff`,
   `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`,
   `Cache-Control: no-store` для `/api/*` и для HTML-страниц под авторизацией.
   CSP добавляется в отчётном режиме `Content-Security-Policy-Report-Only` с политикой
   `default-src 'self'; img-src 'self' data:; media-src 'self'; style-src 'self'
   'unsafe-inline' https://fonts.googleapis.com; font-src https://fonts.gstatic.com;
   script-src 'self' 'unsafe-inline'` — `'unsafe-inline'` неизбежен, пока весь скрипт
   Навигатора лежит в одном HTML; перевод на nonce фиксируется как отдельная задача
   направления «Интерфейс», здесь только заголовок и запись о нарушениях.
6. Ограничения размера тела: `POST /api/rates` и формы — не более 256 КБ; больше → `413`.

**Экраны и компоненты.** `app.py` (три middleware: CSRF, ограничение частоты, заголовки),
новый `security_middleware.py`, `templates/registry_dictionaries.html`,
`templates/registry_manual.html`, `templates/registry_position.html`, `templates/login.html`,
`templates/navigator.html` (`fetch` `:1929-1961`), `docs/LIMITATIONS.md`,
`tests/test_csrf_and_limits.py`.

**Зависимости.** SEC-05 (сессии и cookie — без них CSRF-токен не к чему привязать).
Вопросами из `docs/OPEN-QUESTIONS.md` не заблокировано.

**Критерии готовности.**
- `POST /registry/dictionaries/confirm` без поля `csrf_token` под валидной cookie → `403`;
  с корректным токеном → `303`.
- `POST /api/rates` из `fetch` с заголовком `X-CSRF-Token` → `200`; без заголовка → `403`.
- `POST /registry/manual` с корректным токеном, но заголовком `Origin: https://evil.example`
  → `403`.
- Запрос с HTTP Basic и без CSRF-токена → работает (`200`), совместимость скриптов сохранена.
- 11-й `POST /login` за минуту с одного IP → `429` с заголовком `Retry-After`.
- 6-й `POST /run` за час → `429`; в логе одна строка WARNING на каждое срабатывание.
- Любой ответ приложения содержит `X-Content-Type-Options: nosniff` и `X-Frame-Options: DENY`.
- `/navigator` открывается и работает при включённом `Content-Security-Policy-Report-Only`
  (визуальная проверка + `smoke_navigator.js`).
- Тело запроса 1 МБ на `POST /api/rates` → `413`.

**Приоритет.** P1.

**Риски.** Слишком строгий CSRF ломает работу через `curl` и дымовые прогоны — отсюда
исключение для Basic. Ограничитель частоты в памяти сбрасывается при перезапуске и не
работает при нескольких воркерах: это осознанное упрощение, но его нужно записать, иначе
в инциденте на него понадеются. `X-Frame-Options: DENY` сломает встраивание Навигатора
в iframe, если такое где-то используется — проверить до выката.

### SEC-10. Секреты не попадают в логи, образы и выгрузки

### SEC-11. Аудит TELEGRAM_SESSION и план перехода на технический аккаунт

**Что нужно сделать.** Зафиксировать, что чтение каналов идёт от лица живого Telegram-аккаунта,
оценить объём доступа и подготовить переход на отдельный технический аккаунт-«читатель».
`TELEGRAM_SESSION` — это `StringSession` Telethon (`telegram_userbot.py:27`, `pipeline.py:76`,
получение — `auth_userbot.py`), то есть полный доступ к аккаунту: вся личная переписка,
контакты, возможность отправлять сообщения от имени владельца. Токеном бота это не является.

**Как должна работать логика.**

1. Аудит, результат — `docs/SECURITY-TELEGRAM.md`:
   - чей аккаунт используется сейчас (номер телефона и username выясняются на шаге 2),
     кто имел к строке сессии доступ, где она хранилась и хранится (`.env` на сервере,
     резервные копии, переписка при передаче проекта, образ до правки `.dockerignore`

   - что произойдёт при утечке строки: чтение личной переписки владельца и отправка
     сообщений от его имени в чаты контрагентов.
2. Диагностика без догадок: при создании клиента Telethon (`telegram_userbot.py`) один раз
   за прогон логировать `me.id`, `me.username`, `me.phone` в маскированном виде
   (последние 4 цифры). Это даёт проверяемый ответ на вопрос «под кем мы читаем»
   и сразу покажет момент, когда сессия сменится на техническую.
3. План перехода (вариант 1 вопроса C2), пошагово, в том же документе:
   - отдельный номер и аккаунт, не привязанный к сотруднику; включённая двухфакторная

   - новая `StringSession` генерируется `auth_userbot.py` на рабочей машине,
     не на сервере, и сразу кладётся в хранилище секретов;
   - контрольный прогон `python main.py --sources vahtapro,aaaplus` и
     `--sources ametist` на новой сессии;
   - **старая сессия отзывается** в Telegram: «Настройки → Устройства → Завершить сеанс»;

   - в аккаунте технического читателя личной переписки нет, и это правило записывается.
4. До перехода — организационное ограничение: строка сессии не пересылается в мессенджерах

**Экраны и компоненты.** `telegram_userbot.py` (создание клиента), `auth_userbot.py`,
`pipeline.py:69-79` (`_ametist_post_fetcher`), `.env.example`,
новый `docs/SECURITY-TELEGRAM.md`, `docs/LIMITATIONS.md` (пункт 6).

работ по приёму меняется у направления «Telegram» (`TG-*`). Аудит и документ (пункты 1, 2, 4)

**Критерии готовности.**
- `docs/SECURITY-TELEGRAM.md` существует и отвечает на четыре вопроса: чей аккаунт,

### SEC-12. Хранение токенов по ссылке на секрет

**Что нужно сделать.** Ввести правило: в базе и в настройках контрагента лежит **ссылка**
на секрет, а не его значение. Сегодня токены живут только в окружении процесса
(`TELEGRAM_BOT_TOKEN` читается один раз в `navigator_api.py:771`), но в макете уже есть поле
«Токен BotFather» в карточке контрагента, и как только появится хранилище настроек, значение
неизбежно попадёт в базу и в выгрузки.

**Как должна работать логика.**

1. Новый модуль `registry/secrets_store.py`:
   - формат ссылки — `env:ИМЯ_ПЕРЕМЕННОЙ` (вариант 1 вопроса C4 на старте);
     парсер устроен так, чтобы позже добавились схемы `file:` и `vault:` без изменения
     вызывающего кода;
   - `resolve(ref) -> str` возвращает значение или бросает `SecretNotFound` с текстом,
     содержащим **ссылку, а не значение**;
   - `mask(value) -> str` — `«…последние 4 символа»`; для значений короче 8 символов —
     `«***»` целиком;
   - `is_ref(value) -> bool` — проверка, что перед нами ссылка, а не сырой секрет.
2. В любой таблице настроек (её заводит направление «Данные») колонка называется
   `*_ref` и хранит только ссылку. Валидация на записи: если значение не проходит
   `is_ref`, запись отклоняется с ошибкой «Сюда кладётся ссылка на секрет
   (например, `env:TELEGRAM_BOT_TOKEN_AAAPLUS`), а не сам токен».
3. Соглашение об именах переменных: `TELEGRAM_BOT_TOKEN_<ALIAS_ИСТОЧНИКА_ЗАГЛАВНЫМИ>` —
   совпадает с уже действующим соглашением `TELEGRAM_{ALIAS}_CHAT_ID` (`pipeline.py:260`).
   Все имена перечисляются в `.env.example` секцией B, без значений.
4. API и интерфейс никогда не отдают значение: в ответе — `{"tokenRef": "env:...",
   "tokenMask": "…4821", "tokenPresent": true}`. Поле ввода в карточке контрагента
   принимает ссылку, а не токен.
5. Каждое обращение `resolve` пишет в лог INFO строку с именем ссылки и потребителем
   («кто и зачем»), без значения. Это даёт минимальный аудит использования секретов.
6. Отсутствующий секрет — не 500 посреди прогона: `resolve` вызывается на старте
   соответствующей операции, и при `SecretNotFound` операция отменяется с понятной ошибкой
   «Для контрагента X не настроен секрет env:Y».

**Экраны и компоненты.** Новый `registry/secrets_store.py`, `.env.example` (секция имён),
`navigator_api.py` (поле токена в карточке контрагента — сейчас пустая строка,
`navigator_api.py:579-588`), `templates/navigator.html` (модалка «Настройки контрагента»
`:1855-1900`), `tests/test_secrets_store.py`.

**Зависимости.** Блокируется вопросом **C4** «Где хранятся токены ботов и ключи» —
от него зависит набор поддерживаемых схем ссылки (по умолчанию принят вариант 1:
переменные окружения по соглашению об именах). Также зависит от вопроса **B1**
и от задачи направления «Данные» (`DB-*`), заводящей таблицы `counterparties`
и `counterparty_settings`: до них колонку `*_ref` некуда положить, и делается только модуль
с разрешением ссылок и правилами именования.

**Критерии готовности.**
- `resolve("env:TELEGRAM_BOT_TOKEN")` возвращает значение переменной;
  `resolve("env:НЕТ_ТАКОЙ")` бросает `SecretNotFound`, и в тексте исключения нет значений
  других переменных.
- `resolve("12345678:AAbbcc")` (сырой токен вместо ссылки) бросает ошибку формата.
- `mask("12345678:AAbbccddeeff")` возвращает строку, оканчивающуюся на 4 символа исходного
  значения и не содержащую остального.
- В `.env.example` перечислены имена по соглашению `TELEGRAM_BOT_TOKEN_<ALIAS>` без значений.
- Ни один ответ API не содержит значения токена — проверяется тестом, который ищет
  подстроку тестового секрета во всём JSON.
- Каждое обращение `resolve` даёт ровно одну строку INFO с именем ссылки и без значения.

**Приоритет.** P2.

**Риски.** Соглашение об именах ломается при переименовании источника: ключи `kpk`,
`yappi`, `vahtapro` намеренно неизменны (`pipeline.py:112-115`), это же правило
распространяется на имена переменных с секретами — зафиксировать явно. Если позже
выбирается внешний vault, миграция ссылок потребует правки данных, но не кода — ради этого
и вводится схема.

### SEC-13. Секретный путь и проверка заголовка вебхука

**Что нужно сделать.** Заранее зафиксировать контракт безопасности для приёма ответов
контрагентов через Telegram: роут `POST /webhook/telegram/...` в приложении отсутствует,
исходящих сообщений и очереди запросов нет. Задача описывает и реализует **только защиту**
эндпоинта; сама обработка обновлений — за направлением «Telegram» (`TG-*`).

**Как должна работать логика.**

1. Роут: `POST /webhook/telegram/{path}`. Значение `path` берётся из окружения
   `TELEGRAM_WEBHOOK_PATH`, генерируется как `secrets.token_urlsafe(32)`. Несовпадение
   пути → `404` с пустым телом (не `401` и не `403`: существование эндпоинта не
   подтверждается).
2. Заголовок: при вызове `setWebhook` у Telegram задаётся `secret_token`, значение —
   `TELEGRAM_WEBHOOK_SECRET` (тоже `token_urlsafe(32)`). На каждый запрос приложение
   сравнивает `X-Telegram-Bot-Api-Secret-Token` с этим значением через
   `secrets.compare_digest`. Несовпадение или отсутствие → `404`, тело пустое.
   Именно заголовок является настоящей проверкой; секретный путь — вспомогательная мера,
   потому что путь попадает в журнал доступа uvicorn и обратного прокси.
3. Роут исключён из HTTP Basic и из cookie-авторизации (Telegram не умеет ни того, ни
   другого) и из CSRF-проверки (SEC-09), но **включён** в ограничение частоты:
   не более 30 запросов в секунду, дальше `429`.
4. Ограничение тела: не более 1 МБ, иначе `413` без разбора содержимого.
5. Логирование: пишется только `update_id`, тип обновления и идентификатор чата.
   Текст сообщения в журнал не пишется — это переписка с контрагентом.
   Значения `TELEGRAM_WEBHOOK_PATH` и `TELEGRAM_WEBHOOK_SECRET` добавляются в список
   маскируемых (SEC-10).
6. Идемпотентность: `update_id` запоминается (таблица заводится вместе с обработкой
   в `TG-*`), повторная доставка того же обновления не обрабатывается дважды.
   Ответ всегда `200` и быстро — разбор уходит в фон, иначе Telegram будет ретраить.
7. Развёртывание: `setWebhook` выполняется скриптом `scripts/set_webhook.py`, который
   читает базовый URL из `PUBLIC_BASE_URL`, путь и секрет из окружения, и печатает
   результат без секретов. Обязательное требование — `https` в `PUBLIC_BASE_URL`;
   Telegram по `http` вебхуки не принимает, и без TLS секретный заголовок уходит открытым.
8. Пока обработка не реализована, роут может отдавать `200` и ничего не делать —
   но проверки пунктов 1-5 должны быть на месте до первого включения вебхука.

**Экраны и компоненты.** `app.py` (новый роут и исключения в middleware),
`security_middleware.py` (исключение CSRF, собственный лимит), новый
`scripts/set_webhook.py`, `.env.example` (`TELEGRAM_WEBHOOK_PATH`,
`TELEGRAM_WEBHOOK_SECRET`, `PUBLIC_BASE_URL`), `tests/test_webhook_auth.py`.

**Зависимости.** SEC-09 (middleware, из которого нужно исключение), SEC-10 (маскирование),
SEC-12 (токен бота по ссылке на секрет). Приём и обработка обновлений — задача направления
«Telegram» (`TG-*`), с ней задачу нужно выкатывать совместно.
Блокируется вопросом **C3** «Согласие контрагентов на автоматические сообщения»:
при варианте 3 (черновик, отправляет человек) вебхук на первом этапе не нужен вовсе,
и задачу можно отложить. Также TLS: без него включать вебхук нельзя, это внешнее условие
к развёртыванию.

**Критерии готовности.**
- `POST /webhook/telegram/<неверный-путь>` → `404`, тело пустое.
- `POST /webhook/telegram/<верный-путь>` без заголовка `X-Telegram-Bot-Api-Secret-Token`
  → `404`.
- Тот же запрос с неверным значением заголовка → `404`; с верным → `200`.
- Запрос с телом 2 МБ → `413`, тело не разбиралось (в логе нет `update_id`).
- 31-й запрос за секунду → `429`.
- В журнале по одному обновлению есть строка с `update_id` и нет текста сообщения.
- `python scripts/set_webhook.py` при `PUBLIC_BASE_URL`, начинающемся с `http://`,
  завершается ошибкой и ничего не вызывает.
- Значения пути и секрета не встречаются в `logs/eltera.log`.

**Приоритет.** P2.

**Риски.** Секретный путь виден в журнале доступа обратного прокси и в его метриках —
он не заменяет проверку заголовка, и полагаться на него нельзя. Ответ `404` вместо `403`
затрудняет отладку: при настройке вебхука легко перепутать секрет и получить молчаливое
`404` — предусмотреть строку в логе уровня WARNING «отказ вебхука: неверный секрет»
без самих значений.

### SEC-14. Ротация ключей и вывод общей Basic-пары из обращения

**Что нужно сделать.** Провести разовую ротацию всех действующих секретов и завести

`1207` был в исходнике страницы (SEC-03). Считать все эти значения скомпрометированными
