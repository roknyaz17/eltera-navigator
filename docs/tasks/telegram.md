## Telegram

**Как есть сейчас.** Telegram в системе работает ровно в одну сторону — на чтение.
`telegram_userbot.py` — тонкая обёртка над Telethon: подключение по `StringSession`
из переменной `TELEGRAM_SESSION` (`telegram_userbot.py:25-32`), метод
`get_messages(chat_id, limit, min_id, after)` (`telegram_userbot.py:64-95`), который
идёт `iter_messages` от новых к старым и обрывает обход на первом сообщении старше
`after`. Ни одного `try/except`, ни одного ретрая, ни обработки `FloodWaitError`
в файле нет: любая сетевая ошибка или лимит Telegram роняет весь прогон источника
(`pipeline._read_telegram`, `pipeline.py:137-165` — оба канала читаются внутри одного
`async with TelegramUserbot()`).

Окно чтения — не курсор, а время: `_since_today_msk()` (`pipeline.py:91-99`) даёт
«сегодня 07:00 МСК» (`TG_SINCE_HOUR_MSK = 7`, `pipeline.py:84`), верхний предел —
`TG_LIMIT = 20` сообщений (`pipeline.py:82`). Каждый прогон перечитывает одно и то же
окно заново; сообщения, вышедшие за 20 штук или за границу окна, не читаются никогда.

Сообщение без текста отбрасывается прямо в `get_messages`: `text = (msg.message or "").strip()`,
`if not text: continue` (`telegram_userbot.py:85-87`) — **без единой строки лога**.
Фото, документ, xlsx, pdf исчезают молча. Альбомы (несколько сообщений с общим
`grouped_id`) не склеиваются: подпись лежит на одном сообщении группы, остальные
теряются. Склейка альбома реализована только в `telegram_post_fetcher.py`
(`ALBUM_SPAN = 9`) и только для подтягивания описаний Аметиста по ссылке из таблицы.

Дальше сообщения превращаются в заявки в `TelegramChannelProcessor.collect_requests`
(`telegram_channel_processor.py:96-175`): одно сообщение = одна заявка,
`source_ref = f"msg:{msg_id}"`, нарезка по эмодзи уходит в `parse_chunks`,
снимок дня опознаётся по `snapshot_marker`. Каналов два: Градус
(`TELEGRAM_VAHTAPRO_CHAT_ID`, `vahtapro_message_processor.py`) и AAA+
(`TELEGRAM_AAAPLUS_CHAT_ID`, `aaaplus_message_processor.py`). Аметист с Telegram-чата
переведён на таблицу; `ametist_message_processor.py` в коде не используется.

**Исходящей половины нет вообще.** Нет модуля поверх Bot API, нет вебхука, нет очереди,
нет таблиц. `TELEGRAM_BOT_TOKEN` читается ровно один раз — `bool(os.getenv("TELEGRAM_BOT_TOKEN","").strip())`
в `navigator_api.py:771`, чтобы отдать во фронт флаг `outreachEnabled` и показать кнопку.
Текст запроса контрагенту целиком собирается **в браузере**: `computeOutreach()`
(`templates/navigator.html:738-781`), `outreachText()` (`:704-734`), словарь вопросов
`FIELD_ASK` (`:660-668`), приветствие `GREETING = 'Добрый день!'` (`:652`), проверка
длины против `TG_LIMIT = 4096` (`:104`). Константы `SEND_TIME = '09:00'` и `MAX_TRIES = 3`
(`:101-102`) — просто подписи на экране. Кнопки «Отправить», «Отправить сейчас»,
«Отправить тестовое», «Проверить подключение» (`cpTest`, `cpTestMsg`, `cpCheck`,
`sendNow`, `outSend` — `:2027-2105`) показывают тост и не делают ничего.
В карточке контрагента `contact/bot/token/chat/thread/sendTime` — пустые строки,
`delivery = "отправка запросов не настроена"`, `deliveryOk = False`
(`navigator_api.py:579-588`): хранилища настроек контрагента в системе нет.

Обязательные поля, по которым считаются пробелы и строится запрос, — `REQUIRED_FIELDS`
в `navigator_api.py:33-40` (`cits`, `house`, `meals`, `rate`, `sched`, `need`).
Первая строка запроса — `DEFAULT_TEMPLATE` (`navigator_api.py:44-47`).

**База.** SQLite, `MIGRATIONS` в `registry/db.py` содержит шесть элементов, 11 таблиц
плюс FTS5 `search_index`. Таблиц `counterparties`, `counterparty_settings`,
`outreach_threads`, `outreach_messages`, `outreach_questions` нет. Схема накатывается
автоматически при первом обращении к базе; DDL позиции в миграции v1 собирается из
списков `registry/models.py`, поэтому любое новое поле требует **новой** миграции
с `ALTER TABLE`.

**Авторизация.** Одна общая пара HTTP Basic (`WEB_USER`/`WEB_PASSWORD`,
`app.py:191-207`), ролей нет. Без авторизации открыты `/health`, `/metrics`, `/jobs`,
`/static`, `/docs`, `/openapi.json`.

**Планировщик.** APScheduler внутри процесса приложения, `JOBS` в `app.py:84-109`
(четыре задачи, `timezone="Europe/Moscow"`), расписание продублировано в
`navigator_api.SOURCE_SCHEDULE` (`:51-59`) и в `next_run` (`:703-710`).

### TG-01. Устойчивость чтения Telegram: ретраи, таймауты, FloodWaitError

**Что нужно сделать.** Обернуть все сетевые вызовы Telethon в `telegram_userbot.py`
(`__aenter__`, `whoami`, `get_messages`) и вызов `_read_telegram` в `pipeline.py:137-165`
в явную обработку ошибок с ограниченным числом повторов. Добавить в `telegram_userbot.py`
внутренний хелпер `_with_retry(coro_factory, *, what: str)`, через который проходят
`connect`, `is_user_authorized`, `get_entity` и итерация `iter_messages`. Ввести
собственные типы исключений модуля: `TelegramTemporaryError` (можно повторить) и
`TelegramFatalError` (повтор бессмысленен — сессия недействительна, канала нет,
нет доступа), чтобы `pipeline` мог различать «источник пропустили» и «источник сломан».

**Как должна работать логика.**
1. `FloodWaitError` (`telethon.errors.FloodWaitError`): читаем `exc.seconds`. Если
   `seconds <= TG_FLOOD_WAIT_MAX` (новая константа, значение по умолчанию 300) —
   ждём `seconds + 2` и повторяем тот же вызов, в лог `warning` с именем канала
   и числом секунд. Если больше — повтор не делаем, поднимаем `TelegramTemporaryError`,
   источник помечается пропущенным.
2. Сетевые и серверные ошибки (`ConnectionError`, `asyncio.TimeoutError`,
   `telethon.errors.RPCError` с кодом 5xx, `ServerError`, `TimedOutError`) —
   до трёх попыток, пауза 2, 8, 20 секунд.
3. `AuthKeyError`, `SessionRevokedError`, `UserDeactivatedError`, неуспех
   `is_user_authorized()` — `TelegramFatalError` сразу, без повторов; текст ошибки
   обязан содержать инструкцию «перевыпустить строку через `auth_userbot.py`»
   и **не должен** содержать саму строку сессии.
4. `ChannelPrivateError`, `ChatIdInvalidError`, `ValueError` из `get_entity` —
   `TelegramFatalError` с именем переменной окружения, из которой взят `chat_id`.
5. Общий бюджет на чтение одного канала — `TG_READ_TIMEOUT` (по умолчанию 120 секунд)
   через `asyncio.wait_for`. Истёк — `TelegramTemporaryError`.
6. В `_read_telegram` каждый канал читается в собственном `try/except`: падение
   Градуса не отменяет чтение AAA+. Упавший канал даёт `out[alias] = None`,
   и в `_collect_requests` он не превращается в пустую пачку — иначе снимок дня
   с `reset=True` погасил бы все позиции источника (`pipeline.py:270`).
7. Каждая попытка и каждый отказ пишутся в лог с префиксом `[tg-read]` и алиасом
   источника; итог прогона по каналу — одна строка `прочитано N сообщений за M попыток`.

**Экраны и компоненты.** `telegram_userbot.py`, `pipeline.py` (`_read_telegram`,
`_collect_requests`), `metrics.py` — новые счётчики `eltrea_telegram_read_errors_total{source,kind}`
(kind = `flood`/`network`/`fatal`) и `eltrea_telegram_flood_wait_seconds{source}`.
Тесты: новый `tests/test_telegram_read.py` с подставным клиентом (по образцу
`FakeFetcher` из `tests/test_ametist_telegram.py`), сеть не нужна.

**Зависимости.** Нет. Задача не заблокирована ни одним вопросом из `docs/OPEN-QUESTIONS.md`
и может быть начата немедленно.

**Критерии готовности.**
- В `telegram_userbot.py` нет ни одного сетевого вызова вне обработчика ошибок.
- Тест: клиент бросает `FloodWaitError(seconds=3)` один раз — чтение завершается
  успешно, вызовов клиента два, в логе одна строка `warning`.
- Тест: `FloodWaitError(seconds=3600)` — исключение `TelegramTemporaryError`,
  повторных вызовов нет.
- Тест: три подряд `ConnectionError` — три попытки, затем `TelegramTemporaryError`.
- Тест: `_read_telegram` при падении первого канала возвращает `None` для него
  и список сообщений для второго.
- Тест: `out[alias] is None` не порождает вызова `_deactivate_stale` даже при `reset=True`.
- Текст любого исключения модуля не содержит подстроку значения `TELEGRAM_SESSION`
  (проверяется тестом на подставленной строке-маркере).
- Метрики `eltrea_telegram_read_errors_total` присутствуют в выдаче `/metrics`.

**Приоритет.** P0.

**Риски.** Слишком агрессивные ретраи усиливают флуд-лимит и приводят к более
длинному бану аккаунта — поэтому повтор после `FloodWaitError` строго один,
на указанное Telegram время. Ошибочная классификация временной ошибки как фатальной
заставит источник молчать до ручного вмешательства; ошибочная классификация фатальной
как временной растянет прогон на минуты. Пропуск канала вместо падения делает сбой
менее заметным — компенсируется метрикой и строкой в логе.

### TG-02. Логирование отброшенных сообщений и статистика приёма

**Что нужно сделать.** Убрать молчаливую потерю данных на входе. Сейчас
`telegram_userbot.get_messages` отбрасывает сообщение без текста строками
`text = (msg.message or "").strip()` / `if not text: continue`
(`telegram_userbot.py:85-87`) — ни лога, ни счётчика. Нужно, чтобы каждое
отброшенное сообщение оставляло след с типом вложения, и чтобы по итогам прогона
было видно, сколько заявок мы теряем и какого вида.

**Как должна работать логика.**
1. В `get_messages` вместо `continue` собирать признак сообщения:
   `kind` = `photo` | `document` | `video` | `voice` | `poll` | `service` | `empty`
   (определяется по `msg.media`, `msg.action`, типу документа через `msg.document.mime_type`),
   `has_caption` (есть ли непустой `msg.message` — тогда сообщение не отбрасывается),
   `grouped_id`, `id`, `date`, имя файла для документа.
2. Каждое отброшенное сообщение — одна строка `warning` вида
   `[tg-skip] {канал} #{msg_id} {kind} grouped_id={...} file={...}` без содержимого
   вложения. Скачивание файлов на этом этапе не делается.
3. Возвращать статистику: `get_messages` отдаёт не только список сообщений, но и
   счётчик `skipped_by_kind: Dict[str, int]`. Сигнатура меняется — обновить
   вызовы в `pipeline._read_telegram` (`pipeline.py:158-163`) и `run_vahtapro.py`,
   `run_aaaplus.py`.
4. В конце чтения канала — одна итоговая строка: `прочитано N, отброшено M
   (photo=…, document=…, service=…)`. Если `M > 0` и `N == 0`, уровень строки —
   `error`: это ситуация «весь канал прислал вложения, мы не приняли ничего».
5. Метрика `eltrea_telegram_skipped_messages_total{source,kind}` — по ней через месяц
   принимается решение по вопросу D6.
6. Служебные сообщения, которые уже отсеиваются позже по сигналам
   (`_has_vacancy_signals`, лог `[{source_name} #{id}] service:` —
   `telegram_channel_processor.py:121-124`), в этот счётчик не попадают: там
   сообщение с текстом, оно принято и осознанно отклонено. Разделение обязано быть
   видно в логе разными префиксами.

**Экраны и компоненты.** `telegram_userbot.py`, `pipeline.py`, `run_vahtapro.py`,
`run_aaaplus.py`, `metrics.py`, `tests/test_telegram_read.py`.

**Зависимости.** Нет. Это ровно та половина вопроса **D6** из
`docs/OPEN-QUESTIONS.md`, которую разрешено делать до ответа: вариант по умолчанию —
«только текст плюс обязательное логирование, чтобы понять масштаб». Приём вложений —
отдельная задача TG-13, она ответом D6 заблокирована.

**Критерии готовности.**
- Тест: сообщение с `media` и пустым `message` не попадает в результат, но порождает
  ровно одну строку лога с `kind` и `msg_id`.
- Тест: сообщение с `media` и непустой подписью попадает в результат (подпись — текст заявки).
- Тест: `get_messages` возвращает `skipped_by_kind` с верными числами по трём видам.
- Метрика `eltrea_telegram_skipped_messages_total` растёт на реальном прогоне и видна в `/metrics`.
- В логе прогона есть итоговая строка с числом отброшенных по каждому виду.
- Ни одна строка лога не содержит скачанного содержимого вложения.

**Приоритет.** P0.

**Риски.** Если контрагенты действительно шлют потребность картинками, объём
предупреждений в логе окажется большим и его примут за шум — итоговая строка и
метрика важнее построчных сообщений. Изменение сигнатуры `get_messages` затрагивает
три вызывающих места; пропущенный вызов даст `ValueError: too many values to unpack`
на прогоне, а не при импорте.

### TG-03. Модуль исходящих сообщений поверх Telegram Bot API

**Что нужно сделать.** Завести новый модуль `telegram_bot.py` — единственную точку
исходящих обращений к Telegram. Класс `TelegramBot(token: str, *, timeout: float = 20.0)`
с методами `get_me()`, `get_chat(chat_id)`, `get_chat_member(chat_id, user_id)`,
`send_message(chat_id, text, *, message_thread_id=None, disable_web_page_preview=True,
reply_to_message_id=None)`, `set_webhook(url, secret_token)`, `delete_webhook()`.
Транспорт — `httpx.AsyncClient` на `https://api.telegram.org/bot{token}/{method}`.
Никакой другой модуль в проект не ходит в Telegram на отправку напрямую.

**Почему отдельный бот, а не userbot, которым мы читаем каналы.** Это решение,
а не вкусовщина, и его нужно держать в голове во всех задачах TG-04…TG-11:

1. `TELEGRAM_SESSION` — это полноценный доступ к живому личному аккаунту сотрудника
   (`telegram_userbot.py:25-32`, `docs/LIMITATIONS.md`, раздел 6), а не сервисный токен.
   Автоматические сообщения от его имени юридически и организационно означают, что
   пишет человек, а не система.
2. Массовая автоматическая рассылка с пользовательского аккаунта — прямой путь к
   ограничениям и блокировке аккаунта Telegram. Этим же аккаунтом мы **читаем** оба
   канала-источника: блокировка отправки убьёт и приём заявок. Отдельный бот
   изолирует риск — сломается рассылка, реестр продолжит наполняться.
3. Bot API даёт то, чего у userbot нет: коды ошибок доставки (403 «bot was blocked
   by the user» / «bot is not a member», 400 «chat not found», 429 `retry_after`),
   вебхук с `update_id` для идемпотентного приёма ответов и `secret_token` для
   проверки подлинности запроса. У Telethon пришлось бы держать постоянное
   подключение личного аккаунта и разбирать всю личную переписку владельца.
4. Токен бота выдаётся и отзывается за минуту и может быть свой на контрагента;
   строка сессии отзывается только вместе с доступом к аккаунту человека.
5. Бот добавляется в чат самим контрагентом — это фиксируемое согласие на переписку
   с роботом (вопрос **C3**), и при включённом privacy mode бот видит только
   адресованные ему сообщения, а не всю переписку чата.
6. Тема форума (`message_thread_id`) поддерживается Bot API штатно — запросы уходят
   в ту ветку, о которой договорились, а не общим потоком в чат.

**Как должна работать логика.**
1. Токен берётся из настроек контрагента, а при их отсутствии — из переменной
   окружения по соглашению об именах: `TELEGRAM_BOT_TOKEN_{ALIAS}` (алиас источника
   в верхнем регистре), общий `TELEGRAM_BOT_TOKEN` — резервный. Функция
   `resolve_token(source_alias) -> str | None` живёт в `telegram_bot.py`.
2. Ответ Telegram разбирается всегда: `{"ok": true, "result": …}` → результат;
   `{"ok": false, "error_code": N, "description": "…"}` → исключение
   `TelegramSendError(error_code, description, retry_after)`.
3. Классификация ошибок (используется в TG-11): 429 → временная, `retry_after`
   из `parameters.retry_after`; 5xx и сетевые — временная; 403, 400 — постоянная;
   401 (`Unauthorized`) — постоянная с пометкой «токен недействителен».
4. Ограничитель частоты: не более одного сообщения в секунду на чат и не более
   20 сообщений в минуту суммарно — простой асинхронный семафор плюс таймстемпы
   на чат внутри модуля. Это ограничение самого Telegram, и нарушать его нельзя.
5. Длина сообщения: константа `TG_MESSAGE_LIMIT = 4096`. Метод `send_message`
   **не режет** текст молча — при превышении бросает `TelegramTextTooLong`;
   разбивку на части делает вызывающий код (TG-05), потому что резать нужно
   по границам позиций, а не по символам.
6. Токен никогда не попадает в лог и в текст исключения: в логах — только
   `bot=@username` из `get_me()` и первые 6 символов токена не пишутся вообще.
7. Модуль не знает ни про реестр, ни про пробелы: на вход текст и адрес, на выход
   `message_id` или исключение.

**Экраны и компоненты.** Новый `telegram_bot.py`; `requirements.txt` (`httpx`, если его
ещё нет); `.env.example` — секция переменных бота; `metrics.py` —
`eltrea_telegram_send_total{source,status}`, `eltrea_telegram_send_errors_total{source,code}`.
Новый тест `tests/test_telegram_bot.py` с подставным HTTP-транспортом (`httpx.MockTransport`),
без сети.

**Зависимости.** Нет технической блокировки. Организационно связан с вопросом **C4**
(где хранятся токены ботов): вариант по умолчанию — переменные окружения по
соглашению об именах, именно он и реализуется; если ответ будет иным, меняется
только `resolve_token`.

**Критерии готовности.**
- `TelegramBot.send_message` возвращает `message_id` при `ok: true`.
- Тест: ответ `{"ok": false, "error_code": 429, "parameters": {"retry_after": 7}}`
  даёт `TelegramSendError` с `retry_after == 7` и признаком «временная».
- Тест: `error_code` 403 и 400 дают признак «постоянная».
- Тест: текст длиной 4097 символов даёт `TelegramTextTooLong` и HTTP-запрос не выполняется.
- Тест: при `message_thread_id` параметр уходит в тело запроса; при `None` — отсутствует.
- Тест: строка токена не встречается ни в одном сообщении лога и ни в одном тексте исключения.

### TG-05. registry/outreach.py: сбор пробелов, группировка и текст запроса на сервере

**Что нужно сделать.** Перенести формирование запроса контрагенту с клиента на сервер.
Сейчас это `computeOutreach()` и `outreachText()` в `templates/navigator.html:704-781`:
текст существует только в открытой вкладке браузера, его нельзя ни отправить,

`collect_gaps(conn, source) -> List[GapItem]`, `group_items(items) -> List[PlaceGroup]`,
`render_message(groups, *, greet: bool, template: str) -> List[str]`
и `build_drafts(conn) -> List[Draft]`.

**Как должна работать логика.**
1. **Сбор пробелов.** По активным позициям (`positions.is_active = 1`) считается тот же
   набор, что и в подборе: `REQUIRED_FIELDS` из `navigator_api.py:33-40` —
   `cits`, `house`, `meals`, `rate`, `sched`, `need`. Пустым считается то же, что
   считает `navigator_api.position_row` (`na`/`None`/пустая строка). Если у позиции

2. **Адресат.** Запрос уходит контрагенту-источнику (`positions.source` →

3. **Группировка.** Внутри сообщения — по месту: `город, район` (иначе регион, иначе

4. **Подпись позиции.** `название у контрагента (или профессия) · ставка/смена ·
   график (обрезка до 44 символов по границе слова) · тип смены`, если он не
   «дневная и ночная». Внутренний `ELT-…` в текст не выводится — контрагент такого
   номера не знает.
5. **Слияние одинаковых строк.** Совпавшие «подпись + набор полей» склеиваются:
   спрашивать дважды в одном сообщении незачем.
6. **Шаблон.** Первая строка — `template` из настроек треда, по умолчанию

7. **Приветствие раз в день.** `GREETING = 'Добрый день!'` добавляется в начало

   последующие сообщения того же дня идут без приветствия.
8. **Правило «не переспрашивать».** Перед сборкой читается `outreach_questions`.
   Поле, по которому уже есть строка с `answered_at IS NULL` и `asked_at` не старше

10. **Длина.** Проверка против `TG_MESSAGE_LIMIT = 4096` (TG-03). Не влезает —

11. Каждое сформированное сообщение сохраняется как черновик в `outreach_messages`

### TG-06. Режим «черновик»: система формирует, человек отправляет

**Что нужно сделать.** Реализовать первый этап работы робота — режим `draft`,
в котором система строит сообщение и держит его в очереди, а отправляет человек
кнопкой. Это значение `outreach_threads.mode` по умолчанию (TG-04) и способ
включить робота, не рассылая ничего без ведома людей. Роуты в `app.py`:
`GET /api/outreach` (очередь черновиков), `POST /api/outreach/{message_id}/send`,
`POST /api/outreach/{message_id}/skip`, `POST /api/outreach/refresh` (пересобрать
черновики немедленно).

**Как должна работать логика.**
1. Фоновая задача `outreach_drafts` в `JOBS` (`app.py:84-109`) раз в сутки после
   последнего прогона источников (13:45 МСК) вызывает `outreach.build_drafts(conn)`
   и складывает черновики со статусом `draft`. Повторный вызов в тот же день
   **перезаписывает** незаотправленные черновики того же треда, а не плодит новые.
2. `GET /api/outreach` отдаёт список: тред, контрагент, чат, число позиций, текст
   всех частей, длина каждой части, `attempt`, `silent`, `deliveryOk`, дата
   последнего ответа. Черновик, отправленный или пропущенный, в списке не появляется.
3. `POST /api/outreach/{message_id}/send`: проверяет, что сообщение в статусе `draft`
   и что тред не `off`; отправляет части **по порядку** через `TelegramBot.send_message`
   (TG-03); после каждой успешной части пишет `tg_message_id`, `sent_at`,
   `sent_by = user` (логин из `verify_creds`, `app.py:191-207`); после последней —
   создаёт строки в `outreach_questions`, увеличивает `attempt`, ставит `greeted_on`.
   Ошибка на части N: части 1..N-1 остаются отправленными, сообщение переходит
   в `failed` с текстом ошибки, повторная отправка начинает с части N (номера частей
   хранятся в `outreach_messages.items`).
4. `POST /api/outreach/{message_id}/skip`: статус `skipped`, вопросы не создаются,
   `attempt` не растёт. Пропуск — не отказ от позиции, назавтра черновик соберётся снова.
5. Переключение режима треда `draft` → `auto` — отдельное действие в настройках
   контрагента, доступное только когда по треду есть хотя бы одна успешная отправка
   и хотя бы один входящий ответ. Робот не переводится в автомат на чате, который
   ни разу не сработал.
6. Ответ всех роутов — JSON; тела запросов описаны Pydantic-моделями (в проекте их
   пока нет ни у одного роута: `POST /api/rates` принимает сырой `dict`,
   `app.py:400-438`).
7. Идемпотентность: повторный `POST .../send` для уже отправленного сообщения
   возвращает 409 и не шлёт ничего.

**Экраны и компоненты.** `app.py` (новые роуты, новая задача в `JOBS`),
`registry/outreach.py`, `registry/outreach_store.py`, `telegram_bot.py`,
`templates/navigator.html` — вкладка «Запросы» админ-экрана (`viewOutreach`,
`:1327-1348`), кнопки `outSend`/`sendNow` (`:2027-2029`, `:2099`) перестают быть
тостами. Правка шаблона — направление «Фронтенд».

**Зависимости.** TG-03, TG-04, TG-05. Вопрос **C3** из `docs/OPEN-QUESTIONS.md`
(согласие контрагентов на автоматические сообщения): вариант по умолчанию —
«сначала режим черновик» — это и есть данная задача, поэтому она **не заблокирована**;
заблокирован переход в `auto` (TG-08). Авторство действия опирается на общий Basic —
персональные учётные записи делает направление «Безопасность» (`SEC-*`, вопрос **C1**);
до них в `sent_by` пишется значение `WEB_USER`.

**Критерии готовности.**
- `GET /api/outreach` возвращает черновики только в статусе `draft`.
- Тест: `POST .../send` при успешной отправке переводит сообщение в `sent`,
  создаёт строки `outreach_questions` по всем спрошенным полям, увеличивает `attempt` на 1.
- Тест: повторный `POST .../send` даёт 409 и не вызывает Telegram.

- Тест: `skip` не создаёт вопросов и не меняет `attempt`.

- Тела всех новых роутов валидируются Pydantic-моделями; нечисловое/лишнее поле

- Ни один новый роут не доступен без HTTP Basic.

**Риски.** Кнопка «Отправить» — необратимое действие: сообщение уже у контрагента,
отозвать его нельзя. Отсюда требование показывать полный текст всех частей до

затереть текст, который человек читал в этот момент, — в ответе API отдавать
`updated_at`, чтобы фронт мог предупредить.

### TG-07. «Проверить подключение» и «Отправить тестовое сообщение»

### TG-08. Фоновая рассылка по расписанию с учётом часового пояса контрагента

**Что нужно сделать.** Включить автоматическую отправку для тредов в режиме `auto`:
фоновая задача, которая раз в 10 минут проверяет, кому пора писать, и отправляет
готовые черновики. Задача `outreach_send` добавляется в `JOBS` (`app.py:84-109`)
`CronTrigger(minute="*/10", timezone="Europe/Moscow")`.

**Как должна работать логика.**
1. Отбор: треды с `mode = 'auto'`, `delivery_ok = 1`, `attempt < max_attempts`,
   у которых есть черновик в статусе `draft`.
2. Время: `send_time` и `timezone` берутся из треда (по умолчанию `09:00`,
   `Europe/Moscow`). Сообщение уходит, если локальное время контрагента
   в интервале `[send_time, send_time + 2 часа]` и сегодня по этому треду ещё
   не отправляли. Пропущенное окно (сервер лежал) не догоняется на следующий день
   двойной отправкой — просто уходит в следующее окно.
3. Запрет ночной отправки: за пределами `09:00-20:00` локального времени
   не отправляется ничего, даже вручную поставленным `send_time`. Проверка
   выполняется в момент отправки, а не в момент постановки в очередь.
4. Выходные: флаг `skip_weekends` в треде (по умолчанию включён). В субботу и
   воскресенье автоматическая отправка не идёт; черновик копится, в понедельник
   уходит один, а не три.
5. Догоняющее сообщение: если по треду есть неотвеченные вопросы старше
   `OUTREACH_FOLLOWUP_DAYS` (по умолчанию 2) и `attempt < max_attempts`,
   формируется короткое напоминание со списком уже заданных вопросов
   (тех самых, что правило «не переспрашивать» держит вне основного сообщения),
   без приветствия, если оно уже было сегодня. Догоняющее увеличивает `attempt`.
6. Исчерпание попыток: `attempt >= max_attempts` — тред помечается `silent`,
   автоматическая отправка прекращается, тред попадает в очередь исключений
   административного экрана с формулировкой «заказчик не отвечает N дней,
   автоповторы исчерпаны» и контактом для звонка.
7. Один процесс: задача выполняется только если приложение — единственный
   экземпляр. Планировщик живёт внутри процесса (`app.py:141-178`), при нескольких
   воркерах uvicorn задача продублируется и контрагент получит два сообщения.
   До появления общего механизма блокировки (направление «Эксплуатация») отправка
   защищается блокировкой в самой базе: `UPDATE outreach_messages SET status='queued'
   WHERE id=? AND status='draft'` и проверка `rowcount` — забрать сообщение может
   только один процесс.
8. Метрики: `eltrea_outreach_sent_total{source}`, `eltrea_outreach_failed_total{source,code}`,
   `eltrea_outreach_threads{state}` (`draft`/`auto`/`silent`/`off`).

**Экраны и компоненты.** `app.py` (`JOBS`, `_job_wrapper`), `registry/outreach.py`,
`registry/outreach_store.py`, `telegram_bot.py`, `metrics.py`,
`navigator_api.counterparties_block` (строка «автоотправка в 09:00 · попытка N из 3»
перестаёт быть подписью-константой из `templates/navigator.html:101-102`).

**Зависимости.** TG-03, TG-04, TG-05, TG-06, TG-11 (обработка недоставки —
без неё автоматика будет молотить в мёртвый чат). **Заблокирована вопросом C3**
из `docs/OPEN-QUESTIONS.md`: пока не получено согласие контрагентов на
автоматические сообщения, ни один тред не переводится в `auto`. Код можно писать
и тестировать, включение в бой — после ответа. Часовой пояс контрагента опирается
на настройки контрагента (`DB-*`, вопрос **B1**); до них — поле в `outreach_threads`.

**Критерии готовности.**
- Тест: тред с `send_time='09:00'`, `timezone='Asia/Yekaterinburg'` отправляется,
  когда в Екатеринбурге 09:05, и не отправляется, когда там 08:55.
- Тест: второй запуск задачи в тот же день по тому же треду ничего не отправляет.
- Тест: локальное время 21:00 — отправки нет ни при каких настройках.
- Тест: суббота при `skip_weekends=1` — отправки нет, черновик сохраняется.
- Тест: два параллельных вызова задачи отправляют сообщение ровно один раз
  (проверяется числом вызовов подставного `TelegramBot`).
- Тест: неотвеченные вопросы старше двух дней порождают догоняющее сообщение
  без приветствия и с теми же формулировками вопросов.
- Тест: на третьей неотвеченной попытке тред переходит в `silent` и попадает
  в список исключений.
- Метрики `eltrea_outreach_*` присутствуют в `/metrics`.

**Приоритет.** P1.

**Риски.** Самая опасная задача направления: ошибка расписания означает ночные
сообщения или несколько сообщений подряд одному контрагенту — это репутационный

### TG-09. Вебхук приёма ответов: секретный заголовок и идемпотентность по update_id

**Что нужно сделать.** Добавить роут `POST /webhook/telegram/{bot_slug}` в `app.py`,
принимающий обновления Telegram, и функцию регистрации вебхука
(`setWebhook` с параметром `secret_token`) в `telegram_bot.py` (TG-03).
Сейчас такого роута нет вовсе (`docs/AS-IS-VS-TO-BE.md`, раздел 1).

**Как должна работать логика.**
1. **Проверка подлинности.** Telegram присылает заголовок
   `X-Telegram-Bot-Api-Secret-Token` со значением, которое мы задали в `setWebhook`.
   Роут сравнивает его с секретом из окружения (`TELEGRAM_WEBHOOK_SECRET`,
   а при нескольких ботах — `TELEGRAM_WEBHOOK_SECRET_{ALIAS}`) через
   `secrets.compare_digest`. Несовпадение или отсутствие заголовка — 403 и строка
   в лог с IP; тело не разбирается.
2. Секрет пустой в окружении — роут отвечает 503 и пишет `error`: работать
   без проверки подлинности нельзя, вебхук открыт наружу по определению.
3. **Роут не закрывается HTTP Basic** — Telegram не умеет Basic. Единственный
   барьер — секретный заголовок, поэтому в `verify_creds` он не добавляется,
   но и в общую схему открытых роутов не попадает: об этом делается явная запись
   в `docs/`. `bot_slug` в пути — не секрет, а способ различить ботов.
4. **Идемпотентность.** Первым делом `INSERT OR IGNORE INTO telegram_updates
   (update_id, bot_username, received_at, payload) VALUES (…)`. Если `rowcount == 0` —
   это повтор (Telegram повторяет доставку, пока не получит 200), отвечаем 200 `{"ok": true}`
   и ничего не делаем. Обработка идёт только для новой строки, по завершении
   `handled = 1`.
5. **Ответ всегда быстрый.** Роут отвечает 200 сразу после записи `telegram_updates`,
   а разбор уходит в `BackgroundTasks`. Ошибка разбора не превращается в 4xx/5xx:
   иначе Telegram будет повторять доставку бесконечно. Ошибка пишется в
   `telegram_updates.handled = -1` и в лог.
6. Принимаются только `message` и `edited_message` из чатов, для которых есть тред
   в `outreach_threads` (по `chat_id` и `message_thread_id`). Обновление из
   незнакомого чата: записывается в `telegram_updates`, помечается `handled = 2`
   («чужой чат») и логируется — по этому логу видно, что бота куда-то добавили.
7. Локальная разработка без публичного адреса: альтернативный режим `getUpdates`
   (long polling) в отдельном скрипте `scripts/telegram_poll.py`, использующий тот же
   обработчик и ту же таблицу идемпотентности. Одновременно с вебхуком не включается —
   Telegram сам вернёт ошибку `setWebhook` конфликтует с `getUpdates`.
8. Размер тела ограничен (например, 1 МБ) — вложения и большие апдейты отбрасываются
   до разбора.

**Экраны и компоненты.** `app.py` (новый роут, исключение из общего правила
авторизации), `telegram_bot.py` (`set_webhook`/`delete_webhook`),
`registry/outreach_store.py` (`telegram_updates`), новый `scripts/telegram_poll.py`,
`.env.example`, новый `tests/test_webhook.py` (через `fastapi.testclient`).

**Зависимости.** TG-03, TG-04. Разбор содержимого ответа — TG-10 (эта задача
доводит апдейт до обработчика и гарантирует «ровно один раз»). Внешнее условие:
публичный HTTPS-адрес приложения и решение, кто его выдаёт (сейчас в compose
наружу торчит только `8000:8000`) — вопрос эксплуатации, к `docs/OPEN-QUESTIONS.md`
не относится, но без него вебхук не регистрируется, и до тех пор используется
`scripts/telegram_poll.py`.

**Критерии готовности.**
- Запрос без заголовка `X-Telegram-Bot-Api-Secret-Token` → 403, тело не разбирается.
- Запрос с неверным секретом → 403; сравнение выполняется `secrets.compare_digest`.
- Пустой секрет в окружении → 503.
- Тест: два одинаковых `update_id` подряд — обработчик вызван один раз, оба ответа 200.
- Тест: исключение внутри обработчика — ответ всё равно 200, строка помечена `handled = -1`.
- Тест: апдейт из чата без треда помечается `handled = 2` и не создаёт записей
  в `outreach_messages`.
- Роут отсутствует в списке защищённых Basic и это зафиксировано в `docs/`.
- `scripts/telegram_poll.py` принимает те же апдейты и пишет в ту же таблицу.

**Приоритет.** P1.

**Риски.** Открытый наружу роут — новая поверхность атаки; единственная защита
секретный заголовок, поэтому его отсутствие обязано означать отказ обслуживания,
а не «пропускаем всех». Отказ отвечать 200 приводит к экспоненциальным повторам
Telegram и лавине записей. Общий секрет на всех ботов означает, что компрометация
одного требует перевыпуска всех.

### TG-10. Разбор ответа контрагента и привязка к заданным вопросам

**Что нужно сделать.** Обработчик входящих сообщений: связать текст ответа с тем,
что мы спрашивали, записать его в `outreach_questions` и показать менеджеру.
Функции `match_reply(conn, thread_id, message) -> List[Match]` и
`store_reply(conn, …)` в `registry/outreach.py`.

**Как должна работать логика.**
1. Входящее сообщение сохраняется в `outreach_messages` с `direction='in'`,
   исходным текстом, `tg_message_id`, `reply_to_message_id`; `outreach_threads.last_reply_at`
   обновляется, `attempt` обнуляется (ответ пришёл — счётчик молчания сброшен).
2. **Определение адресата ответа.** Если у входящего есть `reply_to_message_id`
   и он совпадает с нашим `tg_message_id` — берётся карта `items` именно того
   сообщения. Иначе берётся последнее наше сообщение в треде со статусом `sent`
   не старше 7 дней. Нет ни одного — ответ считается свободным (шаг 5).
3. **Разбор по номерам.** Текст режется на строки и фрагменты по разделителям
   `;` и переводам строки. В каждом фрагменте ищется ведущий номер по шаблону
   `^\s*(\d{1,3})\s*[.)—-]?\s*` — это тот же формат, который мы сами предлагаем
   в подсказке «Ответить удобно номерами: „1 — общежитие…“». Номер сопоставляется
   с `items[].n` → `position_id` и списком спрошенных полей.
4. **Одна позиция в сообщении.** Если в карте `items` ровно один пункт, а в ответе
   номеров нет — весь текст относится к этому пункту.
5. **Свободный ответ.** Номера не распознаны и позиций больше одной — ответ
   сохраняется целиком, привязывается к треду (не к позиции), помечается
   `needs_human = 1` и попадает в очередь исключений административного экрана
   с формулировкой «пришёл ответ, нужно разнести по позициям вручную».
6. **Запись.** Для каждой пары «позиция + поле» из совпавшего пункта в
   `outreach_questions` проставляются `answered_at` и `answer_text` (фрагмент
   ответа целиком, без попытки извлечь значение). Если у пункта спрошено несколько
   полей, а ответ один — он записывается ко всем полям пункта; разбирать, что
   относится к чему, будет человек.
7. **Никакой автоматической записи в позицию.** `positions` этот код не трогает
   ни при каких условиях. Значение переносит менеджер в карточке позиции
   (`/registry/position/{position_id}`, `app.py:850-905`), и только там появляется
   `applied_at`. Это прямое следствие принципа «пустое поле честнее правдоподобной
   выдумки» (`vacancy_parser.py:93-98`).
8. Отвеченные вопросы перестают повторяться правилом «не переспрашивать» (TG-05)
   и исчезают из догоняющих сообщений (TG-08).
9. Ответ, пришедший на тестовое сообщение (`kind='test'`), в вопросы не пишется —
   только в журнал треда.

**Экраны и компоненты.** `registry/outreach.py`, `registry/outreach_store.py`,
`app.py` (обработчик вебхука вызывает `store_reply`), `navigator_api.py` — карточка
позиции получает блок «что спрашивали и что ответили», административный экран —
очередь ответов, требующих разнесения. `templates/registry_position.html` — панель
с ответами контрагента (правка шаблонов реестра — направление «Фронтенд»).
Тесты — `tests/test_outreach.py`.

**Зависимости.** TG-04, TG-05, TG-09. Перенос ответа в поле позиции с записью автора
опирается на персональные учётные записи — направление «Безопасность» (`SEC-*`),
вопрос **C1**; до них автор правки = общий `WEB_USER`. Запись правок менеджера
в `position_history` сейчас отсутствует вовсе — это задача направления «Реестр».

**Критерии готовности.**
- Тест: ответ «1 — общежитие, удержание 250; 3 — нужно 10 человек» при карте из
  трёх пунктов проставляет `answered_at` пунктам 1 и 3 и не трогает пункт 2.
- Тест: ответ без номеров при карте из одного пункта записывается этому пункту.
- Тест: ответ без номеров при карте из трёх пунктов помечается `needs_human = 1`
  и не проставляет `answered_at` никому.
- Тест: `reply_to_message_id`, указывающий на позавчерашнее сообщение, берёт карту
  именно того сообщения, а не последнего.
- Тест: после ответа `positions` не изменилась ни в одном поле.
- Тест: после ответа `outreach_threads.attempt == 0`.
- Тест: отвеченное поле не попадает в следующий черновик и в догоняющее сообщение.
- В карточке позиции виден заданный вопрос, дата, текст ответа и признак «перенесено/не перенесено».

**Приоритет.** P1.

**Риски.** Слишком вольный разбор номеров припишет ответ не той позиции — и данные
разъедутся тише, чем если бы ответа не было вовсе; отсюда запрет на автоматическую
запись в `positions` и обязательный `needs_human` при любой неоднозначности.
Контрагенты редко отвечают по формату — доля свободных ответов может оказаться
подавляющей, и очередь ручного разнесения станет узким местом.

### TG-11. Обработка недоставки и деградация чата

**Что нужно сделать.** Отдельно описать поведение системы, когда сообщение не ушло:
классификация ошибки, повторы, перевод треда в нерабочее состояние и показ этого
человеку. Логика живёт в `registry/outreach.py` (`handle_send_error`) поверх
классификации из `telegram_bot.py` (TG-03).

**Как должна работать логика.**
1. **429 `retry_after`.** Сообщение остаётся в `queued`, время следующей попытки
   `now + retry_after + 2`. Попытка не считается за `attempt` треда: контрагент
   ничего не получил. Не более 5 таких переносов подряд, дальше — как временная ошибка.
2. **5xx и сетевые ошибки.** Повтор через 1, 5, 15 минут (три попытки).
   Исчерпаны — статус `failed`, `attempt` треда не растёт, тред помечается
   `delivery_ok = 0` с текстом ошибки, в очередь исключений уходит запись
   «Telegram недоступен, сообщение не отправлено».
3. **403 (бота выгнали или заблокировали), 400 chat not found, 401 (токен).**
   Повторов нет. Тред переводится в `mode = 'off'`, `delivery_ok = 0`,
   `delivery_error` — русская формулировка (см. TG-07). Все черновики треда
   помечаются `blocked`. В очередь исключений — запись с действием
   «Открыть настройки чата» и контактным лицом.
4. **Частичная отправка многочастного сообщения.** Уже отправленные части остаются;
   тред не считается сломанным, если ошибка временная. При постоянной ошибке
   в середине — запись в исключения с явным текстом «контрагент получил часть 1 из 3».
5. **Восстановление.** Успешный `POST /api/outreach/check` (TG-07) снимает
   `delivery_ok = 0` и возвращает тред из `off` в тот режим, который был до сбоя
   (хранится в `outreach_threads.mode_before_off`). Автоматически из `off` тред
   не выходит никогда.
6. **Видимость.** Карточка контрагента показывает состояние доставки: дату
   последней успешной отправки, дату и текст последней ошибки. Метрика
   `eltrea_outreach_failed_total{source,code}` и запись в лог с префиксом `[outreach]`.
7. Ошибка доставки не должна ронять фоновую задачу: обработка каждого треда
   в собственном `try/except`, как в `_job_wrapper` (`app.py:144-152`).

**Экраны и компоненты.** `registry/outreach.py`, `registry/outreach_store.py`,
`telegram_bot.py`, `metrics.py`, `navigator_api.counterparties_block`
(`navigator_api.py:555-617`), административный экран — вкладки «Запросы» и
«Исключения» (`templates/navigator.html:1294-1348`).

**Зависимости.** TG-03, TG-04, TG-06. Требуется для включения TG-08.

**Критерии готовности.**
- Тест: 429 с `retry_after=7` — сообщение остаётся `queued`, `attempt` треда не изменился,
  следующая попытка запланирована не раньше чем через 7 секунд.
- Тест: три подряд 502 — статус `failed`, `delivery_ok = 0`, запись в исключениях.
- Тест: 403 — `mode = 'off'`, повторов нет, черновики `blocked`.
- Тест: успешный `check` возвращает тред в прежний режим; без `check` тред остаётся `off`.
- Тест: падение на одном треде не мешает обработать следующий в том же прогоне.
- В карточке контрагента видны дата последней успешной отправки и текст последней ошибки.
- Метрика `eltrea_outreach_failed_total` разделяет коды ошибок.

**Приоритет.** P1.

**Риски.** Автоматический выход из `off` привёл бы к долблению заблокировавшего
бота контрагента — отсюда запрет. Слишком быстрый повтор при 429 усугубляет лимит.
Тред, ушедший в `off` незаметно, означает молчаливую остановку запросов по целому
контрагенту — обязательна запись в очередь исключений, а не только в лог.

### TG-12. Курсор чтения канала вместо перечитывания временного окна

**Что нужно сделать.** Заменить чтение «сегодня с 07:00 МСК, не более 20 сообщений»
(`pipeline._since_today_msk`, `pipeline.py:91-99`, `TG_LIMIT = 20`, `TG_SINCE_HOUR_MSK = 7`,
`pipeline.py:82-84`) на курсор по идентификатору последнего прочитанного сообщения.
Завести таблицу `tg_channel_cursor` (`chat_id TEXT PRIMARY KEY`, `source TEXT`,
`last_message_id INTEGER NOT NULL DEFAULT 0`, `last_read_at TEXT`, `updated_at TEXT`)
новой миграцией и использовать существующий параметр `min_id` в
`TelegramUserbot.get_messages` (`telegram_userbot.py:64-81`), который сейчас всегда 0.

**Как должна работать логика.**
1. Перед чтением канала берётся `last_message_id` из курсора. Читаем
   `get_messages(chat_id, limit=TG_LIMIT_MAX, min_id=last_message_id)`.
   `TG_LIMIT_MAX` — предохранитель (по умолчанию 200), а не рабочий фильтр.
2. Курсор пуст (первый запуск, новый канал) — работает прежнее правило по времени
   (`_since_today_msk`), и после первого успешного чтения курсор ставится на
   максимальный прочитанный `msg.id`.
3. Курсор двигается **только после успешной записи в реестр**: если `ingest_batches`
   упал, сообщения должны быть перечитаны на следующем прогоне. Обновление курсора
   выполняется в `run_registry_pipeline` (`pipeline.py:275-344`) после
   `RegistryIngestor.ingest_batches`, а не в момент чтения.
4. Упёрлись в `TG_LIMIT_MAX` — курсор всё равно двигается на максимальный
   прочитанный id, в лог `warning` «прочитано максимум N, часть сообщений осталась,
   будет добрана следующим прогоном», и делается немедленный повторный проход
   (не более трёх подряд).
5. **Критично: снимок дня и пустая пачка.** Сейчас
   `out[alias] = (requests, had_snapshot or reset)` (`pipeline.py:270`), а
   `morning_telegram` идёт с `reset=True` (`app.py:85-90`). С курсором прогон
   в 13:00 законно прочитает ноль новых сообщений; при `reset=True` это означало бы
   «снимок дня пуст» и деактивацию **всех** позиций источника. Правило меняется:
   снимок засчитывается только если пачка непустая, то есть
   `snapshot = bool(requests) and (had_snapshot or reset)`. Это отдельный, обязательный
   пункт задачи.
6. Ручной пересбор: параметр `POST /run?sources=vahtapro&rewind=1` (или CLI-флаг
   `--rewind`) сбрасывает курсор к прежнему временному окну — на случай, когда
   нужно перечитать день.
7. Курсор виден в логе прогона: `[tg-read] vahtapro: с id=…, прочитано N, новый курсор=…`.

**Экраны и компоненты.** `pipeline.py` (`_read_telegram`, `_collect_requests`,
`run_registry_pipeline`), `telegram_userbot.py`, `registry/db.py` (миграция),
новый доступ в `registry/outreach_store.py` либо отдельный маленький модуль
`registry/cursors.py`, `app.py` (`POST /run`), `main.py` (CLI),
`tests/test_telegram_read.py`.

**Зависимости.** TG-01 (без обработки ошибок курсор будет двигаться по частично
прочитанному каналу). Миграция — вопрос **D1** (явная команда миграции и бэкап).
Задача пересекается с журналом прогонов `sync_runs` (направление «Эксплуатация»):
если он появится раньше, курсор хранится там же, а не отдельной таблицей —
зафиксировать в момент реализации, дублировать сущность не нужно.

**Критерии готовности.**
- Тест: первый прогон при пустом курсоре читает по времени и ставит курсор
  на максимальный id.
- Тест: второй прогон вызывает `get_messages` с `min_id`, равным курсору.
- Тест: сбой на этапе записи не двигает курсор — третий прогон читает те же сообщения.
- Тест: пустая пачка при `reset=True` **не** приводит к вызову `_deactivate_stale`.
- Тест: пачка ровно в `TG_LIMIT_MAX` сообщений порождает повторный проход и строку `warning`.
- Тест: `rewind=1` сбрасывает курсор и возвращает чтение по времени.
- Сообщение, вышедшее за прежнее окно 07:00 (например, ночной пост), после
  внедрения попадает в реестр — проверяется тестом на подставном клиенте.

**Приоритет.** P2.

**Риски.** Самый тяжёлый сценарий — деактивация всех позиций источника из-за
пустой пачки с `reset=True`; он закрыт пунктом 5 и отдельным тестом. Слишком рано
сдвинутый курсор означает безвозвратно пропущенные заявки (перечитать канал можно
только вручную). Рост объёма чтения после долгого простоя упирается в
`TG_LIMIT_MAX` — отсюда повторные проходы.

### TG-13. Приём медиа и склейка альбомов

**Что нужно сделать.** Научиться принимать заявки, присланные не текстом:
склеивать альбомы (несколько сообщений с общим `grouped_id`) в одну заявку и
сохранять факт вложения. Сейчас альбомы не склеиваются вовсе, а сообщение без
текста отбрасывается (`telegram_userbot.py:85-87`). Работающий образец склейки
есть в `telegram_post_fetcher.py` (константа `ALBUM_SPAN = 9`, сбор подписей всех
сообщений группы) — его логика переносится в `telegram_userbot.get_messages`.

**Как должна работать логика.**
1. При обходе сообщений группировать по `msg.grouped_id`: сообщения одной группы
   собираются в одну запись, текстом заявки становится склейка всех непустых
   подписей группы в порядке возрастания `id`, `id` записи — минимальный id группы
   (он же идёт в `source_ref = f"msg:{id}"`, `telegram_channel_processor.py:157`,
   чтобы заявка не двоилась между прогонами).
2. Группа может быть разорвана границей выборки: если первое или последнее сообщение
   пачки имеет `grouped_id`, добираются соседи в пределах `ALBUM_SPAN` — иначе
   часть подписей потеряется.
3. Для каждой заявки в `raw_payload` (сейчас туда кладутся `message_id` и `channel_id`,
   `telegram_channel_processor.py:148-154`) добавляется список вложений:
   `[{"kind": "photo", "file_id": "…", "file_name": "…", "mime": "…"}]` — без скачивания.
4. Сообщение вообще без текста, но с вложением, больше не исчезает: оно попадает
   в реестр как заявка с `parse_status='needs_attachment'`, пустым `raw_text` и
   заполненным списком вложений; позиций не создаёт, но видно в `/registry`
   с фильтром «требуют внимания». Это ровно тот случай, масштаб которого измеряет TG-02.
5. Скачивание и разбор содержимого вложений (OCR, xlsx, pdf) в объём **не входит**:
   это отдельный крупный блок, который заводится только при ответе «да» на D6.
6. Ретеншен: `file_id` Telegram живёт ограниченное время — в `raw_payload`
   сохраняется и дата, чтобы было понятно, что ссылка могла протухнуть.

**Экраны и компоненты.** `telegram_userbot.py`, `telegram_channel_processor.py`
(`collect_requests`), `registry/ingest.py` (новый `parse_status`), `/registry`
(`app.py:601-664`, фильтр `needs_review` уже есть — `r.parse_status != 'ok'`),
`templates/registry_request.html` (список вложений заявки — направление «Фронтенд»),
`tests/test_telegram_read.py`.

**Зависимости.** TG-01, TG-02. **Заблокирована вопросом D6** из
`docs/OPEN-QUESTIONS.md` («приходят ли заявки вложениями»): при варианте 1
делается только логирование (TG-02) и эта задача не начинается; при варианте 2
она обязательна. Решение принимается по данным метрики
`eltrea_telegram_skipped_messages_total` из TG-02 — то есть не раньше чем через
месяц после её внедрения.

**Критерии готовности.**
- Тест: три сообщения с одним `grouped_id`, подпись на втором — одна заявка,
  `source_ref` по минимальному id, текст равен подписи.
- Тест: две подписи в одной группе склеиваются в порядке id через перевод строки.
- Тест: группа, разорванная границей выборки, добирается целиком.
- Тест: повторный прогон по тем же сообщениям не создаёт вторую заявку.
- Тест: сообщение без текста с вложением создаёт заявку `needs_attachment`
  без позиций и с описанием вложения в `raw_payload`.
- Заявка с вложениями видна в `/registry` по фильтру «требуют внимания».
- Файлы вложений не скачиваются (в коде нет вызова `download_media`).

**Приоритет.** P2.

**Риски.** Смена правила формирования `source_ref` для альбомов может задвоить
уже принятые заявки — отсюда критерий на повторный прогон. Заявки без текста
засорят реестр, если контрагенты шлют вложениями много: нужен отдельный фильтр,
а не общий поток. `file_id` протухают, и «сохранённое вложение» через месяц
может оказаться нерабочей ссылкой.

### TG-14. Ротация и мониторинг StringSession

**Что нужно сделать.** Сделать состояние userbot-сессии наблюдаемым и заменяемым
без остановки системы. Сейчас `TELEGRAM_SESSION` — строка в окружении, дающая
полный доступ к живому Telegram-аккаунту (`telegram_userbot.py:25-32`,
`docs/LIMITATIONS.md`, раздел 6); её недействительность обнаруживается только
падением прогона, а перевыпуск требует ручного запуска `auth_userbot.py`
и правки `.env` с перезапуском контейнера.

**Как должна работать логика.**
1. **Проверка живости.** Задача `telegram_session_check` в `JOBS` (`app.py:84-109`),
   раз в час: подключение, `is_user_authorized()`, `whoami()`. Результат —
   метрика `eltrea_telegram_session_valid` (1/0) и
   `eltrea_telegram_session_checked_at` (unix-время). Проверка не читает каналы
   и не создаёт нагрузки на лимиты.
2. **Раннее предупреждение.** Проверка выполняется также при старте приложения
   (в `lifespan`, `app.py:168-178`) и её результат попадает в `/health`
   отдельным полем `telegram_session` — сейчас `/health` всегда `ok`, пока жив
   процесс (`app.py:211-217`). Закрытие `/health` авторизацией — задача направления
   «Безопасность»; здесь только добавление поля, и поле не должно содержать
   ни имени аккаунта, ни строки сессии.
3. **Ротация без правки кода.** Строка читается из переменной окружения либо из
   файла по пути `TELEGRAM_SESSION_FILE` (второй вариант позволяет заменить сессию
   без пересоздания контейнера). Приоритет: файл важнее переменной, если он задан
   и непуст. Значение перечитывается перед каждым прогоном, а не один раз на импорт.
4. **Процедура перевыпуска** описывается в `docs/`: остановка прогонов, запуск
   `auth_userbot.py`, запись новой строки, проверка через `telegram_session_check`,
   возобновление. Отдельно фиксируется, что сессию нельзя пересоздавать под нагрузкой:
   параллельные подключения одной строкой приводят к разлогину.
5. **Гигиена.** Строка сессии не пишется в логи, не попадает в тексты исключений
   (общий критерий с TG-01), не отдаётся ни одним роутом, исключена из `/metrics`
   и из ответов API. В `.env.example` — только имя переменной и описание, без примера значения.
6. **Технический аккаунт.** Реализация должна допускать смену владельца сессии
   (переход на отдельный аккаунт-«читатель») без изменений кода: единственное, что
   меняется, — значение переменной и `chat_id` каналов, если новый аккаунт добавлен
   в другие чаты.

**Экраны и компоненты.** `telegram_userbot.py`, `auth_userbot.py`, `app.py`
(`lifespan`, `JOBS`, `/health`), `metrics.py`, `.env.example`, `docs/` (раздел
об эксплуатации Telegram), `docker-compose.yml` (монтирование файла сессии,
если выбран этот путь).

**Зависимости.** TG-01 (классификация фатальных ошибок сессии). Связана с вопросом
**C2** из `docs/OPEN-QUESTIONS.md` («что делать с TELEGRAM_SESSION»): вариант по
умолчанию — отдельный технический аккаунт-читатель. Техническая часть (проверка,
метрика, ротация без перезапуска) от ответа **не зависит** и делается сразу;
от ответа зависит только то, чей аккаунт в итоге используется. Задача не отменяет
и не заменяет TG-03: чтение остаётся на userbot, отправка — на боте.

**Критерии готовности.**
- `/health` содержит поле `telegram_session` со значением `ok` | `invalid` | `unknown`
  и не содержит ни строки сессии, ни имени аккаунта.
- Метрика `eltrea_telegram_session_valid` присутствует в `/metrics` и меняется
  при подстановке недействительной сессии (тест на заглушке).
- Тест: заданный `TELEGRAM_SESSION_FILE` имеет приоритет над переменной окружения.
- Тест: значение перечитывается перед прогоном — подмена файла между двумя вызовами
  меняет используемую строку без перезапуска процесса.
- Тест: строка сессии не встречается в логах, в тексте исключений, в ответе
  `/health` и `/metrics` (проверяется по строке-маркеру).
- В `docs/` описана процедура перевыпуска с явным предупреждением о параллельных
  подключениях.
- Проверка живости не читает сообщения каналов (в тесте нет вызова `get_messages`).

**Приоритет.** P2.

**Риски.** Частая проверка подключением тоже расходует лимиты Telegram — интервал
не должен быть меньше часа. Перевыпуск сессии разлогинивает прежнюю: если сделать
это в момент прогона, прогон оборвётся. Файл сессии на диске — секрет в файловой
системе контейнера: права доступа и исключение из образа (`.dockerignore` уже
исключает `*.session`) обязаны быть проверены.
