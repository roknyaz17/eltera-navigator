### BE-02. Pydantic-модели на телах запросов и единый формат ошибки

**Что нужно сделать.** Описать Pydantic-модели на все тела POST и на query-параметры
изменяющих роутов, заменить ручную валидацию `POST /api/rates` (`app.py:400-438`,
`_rate_rules_from_payload`, `app.py:455-496`) на модель, и завести единый конверт ошибки
для JSON-роутов через `app.exception_handler`.

Роуты, которые нужно закрыть моделями: `POST /api/rates` (`app.py:400`), `DELETE
/api/rates/{rule_id}` (`app.py:441`, проверка `rule_id > 0`), `POST /run` (`app.py:341`,
query `sources`, `reset`), `POST /trigger/{name}` (`app.py:328`), `POST
/registry/dictionaries/confirm|delete|confirm-all` (`app.py:755,767,779`), `POST
/registry/manual` (`app.py:796`), `POST /registry/position/{position_id}` (`app.py:883`).

**Как должна работать логика.**
1. Модель `RateSavePayload`: `source: Literal[...]` по `pipeline.ALL_SOURCES`,
   `strategy: Literal["all","shifts","clients"]`, `amount: int | None` (>0),
   `tiers: list[RateTier]`, `clients: list[str]`, `vacancy: str = ""`, `note`, `payout`,
   `validFrom`/`validTo` — либо пустая строка, либо `YYYY-MM-DD`, `dryRun: bool = False`.
   `RateTier`: `minShifts: int > 0`, `amount: int > 0`. Правила, которые сейчас проверяются
   вручную, переносятся в валидаторы модели: при `strategy="all"` обязателен `amount`;
   при `strategy="shifts"` — непустой `tiers`; при `strategy="clients"` — непустой `clients`.
   Пустой набор правил остаётся ошибкой 422 с текстом «не заданы суммы».
2. Нечисловое значение суммы или ступени даёт **422** с указанием пути поля
   (`tiers.1.amount`), а не 500, как сейчас (`int()` без `try`, `app.py:465-469`).
3. `POST /registry/position/{position_id}`: `market_rate` перестаёт молча превращаться в `None`
   (`app.py:893-896`). Пустая строка — это `None` (значение снято), непустая нечисловая —
   ошибка; форма возвращается с сообщением у поля и HTTP 200 (это HTML-форма, не API).
4. Единый конверт ошибки для всех роутов с префиксом `/api/`:
   `{"error": {"code": "validation_error|not_found|conflict|internal", "message": "<человеческий текст>",
   "details": [{"field": "tiers.1.amount", "message": "..."}]}}`. Реализуется двумя обработчиками:
   на `RequestValidationError` (422) и на `HTTPException` (переупаковка `detail`). Тексты — русские.
5. Роуты, отдающие HTML (`/registry/*`), в конверт не заворачиваются: они возвращают ту же

6. Существующие коды ответов сохраняются там, где они уже осмысленны: неизвестный источник —
   400/422 с перечнем допустимых, неизвестная задача в `/trigger` — 404, отсутствующее правило

**Экраны и компоненты.** `app.py` (все перечисленные роуты), новый модуль `api_models.py`
(или `schemas.py`), новый `tests/test_api_rates.py` и `tests/test_api_errors.py`.
Контракт ошибки описывается в `docs/` одной таблицей — им же пользуется BE-13.

**Зависимости.** BE-01 (не обязательна, но обе задачи трогают `app.py` — делать после неё
дешевле). Фронтенд показывает `error.message` и подсвечивает поля из `details` — это `FE-*`;
до его готовности старое поведение фронта не ломается, потому что текст ошибки остаётся

**Критерии готовности.**

### BE-03. Журнал прогонов sync_runs

**Что нужно сделать.** Завести таблицу `sync_runs` (и подчинённую `sync_run_sources`) новой
миграцией и писать в неё каждый прогон пайплайна — плановый, ручной через HTTP и запущенный
из CLI. Сейчас журнала нет вовсе: что сделал ночной прогон, восстанавливается только по
`logs/eltera.log`, а упавший табличный источник просто выпадает из результата
(`pipeline.py:242-248`) и в статистике не виден.

Состав `sync_runs`: `id INTEGER PK`, `run_key TEXT UNIQUE` (идемпотентный ключ, см. BE-04),
`trigger TEXT` (`schedule` | `http` | `cli`), `job_name TEXT` (для планового — id задачи из
расписания, для ручного — `manual(<источники>)` как сейчас в `app.py:350`), `sources TEXT`
(JSON-массив алиасов), `reset INTEGER`, `status TEXT` (`running` | `ok` | `partial` | `failed`),
`started_at`, `finished_at`, `duration_ms`, счётчики из `IngestStats` (`registry/models.py:214-246`):
`requests_new`, `requests_changed`, `requests_unchanged`, `requests_failed`, `positions_added`,
`positions_updated`, `positions_deactivated`, `llm_calls_saved`; расход LLM: `llm_requests`,
`llm_tokens_in`, `llm_tokens_out`, `llm_cost_rub`; `error TEXT`, `host TEXT`, `pid INTEGER`,
`author TEXT` (логин из `verify_creds` для ручного запуска). Состав `sync_run_sources`:
`run_id`, `source`, `status`, `started_at`, `finished_at`, `requests`, `positions_added`,
`positions_updated`, `positions_deactivated`, `error`.

**Как должна работать логика.**
1. Запись со `status='running'` создаётся **до** первого сетевого вызова — в `_job_wrapper`
   (`app.py:144-152`) и в `run_pipeline` (`pipeline.py:347`), в одной точке-обёртке, чтобы
   плановый, HTTP- и CLI-запуск шли одним путём.
2. По завершении строка обновляется: `ok` — все источники отработали; `partial` — часть
   источников упала (сегодня такие ошибки только логируются, `pipeline.py:246-248`);
   `failed` — исключение до/вместо приёма.
3. Исключение внутри `_job_wrapper` уже ловится и не выходит наружу (`app.py:150-152`) —
   теперь оно дополнительно записывается в `error` (первые 500 символов) и в статус.
4. Каждый источник получает свою строку в `sync_run_sources`, включая те, что упали:
   именно здесь видно, что «ЯППИ не читался четыре дня».
5. Осиротевшие `running` (процесс убит в середине прогона) закрываются при старте приложения:
   строки со `status='running'` и `started_at` старше порога (по умолчанию 2 часа, значение
   в конфиге) переводятся в `failed` с `error='процесс прерван'`.

### BE-04. Флаг планировщика, единственность прогона и идемпотентность /trigger и /run

**Что нужно сделать.** Добавить переменную `SCHEDULER_ENABLED` (по умолчанию включено),
защиту от одновременных прогонов между процессами и идемпотентные ответы `POST /trigger/{name}`
(`app.py:328-338`) и `POST /run` (`app.py:341-353`). Сегодня планировщик крутится внутри
процесса приложения (`app.py:141,168-178`), и второй воркер uvicorn или второй контейнер
задваивает и прогоны, и полную перезапись Google-витрины
(`registry/export_sheets.export_to_sheets` перезаписывает лист целиком).

**Как должна работать логика.**
1. `SCHEDULER_ENABLED=0` — задачи не регистрируются, `scheduler.start()` не вызывается,
   в лог пишется одна строка «планировщик выключен флагом». `GET /health` и `GET /jobs`
   в этом режиме отдают `scheduler_running: false` и пустой список задач плюс явный признак
   `scheduler_enabled: false`, чтобы выключенный планировщик не выглядел как сломанный.
2. Межпроцессная защита: перед стартом прогона берётся файловый лок (`fcntl.flock`
   на `<каталог базы>/pipeline.lock`, неблокирующий) **и** проверяется отсутствие строки
   `sync_runs.status='running'` с пересекающимся набором источников. Лок отпускается в `finally`.
   Пересечение считается по множеству алиасов: прогон `["vahtapro","aaaplus"]` конфликтует
   с прогоном `["vahtapro"]`, но не с `["kpk"]`.
3. Занято — `POST /trigger` и `POST /run` отвечают **409** в едином конверте ошибки (BE-02):
   `{"error":{"code":"conflict","message":"Прогон по этим источникам уже идёт","details":[{"field":"run_id","message":"<id>"}]}}`.
   Плановая задача при занятом локе не ставится в очередь, а пропускается с записью в журнал
   (`status='failed'`, `error='пересечение с прогоном #N'`) — накапливать отложенные прогоны
   опаснее, чем пропустить один.
4. Идемпотентность: оба роута принимают заголовок `Idempotency-Key`. Ключ вместе с набором
   источников и флагом `reset` образует `sync_runs.run_key`. Повторный запрос с тем же ключом
   в течение окна (по умолчанию 10 минут, значение в конфиге) не запускает новый прогон,
   а возвращает **200** с тем же `run_id` и текущим статусом. Без заголовка ключ генерируется
   сервером, и идемпотентность работает только через проверку пересечения из пункта 2.
5. Ответ обоих роутов меняется с `{"status":"started", ...}` на
   `{"status":"started|already_running","run_id":<id>,"sources":[...],"reset":bool}`. Появляется
   `GET /api/runs/{id}` (BE-03) — по нему клиент узнаёт, чем кончилось.
6. Ограничение на число воркеров фиксируется в эксплуатации: `Dockerfile:33` остаётся
   с одним воркером, а в комментарии к команде запуска пишется, почему. Лок при этом остаётся —
   он защищает и от параллельного `python main.py` на том же каталоге данных.

**Экраны и компоненты.** `app.py` (`lifespan`, `_register_jobs`, `_job_wrapper`, `/health`,
`/jobs`, `/trigger/{name}`, `/run`); `registry/runs.py` (проверка пересечения); новый
`runlock.py` (файловый лок); `config.py`; `Dockerfile` (комментарий), `docker-compose.yml`;
новый `tests/test_run_lock.py`.

**Зависимости.** BE-03 (журнал прогонов — источник состояния «идёт»), BE-01
(`SCHEDULER_ENABLED` и окна — из конфига), BE-02 (формат ответа 409).

**Критерии готовности.**
- [ ] `SCHEDULER_ENABLED=0`: приложение поднимается, `GET /jobs` отдаёт пустой список,
      за сутки в `sync_runs` нет ни одной строки с `trigger='schedule'`.
- [ ] Два одновременных `POST /run?sources=kpk`: первый — 200 `started`, второй — 409
      с `run_id` первого; в `sync_runs` ровно одна строка.
- [ ] Два процесса приложения на одном каталоге данных не запускают прогон одновременно —
      проверено тестом на файловом локе.
- [ ] Повторный `POST /trigger/noon_tables` с тем же `Idempotency-Key` в течение окна
      возвращает 200 и тот же `run_id`, нового прогона не стартует.
- [ ] Тот же ключ спустя окно запускает новый прогон.
- [ ] Плановая задача, пришедшая на занятый лок, пропускается и оставляет запись в журнале
      с причиной; следующая по расписанию отрабатывает штатно.
- [ ] Лок снимается после падения процесса (проверено убийством процесса в тесте) —
      следующий запуск не блокируется навсегда.

**Приоритет.** P0.

**Риски.** Неверно снятый лок — худший исход: прогоны перестанут запускаться совсем, и это
не будет заметно до вечера. Поэтому лок обязан сниматься операционной системой при смерти
процесса (`flock`, а не файл-маркер), а «осиротевшие» строки `running` — закрываться по
таймауту (BE-03). Второй риск — 409 на кнопке «Запустить сейчас»: без правки фронта
пользователь увидит непонятную ошибку вместо «прогон уже идёт»; текст сообщения должен
быть пригоден к показу как есть.

### BE-05. Таймауты и ретраи для внешних вызовов

**Что нужно сделать.** Завести общий модуль `retry.py` с одной реализацией повторов
(экспоненциальная пауза с джиттером, потолок попыток, общий бюджет времени, классификация
ошибок на «повторяемые» и «фатальные», лог каждой попытки) и применить его во всех точках
выхода наружу. Сейчас ретраи есть только у Яндекс.Диска (`RETRY_PAUSES = (1.0, 3.0, 7.0)`,
`yandex_disk.py:26`) и одна повторная попытка у LLM (`MAX_RETRIES = 1`,
`vacancy_parser.py:231`); у Telethon и gspread нет ни таймаутов, ни `try/except`, поэтому
`FloodWaitError` или обрыв связи роняет прогон источника целиком.

**Как должна работать логика.**
1. Telethon (`telegram_userbot.py:16-70`, вызовы `get_messages`): `FloodWaitError` обрабатывается
   отдельно — уважается `e.seconds`, но с потолком (по умолчанию 300 с, значение в конфиге);
   если ожидание превышает потолок, источник помечается упавшим, а прогон остальных
   продолжается. Сетевые обрывы (`ConnectionError`, `TimeoutError`, `RpcCallFailError`) —
   до трёх повторов. Ошибки авторизации (`AuthKeyError`, `SessionPasswordNeeded`) — фатальны,
   повторять бессмысленно, нужен внятный текст в лог и в журнал прогонов.
2. gspread (`sheets_adapter.py`: `get_sheet_data`, `get_project_matrix_data_all`,
   `upsert_vacancies`, `batch_update`, `append_rows`, `batch_clear`): явный таймаут на HTTP,
   повтор на 429 и 5xx, отсутствие повтора на 403/404. Отдельно — выгрузка витрины
   (`registry/export_sheets.py:31-62`): она перезаписывает лист целиком, повтор середины
   записи опасен, поэтому повторяется операция целиком, а не отдельный `update`.
3. Seatable (`seatable_adapter.py:41-79`): таймауты уже заданы (15/30 с), добавляются повторы
   на 429/5xx. Отдельно: если регулярное выражение не нашло `accessToken` в HTML
   (`seatable_adapter.py:48-50`), ошибка должна называть причину — «страница external-link
   изменилась», а не общий `RuntimeError`.
4. LLM (`vacancy_parser.py:206-231`): добавляется явный таймаут запроса и повтор на 429/5xx
   с паузой; существующая логика `MAX_RETRIES` на невалидный JSON сохраняется и не смешивается
   с сетевыми повторами — это разные причины.
5. Все повторы пишут в лог одну строку на попытку: точка вызова, номер попытки, причина, пауза.
   Итоговая неудача попадает в `sync_run_sources.error` (BE-03).
6. Значения по умолчанию (число попыток, паузы, потолок ожидания FloodWait, таймауты)
   объявляются в конфиге, а не в коде вызова.

**Экраны и компоненты.** Новый `retry.py`; правки `telegram_userbot.py`,
`telegram_post_fetcher.py` (`fetch_many`, `_fetch_chat`), `sheets_adapter.py`,
`registry/export_sheets.py`, `seatable_adapter.py`, `vacancy_parser.py`, `yandex_disk.py`
(переезд на общий модуль); `config.py`; новый `tests/test_retry.py`.

**Зависимости.** BE-01 (параметры из конфига), BE-03 (запись причины отказа в журнал).
Вопрос **C2** из `docs/OPEN-QUESTIONS.md` (судьба `TELEGRAM_SESSION`) на эту задачу не влияет:
ретраи нужны при любом варианте аккаунта.

**Критерии готовности.**
- [ ] Стаб Telethon, бросающий `FloodWaitError(seconds=5)`, приводит к паузе и успешной второй
      попытке; прогон не падает.
- [ ] `FloodWaitError(seconds=3600)` не приводит к часовому ожиданию: источник помечается
      упавшим за секунды, остальные источники прогона отрабатывают.
- [ ] Стаб gspread, отдающий 429 дважды и затем 200, приводит к успешной записи;
      403 повторов не вызывает.
- [ ] У каждого внешнего вызова есть явный таймаут — проверено ревью-чеклистом в описании PR
      и тестом, что вызов без таймаута не проходит линтер-правило проекта.
- [ ] Число попыток и паузы читаются из конфига; при `RETRY_ATTEMPTS=1` повторов нет.
- [ ] В логе на каждую попытку — ровно одна строка с причиной и паузой.

**Приоритет.** P1.

**Риски.** Слишком агрессивные повторы к Telegram усиливают FloodWait и могут привести
к временной блокировке аккаунта — потолок ожидания и общий бюджет обязательны. Повтор записи

поэтому повторяется только идемпотентная операция (полная перезапись листа), а `append_rows`

### BE-06. Ограничитель числа вызовов LLM за прогон

**Что нужно сделать.** Добавить предохранитель на расход модели: `LLM_MAX_CALLS_PER_RUN`
и `LLM_MAX_COST_RUB_PER_RUN` (оба по умолчанию выключены, значение 0 = без ограничения)
и счётчик в фазе разбора `RegistryIngestor._parse` (`registry/ingest.py:272-320`). Сейчас
предохранителя нет вовсе: большой снимок дня в Telegram или разово перечитанная таблица
уводят прогон в неограниченный расход, а стоимость видна только постфактум в логе
(`pipeline.py:323-326`).

**Как должна работать логика.**
1. Счётчик вызовов и накопленная стоимость ведутся на прогон (не на источник), стоимость
   считается тем же `TokenUsage` (`vacancy_parser.py:20-45`).
2. При достижении лимита новые вызовы не делаются. Заявки, до которых не дошла очередь,
   **не** помечаются провалом разбора: они остаются с прежним `parse_status` (`pending`
   для новых, `ok` для ранее разобранных), а их позиции попадают в `keep`.
3. Ключевое правило: при срабатывании лимита снапшот-деактивация (`_deactivate_stale`,
   `registry/ingest.py:597-618`) для затронутого источника **не выполняется**. Иначе неразобранная
   часть снимка будет прочитана как «потребность исчезла», и живые позиции погаснут — это
   необратимо для витрины и заметно сразу.
4. Прогон завершается со статусом `partial` (BE-03), в `sync_runs.error` пишется
   «лимит вызовов LLM исчерпан: N из M заявок не разобраны», в лог — предупреждение,
   в метрики — счётчик срабатываний ограничителя (новая метрика `eltrea_llm_limit_hits_total`).
5. Следующий прогон дораз бирает оставшееся: заявки с `parse_status != 'ok'` перепарсиваются
   даже при неизменившемся тексте — это уже действующее поведение (`registry/ingest.py:172-175`).
6. Приоритет разбора при нехватке лимита — по возрастанию `first_seen_at` заявки: сначала
   старые, чтобы одна и та же заявка не откладывалась бесконечно.

**Экраны и компоненты.** `registry/ingest.py` (`RegistryIngestor.__init__`, `_parse`, `_store`),
`pipeline.py` (передача лимитов), `config.py`, `metrics.py` (новая метрика),
`tests/test_ingest.py` (новые случаи).

**Зависимости.** BE-01 (лимиты из конфига), BE-03 (статус `partial` и текст причины).

**Критерии готовности.**
- [ ] При `LLM_MAX_CALLS_PER_RUN=5` и 20 новых заявках стаб-парсер получает ровно 5 вызовов.
- [ ] Ни одна активная позиция источника после срабатывания лимита не деактивирована.
- [ ] Заявки, не попавшие в разбор, сохраняют `parse_status='pending'` и разбираются
      на следующем прогоне без изменения текста.
- [ ] Прогон завершается со `status='partial'` и внятным текстом причины в журнале.
- [ ] При лимите 0 (по умолчанию) поведение полностью совпадает с текущим — проверено
      прогоном существующих тестов `tests/test_ingest.py` без изменений.
- [ ] Лимит по стоимости срабатывает независимо от лимита по числу вызовов.

**Приоритет.** P1.

**Риски.** Слишком низкий лимит превратит систему в вечно недоразобранную: каждый прогон
будет обрабатывать часть, а витрина — отставать. Значения по умолчанию должны быть выключены,
а включение — осознанным решением с оглядкой на статистику расхода из журнала прогонов.
Второй риск — отключение снапшот-деактивации: если лимит будет срабатывать регулярно,
погашенные у контрагента позиции перестанут гаснуть и витрина начнёт показывать закрытые
потребности.

### BE-07. Модуль registry/validate.py — единый слой проверки

**Что нужно сделать.** Создать `registry/validate.py` — единственное место, где система решает,
какое поле обязательно, в каком состоянии находится значение и какие проблемы есть у позиции.
Сейчас это размазано по трём местам с разными ответами: `navigator_api.REQUIRED_FIELDS`
(`navigator_api.py:33-40`: cits, house, meals, rate, sched, need), `registry.queries.KEY_FIELDS`
(`registry/queries.py:25-27`: vacancy_name, city, shift_rate, need_total, schedule, counterparty)
и клиентская функция `issues()` в шаблоне (`templates/navigator.html:362-424`). Пересечение
двух списков — три поля, из-за чего один и тот же пробел считается по-разному на `/registry`
и на `/navigator`.

**Как должна работать логика.**
1. Один перечень обязательности с тремя уровнями: базовый набор системы, набор по источнику
   и набор по контрагенту. Пока сущности контрагента нет (таблица `counterparties` отсутствует,
   заводится задачей `DB-*`), переопределение делается по `positions.source` — этого достаточно,
   потому что сегодня «контрагент» на экране и есть источник.
2. Функция `field_state(position, field)` возвращает одно из состояний, которые уже рисует
   интерфейс пятью способами (`templates/navigator.html`, единая модель значения):
   `known` — значение есть; `empty` — `NULL` («в заявке не сказано»); `default` — значение
   подставлено `field_defaults`, а не извлечено; `conflict` — источники расходятся;
   `asked` — поле запрошено у заказчика и ждёт ответа. Состояния `default` и `asked` требуют
   хранения (таблицы `field_status`/`field_conflicts` — задача `DB-*`); до их появления
   функция возвращает их только для случаев, вычислимых на лету: `conflict` — по нынешнему
   алгоритму `find_dupes`/`CONFLICT_FIELDS` (`navigator_api.py:458-510`).

### BE-08. Виды проблем format, unparsed и source: породить или удалить

**Что нужно сделать.** Закрыть три мёртвые ветки. `ISSUE_KINDS` в `templates/navigator.html:138-145`
объявляет шесть видов проблем с подписями и цветами, но ни один код-путь не порождает `format`,
`unparsed` и `source` — на экране их не бывает никогда. Объём задачи определяется ответом
на вопрос **B4**: вариант 1 — реализовать, вариант 2 (принят по умолчанию) — убрать из разметки.

**Как должна работать логика.**

Вариант «реализовать» (объём бэкенда):
1. `unparsed` — непустое сырое значение при пустом нормализованном. Вычисляется по парам
   «сырое → нормализованное» из `RAW_FIELDS` (`registry/models.py:82-90`): `city_raw` есть,
   `city` пуст; `schedule_raw` есть, `work_pattern` и `min_shifts` пусты; `shift_rate_raw` есть,
   `shift_rate` и `hourly_rate` пусты; `requirements_raw` есть, `requirements` пуст;
   `counterparty_raw` есть, `counterparty` пуст; `region_raw` есть, `region` пуст.
   Текст проблемы содержит исходную строку — рекрутёр должен видеть, что именно не разобралось.
2. `format` — значение разобралось, но противоречиво по форме: в `shift_rate_raw` одновременно
   есть признаки часа и смены («2200 ₽/смена, 250 ₽/час» — `parse_rate`, `registry/normalize.py:274-312`,
   намеренно не пересчитывает одно в другое); ставка ниже порогов правдоподобия
   (`MIN_SHIFT_RATE = 100`, `MIN_HOURLY_RATE = 20`, `registry/normalize.py:77-78`) при непустом
   сыром значении; `age_from > age_to`; `need_men + need_women + need_couples > need_total`
   при явно заданном `need_total`.
3. `source` — проблема не позиции, а канала: последний прогон источника завершился `failed`
   или `partial` (журнал `sync_runs`, BE-03); заявка позиции имеет `parse_status != 'ok'`
   (`requests.parse_status`, признак `needs_review` в реестре); материал позиции признан
   недоступным (BE-14). Проблема вида `source` привязывается к позиции, но в админской очереди
   группируется по источнику — иначе одна сломанная таблица даст сотню одинаковых карточек.
4. Все три вида порождаются в `registry/validate.issues` (BE-07), в том же формате, что
   `conflict`/`duplicate`/`missing`, и попадают в `/api/navigator`.

Вариант «удалить» (объём бэкенда): убедиться, что серверная часть их не порождает и не заявляет,
описать решение в `docs/`, поставить задачу `FE-*` на удаление трёх записей из `ISSUE_KINDS`
и связанных веток разметки. Бэкенд при этом фиксирует перечень видов проблем в одном месте
(`registry/validate.ISSUE_KINDS`) и отдаёт его в `/api/navigator` — чтобы интерфейс больше
не мог объявить вид, которого не бывает.

**Экраны и компоненты.** `registry/validate.py`, `navigator_api.py` (ключ `issues`),
`registry/normalize.py` (только чтение порогов — правила не меняются),
`tests/test_validate.py`. Разметка — `FE-*`.

**Зависимости.** BE-07 (единый слой проверки и формат проблемы). Для вида `source` — BE-03
(журнал прогонов) и BE-14 (живость ссылок). Блокирующий вопрос **B4** из
`docs/OPEN-QUESTIONS.md`: без ответа выбирается вариант по умолчанию — удалить.

**Критерии готовности.**
- [ ] Перечень видов проблем объявлен ровно в одном месте на сервере и отдаётся в API;
      разметка его не дублирует.
- [ ] Для варианта «реализовать»: заявка со ставкой «2200 за смену / 250 в час» порождает
      проблему `format` с исходной строкой в тексте; заявка с непустым `city_raw` и пустым
      `city` порождает `unparsed`.
- [ ] Для варианта «реализовать»: упавший источник даёт ровно одну карточку в админской
      очереди, а не по одной на каждую позицию.
- [ ] Для варианта «удалить»: в кодовой базе (сервер и шаблон) нет упоминаний `format`,
      `unparsed`, `source` как видов проблем; решение записано в `docs/`.
- [ ] `tests/test_validate.py` содержит по одному случаю на каждый реализованный вид.

**Приоритет.** P1.

**Риски.** При реализации `format` и `unparsed` объём очереди исключений может вырасти
в разы — сырые поля непустые почти всегда, а нормализованные часто пусты по правилу «ничего
не додумываем». Прежде чем включать, нужно посчитать на боевой базе, сколько позиций получат
новую проблему; если счёт идёт на сотни, вид проблемы включается по одному полю за раз.

### BE-09. Модуль registry/public.py — PUBLIC_FIELDS, серверная проекция и текст кандидату

**Что нужно сделать.** Создать `registry/public.py` — серверную границу между внутренними
данными и тем, что можно показать кандидату. Сегодня такой границы нет: `/api/navigator`
отдаёт всё, включая контрагента, объект, источник, внутренние номера и ставку рекрутера,
а вырезание делает клиентская функция `scrub()` в шаблоне
(`templates/navigator.html:448-461`) — последний барьер вместо первого. Текст кандидату тоже
собирается в браузере (`candidateText`, `templates/navigator.html:464-535`).

**Что реализуется:** белый список `PUBLIC_FIELDS`; функция `public_position(row) -> dict`
(проекция позиции на публичные поля); функция `scrub(text, secrets) -> (text, removed)`
(вырезание внутренних имён из свободных текстов с сохранением ссылок); функция
`candidate_text(position, media_ids) -> str` (готовый текст кандидату).

**Как должна работать логика.**
1. `PUBLIC_FIELDS` — явный белый список, а не «все поля минус несколько». В него не входят
   и не могут войти: `counterparty`, `counterparty_raw`, `object_name`, `object_address`,
   `source`, `source_name`, `source_url`, `position_id`, `request_id`, `legacy_id`, все поля
   ставки рекрутера (`rec`), все менеджерские поля (`registry/models.py:92-106`), `raw_text`
   и любые `*_raw`. Список сопровождается тестом-сторожем: добавление нового поля в
   `registry/models.DATA_FIELDS` не делает его публичным автоматически.
2. `scrub(text, secrets)` вырезает из свободных текстов (`requirements`, `duties`, `advantages`,
   `risks`, `housing_conditions`, `transport_terms`) вхождения контрагента, объекта и названия
   источника, заменяя их на `———`, и возвращает список вырезанных слов, чтобы рекрутёр видел,
   что именно ушло. Правило из действующего шаблона сохраняется: URL из-под замены выводятся,
   ссылки ломать нельзя (`templates/navigator.html:451-459`). Сравнение регистронезависимое,
   с нормализацией `ё`→`е`.
3. `candidate_text(position, media_ids)` повторяет порядок абзацев, который уже принят
   и проверен на людях: должность и город → ставка, график, часы → требования (пол, возраст,
   гражданство) → требования текстом → проживание → питание → выплаты и удержания → проезд →
   медкнижка, СБ, тестирование → приглашение → блок «Подробнее:» со ссылками. В текст попадают
   только материалы со `vis="public"` и `alive=true`, выбранные рекрутёром.
4. Незаполненные поля в текст не попадают вовсе — не «не указано», а отсутствие абзаца.
   Правило «ничего не додумываем» действует и здесь.
5. Роут `POST /api/positions/{position_id}/candidate-text` (Basic) принимает список выбранных
   материалов и возвращает `{text, removed: [...], media: [...]}`. Клиентская генерация
   после этого удаляется задачей `FE-*`; `scrub()` в шаблоне остаётся не дольше переходного
   периода.
6. Публичный алиас контрагента (`cpAlias`, `navigator_api.py:381`, всегда пустой) в этой задаче
   **не заводится** — нужна сущность контрагента и решение, кто алиас подтверждает. До ответа
   работодатель показывается как сейчас: категория объекта (`vacancy_category`).

**Экраны и компоненты.** Новый `registry/public.py`; `app.py` (новый роут);
`navigator_api.py` (`build_payload` — публичная часть больше не собирается на клиенте);
новый `tests/test_public.py`. Разметка и удаление клиентского генератора — `FE-*`.

**Зависимости.** BE-02 (формат ошибки и модель тела запроса). Публичный алиас блокирует
вопрос **C5** из `docs/OPEN-QUESTIONS.md` и сущность контрагента (`DB-*`, вопрос **B1**) —
эта часть выносится за рамки задачи. Публичный API (BE-13) обязан строиться поверх этого
модуля, а не наоборот.

**Критерии готовности.**
- [ ] Тест перебирает все позиции тестовой базы и проверяет: ни в одном значении
      `public_position()` не встречается `counterparty`, `object_name`, `source_name`
      этой позиции.
- [ ] Тот же тест — для результата `candidate_text()`; проверка идёт по подстроке
      без учёта регистра и с нормализацией `ё`.
- [ ] Ставка рекрутера, внутренний идентификатор позиции и номер заявки не встречаются
      в публичной проекции ни при каких данных.
- [ ] Добавление нового поля в `DATA_FIELDS` без правки `PUBLIC_FIELDS` роняет тест-сторож.
- [ ] Ссылки внутри свободного текста после `scrub()` остаются кликабельными и неизменными.
- [ ] `candidate_text` для позиции с пустыми проживанием и питанием не содержит слов
      «не указано» и не содержит пустых абзацев.
- [ ] Текст, собранный сервером, совпадает с текстом, который сегодня собирает браузер,
      на десяти контрольных позициях (сверка при переносе).

**Приоритет.** P1.

**Риски.** Утечка внутреннего названия в текст кандидату — репутационная и коммерческая
проблема: кандидат узнаёт заказчика в обход агентства. Поэтому проверка строится не на «мы
вырезали известные слова», а на белом списке полей: то, чего нет в `PUBLIC_FIELDS`,
физически не доезжает до генератора. Второй риск — расхождение серверного и клиентского
текста на переходный период: два генератора одновременно жить не должны, порядок выкатки —
сервер, сверка, удаление клиентского.

### BE-11. PATCH позиции с записью автора в историю

**Что нужно сделать.** Добавить `PATCH /api/positions/{position_id}` для менеджерских полей
и начать писать ручные правки в `position_history` с указанием автора. Сегодня форма
`POST /registry/position/{position_id}` (`app.py:883-905`) сохраняет пять полей (`status`,
`priority`, `responsible_manager`, `recruiter_comment`, `market_rate`) через
`rq.update_manager_fields` (`registry/queries.py:241-255`) и **не оставляет следа**:
`position_history` заполняется только приёмом заявок (`registry/ingest.py:464-474`), колонки
автора там нет вовсе, а `request_id` объявлен `NOT NULL` без значения по умолчанию
(`registry/db.py:131-139`).

**Как должна работать логика.**
1. Миграция: `ALTER TABLE position_history ADD COLUMN author TEXT NOT NULL DEFAULT ''`
   и `ADD COLUMN change_source TEXT NOT NULL DEFAULT 'ingest'` (значения `ingest` | `manual` |
   `script`). Для ручной правки `request_id` записывается пустой строкой — колонка `NOT NULL`
   без `DEFAULT`, поэтому значение подставляется кодом явно.
2. Новый слой `registry/queries.update_manager_fields(conn, position_id, values, author,
   change_source)` — единственная точка записи менеджерских полей. Он читает старые значения,
   пишет только реально изменившиеся поля, на каждое изменённое поле кладёт строку в
   `position_history` (`field`, `old_value`, `new_value`, `changed_at`, `author`,
   `change_source`) и обновляет `positions.updated_at`.
3. `PATCH /api/positions/{position_id}` принимает JSON с подмножеством `MANAGER_FIELDS`
   (`registry/models.py:92-106`: status, priority, responsible_manager, recruiter_comment,
   sales_script, objections, market_rate, market_deviation) — сегодня форма умеет только пять
   из восьми. Поля, не входящие в `MANAGER_FIELDS`, отклоняются с 422: приём заявок эти поля
   не трогает никогда, и наоборот — менеджер не правит поля, приходящие из источника.
4. Отличие «не передано» от «снято»: отсутствующий ключ не меняет поле, `null` — снимает
   значение. Именно поэтому PATCH, а не PUT.
5. Существующая HTML-форма продолжает работать и ходит в тот же слой — расхождения между
   двумя путями быть не должно. Ответ формы остаётся редиректом 303, ответ PATCH — обновлённая
   позиция в едином формате.
6. Автор берётся из `verify_creds` (`app.py:191-207`) — сейчас это общий логин
   `WEB_USER`, и в истории он будет один на всех. Это осознанный промежуточный шаг: колонка
   и запись появляются сразу, а различимость авторов — после появления пользователей (`SEC-*`).
   Значение пишется как есть, без нормализации.
7. `GET /api/positions/{position_id}/history` (Basic) отдаёт историю с автором и источником
   изменения; карточка позиции (`templates/registry_position.html`) начинает показывать
   автора — правка разметки за `FE-*`.

**Экраны и компоненты.** Новая миграция в `registry/db.py`; `registry/queries.py`
(`update_manager_fields`, `history_of_position`); `app.py`
(`POST /registry/position/{position_id}`, новые `PATCH /api/positions/{id}` и
`GET /api/positions/{id}/history`); `tests/test_queries.py` (существующий случай на изоляцию
менеджерских полей дополняется), новый `tests/test_position_patch.py`.

**Зависимости.** BE-02 (модель тела и формат ошибки — в том числе `market_rate`, который
сейчас молча превращается в `None`, `app.py:893-896`). Задача `DB-*` на явную команду миграции
(вопрос **D1**). Вопрос **C1** из `docs/OPEN-QUESTIONS.md` (как заводятся пользователи)

до появления ролей, и после `SEC-*` в неё начнёт писаться идентификатор пользователя.

**Критерии готовности.**
- [ ] Правка `status` через форму и через PATCH даёт одинаковую запись в `position_history`
      с `change_source='manual'` и непустым `author`.
- [ ] Правка, не меняющая значение, записи в историю не создаёт.
- [ ] Передача `null` снимает значение поля; отсутствие ключа значение не трогает.

- [ ] Приём заявки после ручной правки не затирает менеджерские поля — существующий тест

- [ ] Миграция применяется на копии боевой базы, существующие строки `position_history`

**Приоритет.** P1.

**Риски.** До появления пользователей (`SEC-*`) все правки будут подписаны одним общим логином —

### BE-12. Расчёт радиуса и мультивыбора городов на сервере

**Что нужно сделать.** Перенести расчёт расстояния и фильтрацию по городам из браузера
на сервер. Сейчас гаверсинус живёт в шаблоне (`templates/navigator.html:217-222`,
`nearNames()` `:227-235`), а на сервере есть только справочник координат 62 городов
(`registry/geo.CITY_COORDS`, `registry/geo.py:37-91`) и никакой функции расстояния — поиск
по всему репозиторию по `haversine|radius|расстоян` даёт совпадения только в комментариях.
Следствие: чтобы фильтр работал, клиент обязан получить **все** позиции разом —
`/api/navigator` не имеет ни пагинации, ни серверных фильтров.

**Как должна работать логика.**
1. В `registry/geo.py` добавляется `distance_km(city_a, city_b) -> float | None` (гаверсинус,
   R = 6371, округление до целого — та же формула, что в браузере, чтобы цифры совпали)
   и `cities_within(anchor, radius_km, candidates) -> list[(city, distance)]`.
2. Города без координат радиусом не подхватываются — это действующее правило
   (`registry/geo.py:8-10`), оно сохраняется. Но такие города должны быть видимы: в блоке
   `cities` (`navigator_api.cities_block`, `navigator_api.py:667-686`) появляется признак
   `noCoords: true`, чтобы интерфейс мог объяснить, почему город не попал в радиус,
   а не молчал.
3. `/api/navigator` принимает `cities` (список через запятую), `radius_km` (0..200, 0 = выкл)
   и `anchor` (город-якорь; по умолчанию — первый из `cities`, как сегодня в браузере).
   Сервер возвращает только подходящие позиции, а в блоке `cities` — расстояние до якоря
   по каждому городу.
4. Сортировка «Ближе к городу» считается на сервере и приезжает готовым порядком:
   на клиенте её без полного среза данных не выполнить.
5. Источник координат — таблица `cities` (заводится задачей `DB-*`). Пока таблицы нет,
   функция читает `CITY_COORDS`; переключение источника — одна строка, контракт API от этого
   не зависит.
6. Контракт `/api/navigator` меняется: параметры фильтрации становятся серверными.
   Изменение согласуется с `FE-*` и выкатывается одновременно; на переходный период сервер
   при отсутствии параметров отдаёт полный срез, как сейчас.

**Экраны и компоненты.** `registry/geo.py`; `navigator_api.py` (`build_payload`,
`cities_block`, базовый SQL `navigator_api.py:718-730`); `app.py` (`GET /api/navigator` —
новые query-параметры); новый `tests/test_geo.py`. Правка клиентского фильтра — `FE-*`.

**Зависимости.** Блокирующий вопрос **B6** из `docs/OPEN-QUESTIONS.md` (браузер, сервер
или гибрид; по умолчанию — вариант 2, перенос на сервер вместе с заведением `cities`)
и **D3** (откуда берутся координаты городов). Таблица `cities` — `DB-*`. BE-02 (валидация
query-параметров). Согласование контракта — `FE-*`.

**Критерии готовности.**
- [ ] `distance_km("Москва", "Тверь")` совпадает с числом, которое сегодня показывает браузер,
      с точностью до 1 км — сверено на десяти парах.
- [ ] `GET /api/navigator?cities=Москва&radius_km=50` возвращает подмножество позиций,
      совпадающее с результатом текущей клиентской фильтрации на той же базе.
- [ ] Город без координат не попадает в радиус и помечен `noCoords` в блоке `cities`.
- [ ] `radius_km=0` и пустой список городов дают полный срез — поведение по умолчанию
      не меняется.
- [ ] `radius_km=999` отклоняется с 422; `cities` с неизвестным городом не роняет запрос,
      а возвращает пустой результат с пояснением.
- [ ] Сортировка «ближе к городу» приезжает готовым порядком и не требует пересортировки
      на клиенте.
- [ ] Мультивыбор: расстояние считается до **любого** из выбранных якорей, как в браузере

**Приоритет.** P2.

**Риски.** Смена контракта `/api/navigator` ломает работающий экран, если фронт и бэк
выкатятся не одновременно. Поэтому параметры обязаны быть необязательными, а поведение
без них — прежним. Второй риск — расхождение чисел: у клиента и сервера разные округления
дадут «в радиусе 50 км» разный состав городов, и пользователь решит, что что-то сломалось;
формула и округление должны быть скопированы буквально.

### BE-14. Проверка живости ссылок на материалы

**Что нужно сделать.** Заменить константу на факт. Сегодня `media_block`
(`navigator_api.py:322-345`) отдаёт `"alive": True` без единого обращения к сети
(`navigator_api.py:339-343`), а интерфейс при этом рисует состояния «недоступна с 2 августа ·
перепроверок 24» и подпись «перепроверка каждые 6 часов» (`templates/navigator.html:814`) —
под ними нет никакого механизма. Нужны хранение состояния ссылки, фоновая проверка
и честная отдача признака.

**Как должна работать логика.**
1. Хранение: колонки состояния у материала — `last_checked_at`, `http_status`, `alive`,
   `checks_count`, `fail_count`, `first_failed_at`. Место хранения зависит от того, появится
   ли таблица `position_media` (задача `DB-*`); если нет — колонки добавляются к `position_kb`
   (`registry/db.py:232-245`) новой миграцией.
2. Фоновая задача `link_check` с интервалом `LINK_CHECK_INTERVAL_HOURS` (по умолчанию 6 —
   ровно то число, которое уже написано в интерфейсе). Задача регистрируется в том же
   планировщике и подчиняется `SCHEDULER_ENABLED` и локу (BE-04).
3. Проверка: `HEAD` с таймаутом, при ответе 405/501 — `GET` с ограничением по размеру тела.
   Повторы и паузы — через общий модуль (BE-05). Ограничение темпа: не более N запросов
   в минуту к одному хосту (`disk.yandex.ru`, `cloud-api.yandex.net`), чтобы не получить 429
   на индексации базы знаний, которая ходит туда же.
4. Правило пометки: ссылка считается мёртвой только после **двух** подряд неудачных проверок —
   одиночная сетевая ошибка не должна гасить кнопку у рекрутёра. `first_failed_at` — дата
   первой неудачи, из неё интерфейс строит «недоступна с 2 августа».
5. Ссылка **не удаляется** при недоступности: источник сохраняется, перепроверки продолжаются
   с увеличенным интервалом. Это уже сформулированное правило интерфейса
   (`templates/navigator.html`, блок «Материалы и ссылки»), бэкенд обязан ему соответствовать.
6. `media_block` начинает отдавать реальные `alive`, `upd`, `checks`, `since`; позиция
   с мёртвой ссылкой порождает проблему вида `source` (BE-08), если этот вид принят к реализации.
7. Материалы, пропавшие при переобходе диска, по-прежнему исчезают из `position_kb`
   (`project_kb.py:482-484`) — проверка живости это поведение не отменяет и не дублирует.

**Экраны и компоненты.** Новая миграция в `registry/db.py`; новый `link_check.py`;
`navigator_api.py` (`media_block`); `app.py` (регистрация задачи, ручной запуск через
`POST /trigger/link_check`); `metrics.py` (счётчики проверок и мёртвых ссылок);
новый `tests/test_link_check.py`.

**Зависимости.** BE-05 (таймауты и повторы), BE-04 (флаг планировщика и защита от двойного
запуска), BE-03 (журнал — проверка ссылок тоже прогон и должна быть видна), BE-08 (вид
проблемы `source`). Таблица `position_media` — `DB-*`. Отображение состояний — `FE-*`.

**Критерии готовности.**
- [ ] Стаб, отдающий 404, помечает ссылку мёртвой только после второй неудачной проверки.
- [ ] Восстановившаяся ссылка возвращается в `alive=true`, `fail_count` обнуляется,
      `first_failed_at` очищается.
- [ ] `media_block` отдаёт `alive` из базы; в коде не осталось литерала `True`
      (`navigator_api.py:341`).
- [ ] Проход по всем материалам не делает более N запросов в минуту к одному хосту.
- [ ] Мёртвая ссылка остаётся в базе и продолжает перепроверяться; из ответа API она
      не пропадает.
- [ ] Задача не запускается при `SCHEDULER_ENABLED=0`; ручной запуск через `/trigger` работает
      и попадает в журнал прогонов.
- [ ] Материал, который сегодня показывается кандидату, при `alive=false` не попадает
      в текст кандидату (BE-09).

**Приоритет.** P2.

**Риски.** Ложное «недоступна» хуже отсутствия проверки: рекрутёр перестанет отправлять
рабочую ссылку. Отсюда правило двух неудач подряд и мягкие пороги таймаута. Второй риск —
конкуренция с индексацией диска: обе подсистемы ходят на один хост, и агрессивная проверка
живости может привести к 429 на обходе базы знаний, то есть сломать источник справок
для LLM. Ограничение темпа обязательно, а интервалы двух задач не должны совпадать.
