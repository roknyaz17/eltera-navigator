# Telegram-робот: сообщения контрагентам

> **Состояние: не реализовано.** Ни одного исходящего сообщения в коде нет. Есть только
> подготовка: текст запроса формируется, шаблон и список пробелов доезжают до интерфейса,
> но кнопка отправки показывает тост-заглушку. Нет модуля `registry/outreach.py`, таблиц
> переписки, вебхука, учёта попыток и приветствий.

## Что уже есть

| Элемент | Где | Что делает |
|---|---|---|
| Список обязательных полей | `navigator_api.py`, `REQUIRED_FIELDS` | шесть полей: гражданство, проживание, питание, ставка кандидата, график, потребность |
| Шаблон первой строки запроса | `navigator_api.py`, `DEFAULT_TEMPLATE` | «Уточните, пожалуйста, по вакансиям ниже…» — настраивается только просьба, список позиций и вопросы собираются из самих заявок |
| Признак готовности к отправке | `navigator_api.py`, `outreachEnabled` | `true`, если задан `TELEGRAM_BOT_TOKEN` |
| Сборка пробелов по позиции | `navigator_api.py` | какие обязательные поля пусты |
| Экран «Админ» в подборе | `templates/navigator.html` | показывает текст запроса и кнопку отправки |

То есть черновик сообщения система уже умеет составить. Отправить — нет.

## Чего нет

- модуля `registry/outreach.py` и вообще любого вызова Bot API;
- таблиц `outreach_threads`, `outreach_messages`, `outreach_questions`;
- фонового процесса рассылки (в `JOBS` четыре задачи, все — чтение источников);
- роута приёма ответов `POST /webhook/telegram/{secret_path}`;
- учёта попыток, приветствия раз в день, правила «не переспрашивать»;
- хранилища настроек контрагента: чата, темы, времени отправки, шаблона.

`TELEGRAM_BOT_TOKEN` в коде читается ровно один раз — чтобы понять, показывать ли кнопку.
Сообщения им не отправляются.

## Зачем робот нужен

Заявки приходят неполными: нет графика, не указано гражданство, ставка написана вместе
с условиями стажировки. Рекрутер идёт в чат и спрашивает руками — или, что хуже, система
достраивает недостающее правилом, и отличить догадку от факта становится невозможно.

Робот закрывает этот разрыв: собирает пробелы по всем заявкам контрагента, задаёт их
одним сообщением, получает ответ и записывает значение в поле с пометкой «источник —
переписка». Человек подключается, только когда автоматика не справилась.

## Правила общения

Семь правил. Каждое существует, чтобы полезный механизм не превратился в спам, после
которого контрагент выкинет бота из чата.

### 1. Одно сообщение на контрагента в сутки

Не на заявку — **на контрагента**. Все его заявки с пробелами и все вопросы собираются
в один текст. У контрагента с двадцатью объектами это разница между одним сообщением
и двадцатью.

### 2. Формат сообщения

```
Добрый день! Просьба дополнить информацию по следующим заявкам:

«Грузчик на склад» (№ МС-77) — отсутствуют: график, питание.
«Комплектовщик» — отсутствуют: возраст, гражданство.

«Комплектовщик СПК»: какая ставка за смену действует после стажировки
и сколько смен она длится?
```

Сначала блок «чего не хватает» по каждой заявке, затем блок конкретных вопросов.
Заявка называется **так, как её называет контрагент**. Внутренние ID и названия в текст
не попадают никогда — см. [NAMING.md](NAMING.md).

### 3. Приветствие — один раз в день на чат

Не на заявку и не на сообщение. Последующие сообщения в тот же день идут без «Добрый
день». Хранится как дата последнего приветствия в диалоге.

### 4. Не переспрашивать

Вопрос, уже отправленный и ожидающий ответа, в следующее сообщение не включается.
Новые вопросы уходят догоняющим сообщением — без приветствия и без повторения старых.

Это единственное, что отличает робота от автоответчика: контрагент, ответивший вчера
на половину вопросов, не должен получить сегодня тот же список целиком.

### 5. Не додумывать

Робот задаёт конкретный вопрос и ждёт ответа. Значения **не подставляются** по прошлым
заявкам этого контрагента, по соседним позициям того же объекта или по «обычно бывает
так». Непонятно — переспросить, а не угадать.

### 6. Разбор ответа

- однозначный ответ → значение в поле, статус «заполнено», источник — переписка,
  вопрос закрывается;
- неполный или неоднозначный → уточняющий вопрос;
- не соотнесённый ни с одним открытым вопросом → в исключения администратору,
  а не в тишину.

### 7. Лимит попыток

Повтор раз в сутки, максимум `MAX_OUTREACH_TRIES` (по умолчанию 3). Дальше диалог
переходит в состояние «исчерпан» и попадает в очередь исключений: «контрагент молчит,
автоповторы исчерпаны».

После заполнения данных заявка сама исчезает из следующего сообщения — снимать её
с вопроса отдельно не нужно.

### Недоставленное сообщение

Бот удалён из чата, нет прав на запись, чат не существует — диалог помечается
недоставляемым, администратор получает уведомление, повторные попытки прекращаются
до вмешательства человека.

## Модель данных

Три таблицы, ни одной из них в схеме нет:

| Таблица | За что отвечает |
|---|---|
| `outreach_threads` | диалог с контрагентом в конкретном чате: дата приветствия, номер попытки, состояние (`open` / `answered` / `exhausted` / `undeliverable`) |
| `outreach_messages` | отправленные сообщения: текст, `tg_message_id`, признак доставки, ошибка, вид (`daily` / `follow_up` / `clarify`) |
| `outreach_questions` | вопрос по конкретному полю конкретной позиции: состояние, сырой ответ |

`outreach_questions` — источник правила «не переспрашивать». Ограничение
`UNIQUE (position_id, field, state)` не даёт завести второй открытый вопрос по тому же
полю.

## Настройки контрагента

Всё, что нужно роботу, задаётся в админ-панели и живёт в базе, а не в коде: имя бота,
**ссылка на секрет** с токеном (не сам токен), `chat_id`, `message_thread_id` для
форумных чатов, время ежедневной отправки, шаблон сообщения, набор обязательных полей
для этого контрагента, состояние последней доставки.

> Токен бота в базе не хранится и в выгрузки не попадает. В базе лежит идентификатор
> секрета, сам секрет — в переменных окружения или секрет-хранилище платформы.

Проверка настроек — две кнопки: «Проверить подключение» (бот состоит в чате, есть право
писать) и «Отправить тестовое сообщение».

## Фоновый процесс

`outreach_dispatch` — проверка ежеминутно, отправка во время, заданное контрагентом,
с учётом его часового пояса.

1. Собрать контрагентов, у которых наступило время отправки и есть открытые пробелы.
2. Для каждого — собрать позиции с проблемами `missing`, `format`, `unparsed`
   (см. [VALIDATION.md](VALIDATION.md)).
3. Отфильтровать поля, по которым уже есть открытый вопрос.
4. Если после фильтра ничего не осталось — сообщение не отправляется.
5. Собрать текст по шаблону; приветствие — только если сегодня ещё не здоровались.
6. Отправить через Bot API, записать сообщение и `tg_message_id`.
7. Завести вопросы в состоянии «ожидает ответа» по каждому включённому полю.
8. Увеличить счётчик попыток; при превышении лимита — исключение администратору.

## Приём ответов

Вебхук `POST /webhook/telegram/{secret_path}`.

Сообщение сопоставляется с диалогом по `chat_id` и `message_thread_id`, затем разбирается
на ответы по открытым вопросам этого диалога.

Требования:

- секретный путь плюс проверка заголовка `X-Telegram-Bot-Api-Secret-Token`;
- идемпотентность по `update_id` — Telegram повторяет доставку;
- ответ 200 всегда и быстро, обработка асинхронно; ошибка обработки не должна приводить
  к бесконечным ретраям Telegram;
- сообщение, не соотнесённое ни с одним диалогом, логируется и уходит в исключения.

## Почему нужен отдельный бот, а не текущий userbot

Сейчас чтение работает через Telethon от лица живого аккаунта. Для исходящих это
не годится:

- сообщения от личного аккаунта неотличимы от сообщений сотрудника — контрагент будет
  отвечать человеку, а не роботу;
- у userbot нет вебхука: придётся держать постоянное соединение и самим разбирать
  апдейты;
- аккаунт можно потерять целиком (блокировка за рассылку) — вместе с чтением заявок;
- права в чате не разграничиваются: userbot видит всё, что видит человек.

Чтение остаётся на userbot, отправка и приём ответов — отдельный бот через Bot API.
Это два разных транспорта, и их состояние не должно быть связано.

## Риски и меры

| Риск | Мера |
|---|---|
| Спам контрагенту | одно сообщение в сутки, приветствие раз в день, вопросы не повторяются, максимум 3 попытки |
| Двойной запуск планировщика → задвоенная рассылка | планировщик ровно на одном инстансе плюс блокировка прогона в базе |
| Утечка внутренних данных в переписку | в текст идут только внешние названия; тест «в сообщении нет `position_id`» |
| Бесконечный цикл «вопрос — непонятный ответ — вопрос» | лимит уточнений на один вопрос, дальше человеку |
| Ответ разобран неверно и записан в поле | источник значения фиксируется, правка видна в истории |
| Часовые пояса | время отправки хранится строкой вместе с зоной контрагента |

## Что проверять тестами

- у контрагента с тремя проблемными заявками получается **одно** сообщение;
- второе сообщение в тот же день идёт без приветствия;
- поле с открытым вопросом не попадает в новое сообщение;
- после третьей попытки диалог исчерпан, отправка прекращается;
- после ответа заявка исчезает из следующего сообщения;
- ошибка Bot API переводит диалог в недоставляемый и создаёт исключение;
- в тексте сообщения нет `position_id`, `request_id` и внутреннего названия должности.

Задачи — раздел «Telegram» в [../DEVELOPER_TASKS.md](../DEVELOPER_TASKS.md).

## Требует согласования

Согласны ли контрагенты на автоматические сообщения и включать ли их по одному;
нужен ли на первом этапе режим «черновик» (текст формирует система, отправляет человек
кнопкой); где хранятся токены ботов. Вынесено в [OPEN-QUESTIONS.md](OPEN-QUESTIONS.md).
