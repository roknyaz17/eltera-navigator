# Автоматическая проверка недостающих данных

> **Состояние: реализовано наполовину.** Система различает «не указано» и «нет», считает
> пробелы и показывает их рекрутеру. Чего нет: хранения статуса поля в базе, настройки
> обязательности на контрагента, очереди исключений и любого исходящего запроса
> заказчику. Модуля `registry/validate.py` не существует.

## Принцип

**Пустое поле означает, что этого не было в заявке.** Модели запрещено достраивать
данные: нет упоминания смены — колонка «Смена» пустая, нет региона — пустой регион.

Раньше часть полей заполнялась правилом-догадкой («вахта → есть питание», «пищевое
производство → нужна медкнижка», смена по умолчанию «день», регион по городу).
Отличить догадку от факта было невозможно. Правила удалены, следы вычищены скриптом
`scripts/clear_legacy_guesses.py` — но только там, где подтверждения в исходном тексте
нет; стёртые значения остались видны в истории изменений позиции.

Отсюда следует всё остальное: если система честно не знает, она может спросить.

## Три состояния значения, которые уже работают

`navigator_api.py` собирает каждый блок карточки (проживание, питание, проезд,
удержания, медкнижка, проверка СБ) не как строку, а как объект с полем `st`:

| Значение `st` | Что означает | Как показывается |
|---|---|---|
| `ok` | значение пришло из заявки | сама величина |
| `no` | источник прямо сказал «нет» | «нет» |
| `na` | в заявке не указано | «не указано», нейтрально |

Это ключевое отличие от прежнего контура: `NULL` доезжает до интерфейса как `na`,
а не превращается в `0`, «нет» или «бесплатно». В `registry/normalize.py` за это отвечает
`to_bool()`, возвращающий `None`, когда в тексте про признак ничего не сказано,
и `_need_total()`, который не складывает неизвестные слагаемые в ноль.

Целевая модель добавляет к этим трём ещё четыре состояния — `default`, `conflict`,
`needs_clarification`, `n_a`. Их нет: хранить статус поля негде, таблицы `field_status`
в схеме не существует.

## Два независимых списка обязательных полей

Это реальная коллизия в коде, о которой нужно знать:

| Где | Константа | Состав | Для чего используется |
|---|---|---|---|
| `navigator_api.py` | `REQUIRED_FIELDS` | гражданство, проживание, питание, ставка кандидата, график, потребность | пробелы в карточке подбора и текст запроса заказчику |
| `registry/queries.py` | `KEY_FIELDS` | должность, город, ставка за смену, потребность, график, контрагент | фильтр «есть незаполненные поля» в реестре и метрика заполненности |

Пересечение — три поля из шести. Один и тот же пробел в реестре и в подборе считается
по-разному, и это выглядит как ошибка данных. Списки нужно свести — либо к одному
источнику, либо к явно разным понятиям с разными названиями на экране.

Оба списка зашиты в код. Целевая модель делает обязательность **настройкой контрагента**
(`counterparty_settings.required_fields`): смена набора не должна требовать релиза.

## Типы проблем

`templates/navigator.html` объявляет шесть видов (`ISSUE_KINDS`) с уровнем важности
и цветом точки:

| Код | Подпись на экране | Уровень | Цвет | Порождается кодом? |
|---|---|---|---|---|
| `conflict` | Обнаружена несостыковка | 1 | `#FF7B6B` | да, из `conflicts` в ответе API |
| `duplicate` | Возможный дубль | 1 | `#FF7B6B` | да, из `dupes` в ответе API |
| `missing` | Не хватает данных | 2 | `#D9A441` | да, по `REQUIRED_FIELDS` |
| `format` | Требует внимания | 2 | `#D9A441` | **нет** — вид объявлен, ветки нет |
| `unparsed` | Требует внимания | 2 | `#D9A441` | **нет** |
| `source` | Ошибка источника | 3 | `#D9A441` | **нет** |

Деление принципиальное: `missing`, `format` и `unparsed` система умеет закрыть, спросив
контрагента. `conflict`, `duplicate` и `source` требуют решения человека — их нельзя
ни спросить, ни угадать.

> **Разные контрагенты с одинаковой должностью — не дубль.** Контрагент и вакансия —
> разные сущности, это две независимые позиции. Дубль — одна и та же позиция, пришедшая
> дважды.

## Что уже работает

| Механизм | Где | Что делает |
|---|---|---|
| `NULL` ≠ `0` ≠ «нет» | `registry/normalize.py`, `to_bool()` | «в заявке не сказано» приходит как `None` |
| `need_total` по известным частям | `Normalizer._need_total` | три пустых слагаемых не дают ноль |
| Регион только из подтверждённого справочника | `registry/normalize.py` | `city_region`, и только `confirmed = 1` |
| Очередь подтверждения справочников | `dictionaries`, `/registry/dictionaries` | незнакомый вариант написания ждёт человека, а не склеивается молча |
| Пробелы в карточке подбора | `navigator_api.py`, `templates/navigator.html` | счётчик «Требуют решения» и модалка со списком |
| Фильтр «есть незаполненные поля» | `registry/queries.py`, `has_gaps` | по `KEY_FIELDS` |
| Метрика заполненности | `fill_ratio()`, `/metrics` | доля активных позиций с пустым ключевым полем |
| Флаг неразобранной заявки | `needs_review`, `requests.parse_status` | заявка, на которой упал разбор |
| Сверка «как пришло / как распозналось» | `templates/registry_position.html` | рядом с каноном видно исходную формулировку |

Этого достаточно, чтобы человек **увидел** пробел. Недостаточно, чтобы система **сама**
решила, что с ним делать, и тем более чтобы спросила заказчика.

## Чего нет

- **`registry/validate.py`** — отдельного слоя проверки не существует; пробелы считаются
  прямо при сборке ответа API.
- **Хранения статуса поля.** `field_status` и `field_conflicts` в схеме нет, поэтому
  нельзя ни пометить «спросили, ждём ответа», ни отличить «неприменимо» от «неизвестно»,
  ни защитить решение человека от перезаписи импортом.
- **Обязательности на контрагента** — только две константы в коде.
- **Ветвей `format`, `unparsed`, `source`** — виды объявлены, ни одна не порождается.
- **Очереди исключений администратора** — экрана нет.
- **Любого исходящего запроса заказчику** — кнопки в интерфейсе показывают тост-заглушку.
  См. [OUTREACH-BOT.md](OUTREACH-BOT.md).
- **Проверки живости ссылок на материалы** — признак `alive` захардкожен.

## Как это должно работать вместе

```
приём данных
   ↓
нормализация (справочники, *_raw рядом с каноном)
   ↓
registry.validate — обязательность по контрагенту, статусы полей, список проблем
   ↓
├─ проблем нет                 → позиция публикуется автоматически
├─ missing / format / unparsed → registry.outreach ставит вопросы в очередь контрагенту
└─ conflict / duplicate / source → очередь исключений администратора
```

Пересчёт — после каждого приёма, только по изменённым позициям.

**Заявка без проблем в очереди не появляется.** Администратор видит не всё подряд,
а только то, что автоматика закрыть не может. Технические детали распознавания ему
не показываются — сверка «как пришло / как распозналось» доступна в карточке позиции.

## Два счётчика с похожими названиями

Счётчик пробелов в подборе и очередь исключений в админке считают **разное**: первый —
все проблемы позиции, вторая — только требующие человека. Цифры не сойдутся, и это будет
выглядеть багом. Названия обязаны различаться: предложение — «Неполные данные»
в подборе и «Требуют решения» в админке.

## Что проверять тестами

- обязательные поля берутся из настроек контрагента, а не из константы;
- пустое необязательное поле не создаёт проблему;
- `na` и `no` различимы в API и в интерфейсе;
- импорт не перезаписывает решения человека;
- расхождение источников порождает `conflict`, а не молчаливую перезапись;
- позиция без проблем не появляется в очереди администратора.

Соответствующие задачи — `BE-*` и `QA-*` в [../DEVELOPER_TASKS.md](../DEVELOPER_TASKS.md).
