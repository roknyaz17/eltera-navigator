# Логика админ-панели

Что сегодня выполняет роль администрирования и что должно появиться, если делать админ-панель по макету заказчика `navigator/navigator.html`. Разделы «как есть» и «как должно быть» разведены намеренно: значительная часть нарисованного в макете в коде отсутствует.

---

## 0. Главное: единой админ-панели нет

Роута `/admin` в приложении нет. Полный список объявленных эндпоинтов: `app.py:211`, `:279`, `:314`, `:328`, `:341`, `:356`, `:366`, `:378`, `:400`, `:441`, `:524`, `:601`, `:667`, `:689`, `:730`, `:755`, `:767`, `:779`, `:789`, `:796`, `:850`, `:883`, `:908`, `:1089` — ни `/admin`, ни `/admin/*` среди них нет. Функции администратора размазаны по семи точкам:

| Функция | Точка входа | Файл |
|---|---|---|
| Просмотр и правка реестра | `GET /registry`, `POST /registry/position/{id}` | `app.py:601`, `app.py:883` |
| Очередь унификации написаний | `GET/POST /registry/dictionaries*` | `app.py:730`, `:755`, `:767`, `:779` |

Плюс экран «Админ» внутри витрины `/navigator` (`app.py:366`) — не отдельный роут, а вторая вкладка того же одностраничного шаблона `templates/navigator.html:1230`.

## 1. Как есть — авторизация

Одна общая пара HTTP Basic из `WEB_USER` / `WEB_PASSWORD` (`app.py:192-193`), проверка — `verify_creds` (`app.py:191-207`), сравнение через `secrets.compare_digest` отдельно по логину и паролю (`app.py:199-200`).

- **Ролей нет.** Любой прошедший Basic получает и чтение, и запись: правила ставок (`app.py:400`), подтверждение справочников (`app.py:755`), ручной ввод заявок (`app.py:796`), запуск прогонов (`app.py:328`, `:341`). Разделения «рекрутёр / руководитель / администратор» в коде не существует.
- **Три роута открыты без авторизации**: `GET /health` (`app.py:211`), `GET /metrics` (`app.py:279`), `GET /jobs` (`app.py:314`), плюс mount `/static` (`app.py:184`). Состав задач планировщика и все метрики (включая число позиций по источникам) доступны любому, кто дотянулся до порта.
- **Пустые переменные дают 500, а не 401** (`app.py:194-198`): при незаполненном `.env` ответ — «WEB_USER / WEB_PASSWORD не настроены в .env», статус 500.
- Имя пользователя из Basic — единственный след авторства: оно уезжает в `author` правил ставок (`app.py:434-435`, `:447`) и в `raw_payload.entered_by` ручной заявки (`app.py:823`). Таблицы пользователей нет.

CORS-middleware, CSRF-защиты, rate-limit и security-заголовков нет: middleware не зарегистрировано ни одного, кроме `StaticFiles` (`app.py:184`).

## 2. Как есть — функции по одной

### 2.1 `GET /registry` — реестр заявок

`app.py:601-664`, шаблон `templates/registry.html`. Фильтры собирает `_registry_filters` (`app.py:557-592`): `q`, `source`, `counterparty`, `city`, `region`, `vacancy_name`, `shift_type`, `sb_policy`, `status`, `rate_min`, `rate_max`, `max_shifts`, `age`, `date_from`, `date_to`, `has_gaps`, `needs_review`, `is_active`. SQL — `registry/queries.py:48-122`, полнотекст через FTS5 `search_index` (`registry/queries.py:112-120`). Сортировка ограничена белым списком из 20 колонок (`registry/queries.py:14-19`), NULL всегда уезжает в конец (`:158`), `per_page` зажимается в 1..500 (`app.py:621`, повторно `registry/queries.py:146`).

Рядом: `GET /api/registry` — тот же срез в JSON, `per_page` по умолчанию 100 (`app.py:667-686`); `GET /registry/export.csv` — выгрузка с `;`, BOM и русскими подписями из `registry/labels.py`, потолок 20 000 строк (`app.py:689-727`).

Ограничение: фильтры `work_format` и `gender` реализованы в SQL (`registry/queries.py:63-64`), но `_registry_filters` их не собирает (`app.py:573-592`) — снаружи они недостижимы.

### 2.2 `GET/POST /registry/position/{id}` — карточка позиции

Чтение — `app.py:850-880`: значения всех `DATA_FIELDS`, счётчик заполненных полей, группы `registry/labels.py:76-91`, история изменений (`registry/queries.py:223`).

Запись — `app.py:883-905`. **Сохраняются ровно пять полей**: `status`, `priority`, `responsible_manager`, `recruiter_comment`, `market_rate`. Последнее парсится как `int`, при ошибке молча становится `None` (`app.py:893-896`). Дальше `rq.update_manager_fields` (`registry/queries.py:241-254`) пропускает только ключи из `MANAGER_FIELDS` (`registry/models.py:94-106`) — приём данных эти поля не трогает никогда. Ответ — редирект 303 на `/registry`, без возврата на карточку. Остальные 53 поля позиции (`registry/models.py:109`) из интерфейса не редактируются: их единственный источник — разбор заявки.

### 2.3 `GET/POST /registry/manual` — ручной ввод

`app.py:789-847`. Форма: `counterparty` (обяз.), `text` (обяз.), `channel`. Собирается `RawRequest` с `source=SOURCE_MANUAL`, `source_name` = «Вручную (channel)» либо «Вручную», `raw_payload={"channel", "entered_by": user}`, `field_defaults={"counterparty": …}` (`app.py:812-824`). `source_ref = f"manual:{content_hash[:16]}"` (`app.py:826`) — дедуп по содержимому: повторная отправка того же текста вторую заявку не заведёт.

Приём — `RegistryIngestor(VacancyParserService()).ingest(SOURCE_MANUAL, [raw], snapshot=False)` (`app.py:829-832`). `snapshot=False` принципиально: иначе одна ручная заявка погасила бы все остальные ручные позиции (`registry/ingest.py:398-399`). Любое исключение превращается в текст ошибки на той же странице со статусом 200 (`app.py:844-847`), а не в 500.

### 2.4 `GET /jobs`, `POST /trigger/{name}`, `POST /run` — управление прогонами

- `GET /jobs` (`app.py:314-325`) — `{"jobs": [{id, name, next_run_time}]}`. **Без авторизации.**
- `POST /trigger/{name}` (`app.py:328-338`) — Basic. `name` сверяется со словарём `JOBS` (`app.py:84-109`), неизвестное → 404 со списком допустимых; запуск фоновой задачей `background.add_task(_job_wrapper, name, cfg["sources"], cfg["reset"])`. Тела запроса нет.
- `POST /run` (`app.py:341-353`) — Basic. Query `sources` (через запятую, пусто → все) и `reset: bool = False`; разбор `pipeline.parse_sources` (`pipeline.py:122-134`), неизвестный источник → 400.

Четыре задачи, все `Europe/Moscow` (`app.py:85-108`): `morning_telegram` 09:30 (`vahtapro`+`aaaplus`, reset), `noon_tables` 12:00 (`kpk`+`yappi`+`marketstaff`, reset), `afternoon_vahtapro` 13:00 (без reset), `afternoon_ametist` 13:30 (без reset). Флага включения планировщика (`SCHEDULER_ENABLED` и подобных) в коде нет — он стартует в `lifespan` безусловно (`app.py:170-171`) и живёт **внутри процесса приложения**: при нескольких воркерах uvicorn задачи продублируются, внешнего лока нет. Обратной связи по прогону в HTTP тоже нет: `_job_wrapper` (`app.py:144-152`) ловит исключение в лог, наружу уходит только `{"status": "started"}`.

### 2.6 Наблюдаемость: `/health`, `/metrics`

Формально это не админ-панель, но сегодня это единственный способ увидеть состояние системы.

- `GET /health` (`app.py:211-217`) — `{"status": "ok", "scheduler_running": …, "jobs": [id, …]}`. БД и Google Sheets не проверяет: пока процесс жив, ответ всегда `ok`. На этот же роут завязан `HEALTHCHECK` контейнера (`Dockerfile:29-30`).
- `GET /metrics` (`app.py:279-292`) — Prometheus, префикс `eltrea_`. Перед отдачей пересчитываются снапшот-гейджи `_refresh_snapshot_metrics` (`app.py:220-276`) и, при `REGISTRY_ENABLED`, реестровые `_refresh_registry_metrics` (`app.py:295-311`); обе обёрнуты в try/except — при сбое метрики всё равно отдаются.

Административно полезные метрики (`metrics.py:137-165`): `eltrea_registry_positions{source,is_active}`, `eltrea_registry_requests_total{source,kind}` с `kind = new|changed|unchanged|failed`, `eltrea_registry_empty_field_ratio{field}` (доля активных позиций с пустым ключевым полем, считается по `KEY_FIELDS` — `registry/queries.py:25-27`), `eltrea_registry_dictionary_pending{kind}` (та самая очередь из 4.1), `eltrea_registry_llm_calls_saved_total{source}`. Плюс расход модели: `eltrea_llm_tokens_total{source,type}` и `eltrea_llm_cost_rub_total{source}` (`metrics.py:118-134`). Смотрят на них через Prometheus + Grafana из `docker-compose.yml` (скрейп `app:8000/metrics` каждые 15 с).

## 3. Как должно быть — целевая админ-панель по макету

Источник постановки — `navigator/navigator.html` (2538 строк), пакет заказчика в каталоге `navigator/`. Приложение о нём не знает: ни mount, ни роута, ни ссылки из шаблонов; рабочий экран `/navigator` читает `templates/navigator.html` (`app.py:373-375`). Пакет исполняется рантаймом `navigator/support.js`, который тянет React 18 и Babel с `unpkg.com` (`navigator/support.js:1071-1076`) — без интернета страница пустая. Всё ниже — постановка, а не описание работающего.

### 3.1 Вход по паролю

**В макете.** Модалка «Вход в админ-панель» (`navigator/navigator.html:941-960`): поле пароля, Enter = вход, ошибка «Неверный пароль», подпись «Спросим один раз на этом устройстве». `_submitAuth()` (`:1710-1715`) сверяет строку с `ADMIN_PASS = '1207'` (`:1697`) и пишет `'ok'` в `localStorage` под ключом `eltera_navigator_admin_v1` (`:1698`). Тем же паролем подтверждается удаление контрагента (`_cpConfirmDelete`, `:1781-1794`).

**Почему прототипный вариант переносить нельзя** — четыре независимые причины:

1. Пароль лежит в клиентском коде открытым текстом (`navigator/navigator.html:1697`) и виден в исходнике страницы любому, кто её открыл. То же с демо-учёткой экрана входа: `anna.kuznetsova@romashka.ru` / `eltera2026` в `navigator/eltera/account.js:15-16`.
2. Флаг доступа хранится в `localStorage` без срока действия и без подписи — подделывается одной строкой из консоли.
3. Сравнение выполняется в браузере, то есть проверки как таковой нет: её можно обойти, минуя форму.
4. Экран `navigator.html` в макете не подключает `eltera/account.js` и не проверяет сессию — прямой переход по URL открывает весь интерфейс; кнопки выхода в пакете нет.

**Что должно быть вместо.** Проверка на сервере. Минимальный вариант, совместимый с текущим кодом: отдельный роут админки под тем же `Depends(verify_creds)` (`app.py:191`) плюс вторая пара учётных данных. Полный вариант требует таблиц пользователей и сессий — их в схеме нет (`registry/db.py:39-362`). Ориентиры из `navigator/.env.example` (`ADMIN_PASSWORD_HASH`, `ADMIN_SESSION_DAYS`, `ADMIN_MAX_ATTEMPTS`, `SECRET_KEY`) брать как спецификацию нельзя: файл описывает Flask-стек, которого в проекте нет — реально читаются `WEB_USER`/`WEB_PASSWORD` (`app.py:192-193`), `REGISTRY_DB_PATH` (`registry/db.py:25`), `OPENAI_API_KEY` (`vacancy_parser.py:208`), а путь к `credentials.json` вообще захардкожен (`app.py:113`).

### 3.2 Панель автопроверки с KPI

**В макете** (`navigator/navigator.html:488-511`) — четыре плитки (`:2424-2429`): «принято автоматически» (позиции без проблем, точка `#6EE7C1`), «запросов заказчикам» (`#16D7FF`), «ссылок перепроверяется» (`#A4F4FD`), «исключений для вас» (`#FF7B6B`, зелёная при нуле). Ниже — «Запросы уходят ежедневно в 09:00» (`SEND_TIME`, `:1352`), «следующая рассылка завтра в 09:00 · сегодня отправлено N» (`:2431`) и кнопка «Отправить сейчас».

**Что под этим есть.** Первый KPI считается из `issues()` и работоспособен. Остальные три — нет: рассылки не существует (см. 2.6), а «ссылок перепроверяется» опирается на проверку живости ссылок, которой в коде нет вовсе — `alive: True` проставляется константой (`navigator_api.py:341`), задачи «перепроверить ссылки» в `JOBS` (`app.py:84-109`) нет, строка «перепроверка каждые 6 часов» в рабочем шаблоне — литерал (`templates/navigator.html:814`).

Реализуемо без новых сущностей: «позиций с пробелами по `REQUIRED_FIELDS`» (`navigator_api.py:33-40`), «заявок с `parse_status != 'ok'`» (`registry/queries.py:109-110`), «вариантов написания в очереди подтверждения» (`registry/dictionaries.py:179-183`) — последнее уже отдаётся метрикой `eltrea_registry_dictionary_pending{kind}` (`metrics.py:137-165`).

### 3.3 Вкладка «Исключения»

**В макете** (`:542-586`) карточка несёт статус-пилюлю с цветной точкой, заголовок, место, наш id, описание проблемы, кнопки-значения при конфликте (значение + источник), строку рекомендации и действия: «Открыть обе заявки» / «Уточнить в чате», при дубле дополнительно «Объединить» и «Разные позиции», всегда «Отложить на сутки». Источников очереди три (`:2223-2265`): проблемы позиций (`conflict`, `duplicate`), «мёртвые» запросы заказчикам, источники со `status === 'error'`.

**Что есть.** Первый источник считается: `find_dupes` (`navigator_api.py:466-510`; дубли ищутся только между разными источниками, ключ `cp|city|prof|obj|shiftType`) и конфликты по `CONFLICT_FIELDS` = rate/sched/citsRaw/gender (`navigator_api.py:458-463`). Второго нет — переписки нет. Третий частично: `sources_block` (`navigator_api.py:515-552`) отдаёт `status: ok|error`.

**Чего не хватает.** «Объединить» и «Разные позиции» требуют хранимого решения оператора по паре позиций — таблицы под это нет; сегодня «исправлено» живёт в памяти вкладки (`templates/navigator.html:426-433`). «Отложить на сутки» требует поля со сроком возврата — его тоже нет. Виды проблем `format` и `unparsed` объявлены в `ISSUE_KINDS` (`templates/navigator.html:142-143`), но ни один код-путь их не создаёт.

### 3.4 Вкладка «Запросы»

**В макете** (`:588-629`) — карточка на контрагента: статус («Ждём ответа» / «Нет ответа N дн.» / «Не доставлено»), адрес чата и тема, список позиций, готовый текст сообщения, блок «уже в запросе, повторно не спрашиваем», отдельный блок догоняющего сообщения без приветствия, мета «отправлено … · попытка N из 3 · следующий повтор завтра в HH:MM», кнопки «Открыть чат» и «Отправить повторно». ## 4. Что уже работает — подробно

### 4.1 Справочники унификации: очередь подтверждения

Задача: свести разные написания одного и того же («КПК», «кнк», «КНК») к одному каноническому значению, ничего не склеивая молча.

**Таблица** `dictionaries` (`registry/db.py:147-157`): `kind`, `alias`, `canonical`, `confirmed INTEGER NOT NULL DEFAULT 0`, `hits`, `note`, `created_at`, `updated_at`, `PRIMARY KEY (kind, alias)`. Индексы `idx_dict_kind_confirmed(kind, confirmed)` и `idx_dict_canonical(kind, canonical)` (`registry/db.py:159-160`). Девять видов (`registry/dictionaries.py:17-25`): `job_title`, `city`, `city_region`, `region`, `counterparty`, `work_format`, `vacancy_category`, `schedule_pattern`, `citizenship`; человеческие названия — `KIND_TITLES` (`:39-49`).

**Как вариант попадает в очередь.** Ключ нормализуется `norm_key` (`registry/dictionaries.py:52-63`: lower, ё→е, всё кроме `\w\s/+-` → пробел, схлопывание пробелов). При нормализации позиции `Normalizer._lookup` (`registry/normalize.py:372-392`) ищет канон: нашёл → возвращает канон и делает `record_seen`; **не нашёл → возвращает значение как есть и всё равно зовёт `record_seen`** (`registry/normalize.py:389-391`). Сам `record_seen` (`registry/dictionaries.py:113-132`) вставляет строку с `confirmed = 0, hits = 1`, а при повторе делает `hits = hits + 1`.

Это и есть очередь: `confirmed = 0` означает «встречено, но человеком не подтверждено». Пока вариант не подтверждён, в реестре он показывается как есть — автосклеивания нет. Причина зафиксирована в докстринге: «Комплектовщик СПК» и «Комплектовщик» могут быть разными позициями с разной ставкой (`registry/normalize.py:375-377`).

**Чтение.** `load(conn, kind, include_pending=False)` (`registry/dictionaries.py:70-75`) по умолчанию отдаёт только `confirmed = 1` — на нормализацию влияют исключительно подтверждённые записи. `pending` (`:167-176`) сортирует `ORDER BY hits DESC, alias ASC`: сверху то, что встречается чаще. `pending_counts` (`:179-183`) даёт счётчики по видам — они же идут в бейджи вкладок и в метрику `eltrea_registry_dictionary_pending{kind}`.

**Интерфейс.** `GET /registry/dictionaries?kind=…` (`app.py:730-752`), шаблон `templates/registry_dictionaries.html`: вкладки по видам с бейджем количества (`:29-40`), кнопка массового подтверждения раздела (`:42-49`), таблица «Как встречается / Каноническое значение / Встреч / Статус» (`:51-60`). Формы вынесены за пределы `<tr>` намеренно (`:62`). Три POST-роута, все отвечают редиректом 303 на ту же вкладку:

| Роут | Форма | Действие |
|---|---|---|
| `/registry/dictionaries/confirm` (`app.py:755-764`) | `kind`, `alias`, `canonical` | `confirm` (`registry/dictionaries.py:135-143`): `confirmed = 1`, и если канон передан непустым — заодно переписывает `canonical` |
| `/registry/dictionaries/confirm-all` (`app.py:779-786`) | `kind` | `confirm_all` (`:146-158`): `UPDATE … SET confirmed = 1 WHERE kind = ? AND confirmed = 0`, возвращает `rowcount` |
| `/registry/dictionaries/delete` (`app.py:767-776`) | `kind`, `alias`, `canonical` | `remove` (`:161-164`): `DELETE`. Поле `canonical` формой принимается, но не используется |

Важная деталь `upsert` (`registry/dictionaries.py:82-110`): `confirmed` берётся как `MAX(dictionaries.confirmed, excluded.confirmed)` — подтверждённая запись никогда не сбрасывается обратно в очередь повторной встречей варианта.

**Чего очередь не делает.** Подтверждение не пересчитывает уже лежащие в базе позиции: для этого есть отдельный ручной скрипт `scripts/renormalize.py` (покрыт `tests/test_renormalize.py` — 4 теста, включая dry-run и неприкосновенность менеджерских полей). После миграции v6 (КПК → КНК, `registry/db.py:341-362`) прогон этого скрипта тоже обязателен вручную: `fingerprint` считается в том числе по контрагенту (`registry/db.py:339-340`, `registry/normalize.py:497-510`).

### 4.2 Правила ставки рекрутера

Слой, который не приходит из заявок и прийти не может: контрагент присылает сетку картинкой раз в неделю (`registry/rates.py:1-22`). Заполняется руками — из вкладки «Ставки» или из CLI `scripts/recruiter_rates.py`.

**Две таблицы** (миграция v5, `registry/db.py:270-327`):

- `recruiter_rate_rules` (`:271-287`): `id`, `source`, `client` (пусто = все объекты), `vacancy` (пусто = все должности), `min_shifts` (0 = без условия), `amount`, `note`, `payout`, `valid_from`, `valid_to`, `created_at`, `author`. Ключевое — **`UNIQUE (source, client, vacancy, min_shifts)`** (`:284`): на неё опирается `ON CONFLICT` при сохранении.
- `recruiter_rate_history` (`:291-307`): те же поля плюс `action` (`set` | `delete`), `changed_at`, `author`; индекс `idx_rate_history_scope(source, client, vacancy)` (`:307`).

Прежняя таблица `recruiter_rates` (одна ставка на контрагента, миграция v2, `registry/db.py:184-196`) удалена в v5 после переноса данных (`:311-326`); процентные ставки при переносе свернулись в рубли: `ROUND(base_amount * value / 100)`. **`source` — это алиас источника, а не бренд заказчика** (`registry/db.py:266-269`): `kpk`, `yappi`, `vahtapro`, `aaaplus`, `ametist`, `marketstaff`; валидация в `app.py:416-418` сверяет именно с `ALL_SOURCES` (`pipeline.py:110`).

**Три стратегии** (`POST /api/rates`, `app.py:400-438`; сборка правил `_rate_rules_from_payload` — `app.py:455-496`). Это три области действия одного и того же правила, а не три разных механизма:

| `strategy` | Что создаётся | Условия |
|---|---|---|
| `all` | одно правило `RateRule(source, amount)`, `client=''`, `vacancy=''`, `min_shifts=0` | `amount > 0`, иначе правил ноль → 400 «Нечего сохранять: не заданы суммы» |
| `shifts` | по одному правилу на ступень: `min_shifts = N`, `amount = сумма` | берутся только ступени, где `value > 0 and shifts > 0` (`app.py:481-482`) |
| `clients` | по правилу (или по лестнице) на каждый выбранный объект: `client = имя объекта`, `vacancy` из payload (пусто = все должности) | пустой список объектов → 400 «Не выбран ни один объект» (`app.py:483-484`) |

Общие поля всех трёх — `note`, `payout`, `valid_from` ← `validFrom`, `valid_to` ← `validTo` (`app.py:457-462`); ступени `tiers` собираются только из элементов с непустым `amount` (`app.py:464-468`).

**`dryRun`** (`app.py:428-430`). Если в теле есть `dryRun`, ответ — `{"ok": true, "dryRun": true, "rules": N, "positions": M}`, и в БД не пишется ничего. `M` считает `_positions_affected` (`app.py:499-521`): выбирает активные позиции источника (`SELECT counterparty, object_name, vacancy_name FROM positions WHERE source = ? AND is_active = 1`) и сопоставляет в Python по `rates.client_key(counterparty, object_name)` и `vacancy_name`; пустая область означает «любой». Смысл — увидеть «затронет 56 позиций» до сохранения, а не после (`app.py:502-505`). В UI это кнопка «Проверить, кого коснётся» (`templates/navigator.html:1457`, обработчик `:2024`).

**Очистка области перед записью** (`app.py:432-434`). Для каждой уникальной тройки `(source, client, vacancy)` сначала вызывается `rates.clear_scope` (`registry/rates.py:250-268`), и только потом `rates.save_rules` (`:210-235`). Причина в комментарии `app.py:431-432`: в новой сетке ступеней может оказаться меньше, и старая ступень «от 30 смен» иначе продолжила бы висеть рядом с новыми. `clear_scope` тоже пишется в историю.

**История** (`registry/rates.py:271-281`, `:284-302`). Каждое изменение — и `set`, и `delete` — пишет строку в `recruiter_rate_history` с автором. Автор берётся из Basic-логина (`app.py:434-435`, `:447`) либо равен `"cli"` / `"cli:import"` при работе через `scripts/recruiter_rates.py`. Чтение — `history(conn, limit=50)`, `ORDER BY id DESC`; в payload навигатора уезжают последние 30 (`navigator_api.py:657-663`), показ — `viewRateHistory` (`templates/navigator.html:1497`). Удаление правила — `DELETE /api/rates/{rule_id}` (`app.py:441-452`): `rates.delete_rule` (`registry/rates.py:238-247`) читает строку, удаляет, пишет `action='delete'` в историю; несуществующий id → 404.

**Как ставка подбирается на витрине** — `rates.resolve` (`registry/rates.py:142-181`), на лету при каждом рендере (в `positions` колонки под ставку нет):

1. отбираются применимые правила: совпал `source`, `client` пуст или равен, `vacancy` пуст или равен (`:151-156`); ничего не подошло → `None`, то есть «ставка не задана», а не 0;
2. берётся максимальный `scope_rank` = `(2 if client else 0) + (1 if vacancy else 0)` (`:50-53`) — частное бьёт общее: объект+должность > объект > контрагент;
3. `_pick_step` (`:184-205`) выбирает ступень: лестницы нет → плоское правило; известен `min_shifts` → последняя ступень с `rule.min_shifts <= min_shifts`; вахта короче нижней ступени → нижняя + пометка «вахта от N смен — ниже нижней ступени»; срок не указан → пометка «срок вахты в заявке не указан»;
4. просроченные правила (`valid_to` в прошлом) **не прячутся**, а помечаются `expired` (`:63-75`) — показать сумму с пометкой честнее, чем «ставка не задана».

`client_key` (`registry/rates.py:132-139`): приоритет у `object_name`, иначе `counterparty` — у Аметиста и КНК объект приезжает в `object_name`, у Градуса и ЯППИ парсер кладёт заказчика в `counterparty`. Справочник для формы (контрагенты, их объекты и должности) собирается из живых позиций, а не заводится руками: `rates_block` (`navigator_api.py:620-664`). Покрытие — `tests/test_rates.py`, 14 тестов: приоритеты областей, ступени 15/20/30, неизвестная длина вахты, истёкшее правило, `clear_scope`, `delete_rule` с историей.
